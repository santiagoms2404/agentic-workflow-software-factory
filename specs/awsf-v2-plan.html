In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it says the same things precisely, for the people — and machines — building it.

What this is about

You built a factory. It takes a piece of work you describe, hands it to an AI assistant inside a sealed copy of your project, runs your real tests against what comes back, and holds the finished work in a waiting room until you personally sign for it. It has a rulebook bolted to the wall that cannot be argued with, and a glass wall you can watch the whole thing through. It is finished, it works, and every box on its plan is ticked.

It has only ever built one thing: itself. Every part of it quietly assumes there is exactly one project, in exactly one place, and that the factory and the product are the same building. Point it at anything else and it does not refuse — it simply has nowhere to put the answer to "which project?"

There is a second problem, smaller and more immediate. The glass wall is fogged. Watching a worker means reading a live log of what it is doing, and eighty-five out of every hundred lines in that log say nothing but the name of the kind of line they are. The information is being recorded correctly and thrown away at the last step, by one function that guesses which field to show and gives up when it guesses wrong. In the worst run measured, twelve hundred and eighty-two lines carried about four useful characters each. You would be watching all of this while overseeing everything else in this plan.

Why now

Because the next real project is waiting, it lives in three separate folders rather than one, and there is a window to do this work before it needs the factory. Building the multi-project capability against a real project with real awkward shapes is worth much more than building it against an imagined one — and the alternative is discovering every wrong assumption while under pressure to ship something else.

And because eight ideas for what to build next were written up, then deliberately attacked by a second reviewer, then judged against the factory's own workings rather than split down the middle. That judging found four things wrong with the ideas as written, and all four are cheaper to fix now, in a plan, than later, in code. The most important of the four is a habit rather than a mistake: four separate times, something was described as a wall when it was really a camera. A camera tells you afterwards that someone climbed over; a wall stops them. Both are useful and they are not the same purchase, and writing "wall" when you have bought a camera is how you end up trusting something that was never load-tested. Every one of those four claims has now been re-checked, and the ones that were wrong are written down as wrong rather than quietly deleted.

What this document actually is

This is not a blueprint. It is the commissioning list for fourteen blueprints.

Picture the factory's next expansion. Fourteen separate pieces of work, each big enough to need its own detailed drawings before anyone picks up a tool. This document names all fourteen, says what each is for, says what has already been proved and what has only been assumed, says which ones cannot start until another finishes, and writes down the five decisions still genuinely open. Then it stops. Each of the fourteen gets its own full plan later, written by its own session, and each of those stops for your approval before anything is built.

That restraint is the design. The single biggest problem with the eight original ideas was that one of them was secretly four, so no honest estimate of it existed. Splitting it into four things with four separate finish lines is most of the value of this document, and it only works if nothing here quietly reassembles them.

Five open questions — four now answered

They were written as questions with their options and no preferred answer, because a preference chosen while writing would have been a guess dressed up as advice. You then asked for a recommendation on each and took four of them, on 2026-08-21. That order matters: the trade-offs were written down before anybody had a stake in a particular one. Here is what you chose, in plain terms, and the one that is still open.

  • When one project lives in several folders, what does the agreement between them look like? — decided: a copy in every folder. The alternative was one master copy everyone points at. A copy in each folder means every folder can be checked on its own, without the checker reaching into a folder it is not allowed to touch. The obvious worry is copies falling out of step, and that is handled by giving each copy a fingerprint and having the master list say which fingerprint is correct. Copies drifting apart then shows up as a failed check rather than as a surprise months later.
  • How much should the address book eventually know? — decided: keep it small. Names, locations, and how each folder's work gets checked. The tempting extra was letting a project carry its own settings, and that was refused for a reason that will still be true later: it would let a project quietly overrule the house settings file, which is one of the two files nothing is allowed to edit without your signature. A way around a lock that nobody has to unlock is not a feature.
  • How little allowance is too little to start the next step? — decided: measure the time until it refills. The alternative was the percentage the tool reports, and the problem with it is that it is a share of something everything else you run also spends, so it says less about this job than it appears to. Time until refill does not move when something else spends. The honest gap is that time until refill does not tell you how much work fits before then, so the next improvement is already named: compare it against how long this kind of step has actually taken, which is a number already being recorded.
  • Should the numbered promises be unique inside one plan, across a project, or everywhere? — decided: inside one plan. The wider options both need something central handing out the next free number, which is exactly the kind of shared bookkeeping this project has avoided everywhere else. Referring to a promise in another plan works by naming that plan alongside the number, the same way everything else here refers across files. If it turns out that references really do cross between plans often, that is evidence to revisit it, and the hour of checking that would show it is already scheduled.
  • Can you watch something running without a program sitting there running all the time to watch it? — still open, on purpose. It received no answer in the review and should not have. It belongs to the piece of work that is named but not built, the evidence that would settle it does not exist yet, and answering it carelessly is precisely what produces the always-running program that has already been refused twice. If the answer turns out to be no, saying so plainly is a legitimate outcome, and it would be the third refusal — written down this time.

How you will know it worked

  • A project that is not this one goes through the whole factory — described, built, checked, signed for, and a copy sent out — with the record able to tell you afterwards what happened and what it cost.
  • You can read the log. Every line says something you could act on, and nothing on screen is just the name of what kind of line it is.
  • Somebody who is not an engineer completes the walkthrough on a clean machine without asking a question the guide should have answered.
  • Every claim about a wall says whether it is a wall or a camera, and says what it does not cover. This one is checkable by reading, and it is the habit the whole expansion is trying to build.
  • No house rule was changed by anything except your own signature. The factory physically cannot edit its own rulebook, and this plan does not try to invent a way for it to — that refusal is the rule working, not a gap in it.
  • The two things named but not built are still named and still not built, and neither of them quietly grew into something else while it waited.

Purpose

v1's factory is complete and its markers are all [x]. It builds one repository — this one. v2's purpose is to make it point at any of the owner's projects and carry one from an idea through to published source, with the journal and the projection able to answer what happened and what it cost.

The factory is a mix of deterministic code and non-deterministic agents, and that is not a defect to design away. The line v1 drew holds unchanged in v2: the host advances lifecycle state, models supply structured facts, and a human authorises anything that lands. Every workstream below is bounded by that line, and no workstream may relocate it.

The ceiling is stated so it cannot drift. The owner's vision is four stages — build, publish, deploy, monitor. v2 builds the first two. Deploy and monitor are declared here as workstreams W13 and W14 so the whole is written down and sequenced, and each is authored after v2's core lands. Naming them now is what stops them being absorbed into an adjacent workstream by accident.

Out of scope for v2, explicitly: environment configuration, release migrations, rollback orchestration, operational acceptance, and any resident background process. A candidate that needs one of these is deferred to its own workstream rather than widened into a neighbouring one.

Problem

Eight candidate areas were worked up, adversarially reviewed, and adjudicated against this repository's own code. The adjudication found that the set could not be handed to a build in the shape it arrived in — for four reasons, each of which this spine is built to answer.

One candidate held four architectures

The greenfield planning candidate was written as one thing and contained four: a host-owned bootstrap, a project registry, a chain of compiled recipes, and a five-stage ladder. It had no single acceptance boundary, so no estimate of it could be honest. The adjudication's remedy was a split, and this spine is that split made structural: W03, W04, W05 and W11 are four workstreams with four deep plans and four acceptance boundaries, not one.

Prevention was repeatedly described as stronger than it is

This is the set's dominant pattern rather than four separate incidents, and it is the thing to watch for in every deep plan authored below. Four claims were checked and falsified:

  • agy was called "bounded by worktree containment plus host-side stream inspection." core/src/policy/path-policy.ts compares a worktree fingerprint after the provider returns, and core/src/policy/sandbox-broker.ts degrades to tool-policy where bwrap is absent — which is the case on the development machine. The route is detection-bounded, which is a weaker guarantee and must be described as one.
  • mf was credited with per-role supervision. Only the outer mf process crosses core/src/execution/transport-broker.ts, so no constituent provider launch gets a registration, a reservation id, or its own GO. The gap is supervision and attribution — not arithmetic: settle(id, spent) already handles the halfway composite, and saying otherwise suggests a ledger redesign that is not needed.
  • marimba's boundary was called "bounded by construction" because processOwnerTerminal() checks process.stdin.isTTY. That is a terminal-shape test. Reproduced: script -qec yields stdin.isTTY=true and a scripted answer clears the confirmation. It prevents an accidental non-interactive invocation; it prevents nothing deliberate.
  • "No awsf command mutates outside the state root" is false twice: defaultWorktreeRoot(stateRoot) returns a sibling directory, and land fast-forwards the canonical repository by design.

Three of the four have since been repaired or restated. The fourth — marimba's boundary — was rebuilt at the tool surface, where the guard now denies the six owner-act command shapes by name. The pattern is what survives, and it is a standing instruction to every deep plan below: name the mechanism, then name what it does not cover.

Protected revisions are not factory-buildable

path-policy treats protected-path as an independent rejection reason, checked alongside the write globs. So no configured agent can write AGENTS.md or awsf.config.yaml — not even the documenter, whose write glob is **/*.md. Five of the eight candidate areas imply an amendment to one or both. Any plan that assumes an agent will make that edit fails at its own gate.

The owner reads the factory through a surface that discards what it records

Measured read-only against the live projection on 2026-08-20: 85.3% of every row in the projection is a text.delta, 92.2% in the worst phase, and 918 KB of stored payload bytes against 742 KB for everything else combined. The largest run reassembles to 5,490 characters across 1,282 chunks — about four characters per row, each wrapped in roughly 165 bytes of envelope. Those rows render as the word text.delta, because EventLog.vue's summary() is a five-key fallback chain and anything it does not match falls through to item.name || item.type. This is the surface the owner will read while driving all thirteen other workstreams.

Solution

Fourteen workstreams, each with its own deep plan, its own acceptance boundary and its own Questionables. This document is the spine that holds them: what each is for, what it may not assume, what it depends on, and what evidence it already has.

Five owner decisions are constraints here, not questions. They were taken before this plan was authored and no deep plan may reopen them:

  1. A project may span several repositories; a task owns exactly one. AttemptStatus carries one repository and one worktree, landing is atomic per repository, and a partial cross-repo landing has no rollback story. Cross-repo work is a parent coordination record plus declared contract artifacts between single-repo child tasks.
  2. The registry has two layers. A committed catalog — project identity, which repository holds the plan and which hold code, each repository's default branch and gate commands, delivery posture, the relationships between them. And a machine-local placement layer — where each clone sits on this machine, and per-project worktree roots. The split is forced by code: core/src/config/load.ts refuses absolute machine paths outright. The state root stays out of both — one state root per machine, projects namespaced inside it, because doctor, gc and db rebuild each operate over one root.
  3. marimba is the driving role, and its boundary is enforced at the tool surface. It keeps --dangerously-skip-permissions, and its guard denies both delegation-shaped tool names and the six owner-act command shapes. The TTY check is a terminal-shape test, not an authorisation boundary, and no document in this set may describe it as one.
  4. Invariant and protected-config changes are proposed by marimba and approved by the owner, one at a time. Each amendment names the invariant, what it blocks today with evidence, the replacement guarantee in still-mechanically-checkable form, its cost, and the alternative that avoids the amendment entirely. The amendment lands as an owner-approved commit before the build that depends on it.
  5. Quota is a readout, never a router. Preflight is something the owner reads before starting. At a phase boundary the host may read the window, journal it as explicitly non-attributable context, and stop at AWAITING_OWNER rather than launch the next phase when the remaining window is too small. No timer, no automatic resume, and no per-task cost derived from an account-wide percentage.

Four rules the intent imposes on the plan itself

  • No workstream may put a skill in the execution path. A gate never depends on a document having been read. This is not style: pi-codex launches with --no-skills, so a phase on that route cannot reach an installed skill at all. W05's recipes are compiled recipes with typed envelopes for exactly this reason.
  • Work that cannot land from a managed worktree is owner-side and stays out of the task graph. The owner's shell functions, installed skills, machine-local settings, and upstream contributions to another repository are all named as owner-side below and none of them is a ticket.
  • Every claim carrying a decision names its evidence and the cheapest unused upgrade that would strengthen it. Each workstream's block below carries that pair, and the requirement passes down to every deep plan.
  • A revision restates its guarantee in still-checkable form — and first checks whether the guarantee is already enforced somewhere stronger. This rule was earned: a guard was installed at .claude/settings.local.json where execution-isolation.test.ts already asserted that .claude/ must not exist at the repository root at all. A new weaker guarantee was proposed beside a stronger one that had not been read.

The two ordering gates this spine cannot resequence

G1 — composition before roles
W06's centralisation of prompt composition lands before W05 adds any new agent role's prompt path. core/src/cli/commands/production-run.ts, core/src/cli/commands/review-phase.ts and core/src/cli/commands/rework.ts each compose a system prompt independently. W05 introduces an architecture-reviewer role. Adding it before the three sites are one site creates a fourth copy, and the shared block then has to be retrofitted into four places instead of written into one. Note the inversion: W05's deep plan is authored before W06's, because W06 must know which roles it is centralising for — but W05's new-role code lands after W06's centralisation. Authoring order and build order differ on this one edge, deliberately.
G2 — amendment before the build that needs it
An invariant or protected-config amendment lands as an owner-approved commit before the workstream that depends on it starts building. No agent can write AGENTS.md or awsf.config.yaml: path-policy rejects protected-path independently of the write globs. Do not invent an owner-authorized protected-change mechanism to route around it — that is the boundary working. W08 is the workstream this gate actually blocks today; W13 will be the second.

Owner-side work — named, and deliberately not ticketed

None of this can land from a managed worktree, so none of it is a task in any deep plan. It is listed here so a planning session does not discover it mid-build and quietly widen a workstream to absorb it.

  • Every invariant and protected-config amendment. One owner-authored commit each, one at a time, recorded in the Amendments section of the plan that needed it.
  • The plan-sota rename and its memory files. Done on 2026-08-20, outside every managed worktree, and it must not re-enter a task graph as if it were factory work.

Writing the checklist costs an hour, needs no hardware, and stops the first Mac visit from discovering its own scope. Not a ticket; a note to the owner.
  • Upstream contributions to another repository, including anything sent to the credential broker this project reads from.

DECIDED Q1 — What is the exact shape of the cross-repo coordination artifact between single-repo child tasks? (W04)

Decided (2026-08-21): an immutable contract artifact committed in each child repository — owner verdict via the exported plan-sota-review v1 block. See Amendments.

What the decision buys, and it is the reason to prefer it: a child repository's gate reads its contract from inside its own worktree. The parent-owned alternative would have put the contract outside every child, so a gate would have to reach across the worktree boundary path-policy exists to hold — a new hole in the boundary, opened for a convenience. The generated-package alternative needs a publication step v2 does not have: W08 publishes source to a bare remote and publishes no packages, and a build-time dependency between repositories reintroduces the cross-repository ordering that decision 1 refused.

The cost is N copies that can drift, and it is paid with machinery this repository already runs. Make the artifact content-addressed, have the parent coordination record name {child repository, contract digest}, and add a meta-test asserting each child's copy hashes to what the parent names. That is the same shape as the ticket/plan sync fence, which is a byte-identity check between two copies of one prompt. Drift stops being a hazard and becomes a red test. Changing a contract then costs a new digest plus a coordinated commit in every child — the right price, because it is a breaking change across repositories and should cost something. W04 owns the mechanism; the shape is settled.

What is already decided and is not in question: a project may span several repositories, a task owns exactly one, and cross-repo work is a parent coordination record plus declared contract artifacts between single-repo children. AttemptStatus carries one repository and one worktree; landing is atomic per repository; a partial cross-repo landing has no rollback story. The option set, retained so the road not taken stays readable. An immutable artifact committed in each child keeps every repository self-describing and survives a child being read alone, at the cost of N copies that can drift. A parent-owned record referenced by id has one source of truth and no drift, but a child read in isolation cannot resolve its own contract. A generated interface package makes the contract a build-time dependency and therefore mechanically checkable, at the cost of a publication step that v2 does not otherwise need. DECIDED Q4 — What are the threshold and the units for the phase-boundary stop? (W07)

Decided (2026-08-21): absolute time remaining — minutes to window reset — with the threshold configured per route rather than hard-coded. The owner directed, in the same review, that the recommending session's answer be taken with its reasoning; it is recorded in full below rather than as a bare choice. See Amendments.

Why not the percentage. It is the number the tool hands you and the weakest of the three. The adjudication already stripped the attribution claim from this candidate because an integer percentage of an account-wide window carries no task identity — another client on the same account moves the same number. Using that number as a threshold inherits the same defect at coarse resolution, and it would read as a measurement of this task while measuring the account.

Why not estimated calls. It is the only unit that is about the work rather than the account, and that is what makes it the right eventual answer. It is a ratio of two estimates today: a ceiling, which is an authorisation rather than a prediction, over a per-call consumption nobody has recorded. It would be wrong often, and its wrong direction stops work that could have run. It becomes buildable once provider-authoritative per-call usage has history — the number the adjudication points at, which already has task identity attached.

Why time. It is the unit the owner reasons in, the reset clock does not move when another client consumes the account, and the reset time is a reported field rather than a derived one. The catch, stated rather than buried: time to reset says when the window resets, not how much work fits before it. So W07 ships a configured threshold in minutes and names the upgrade in the same breath — compare the remaining window against the next phase's observed median duration, which the projection already records. That turns a magic number into a comparison against measured history, and it is a versioned change rather than a drift.

What is settled: the host may read the window at a phase boundary, journal it as explicitly non-attributable context, and stop at AWAITING_OWNER rather than launch the next phase. No timer, no automatic resume. The option set, retained so the road not taken stays readable. Percentage of the window is what the tool reports directly and needs no derivation — but it is an integer percentage of an account-wide figure that another client on the same account moves, so a threshold in percent is a threshold on a number that is not about this task. Absolute time remaining is the unit an owner actually reasons in and it survives another client's consumption better, but it needs the window's reset semantics to be read correctly rather than inferred. Estimated calls against the next phase's ceiling is the only unit that is about the work rather than the account, and it is the most likely to be wrong, because the estimate comes from a ceiling rather than from the phase. Unchanged by the decision: the probe needs a stated failure posture — hard timeout, fail-open, and what is journalled when the read fails. What is genuinely missing — the deep plan's actual work

  1. A sealed attempt's candidate lands on no ref. This is the single most necessary piece and it is small. Every candidate this factory has produced is a dangling commit, reachable only through a worktree and one reflog entry; three were preserved by hand-tagging during one session, and one was very nearly lost. A batch of eight unattended runs produces eight commits git is entitled to collect before the owner wakes up. The host should write a ref at seal time. Nothing else in away mode is safe until this is.
  2. The queue itself — written from the dashboard, drained by a session. See the boundary below for why those must be two different actors.
  3. Visual-review classification. Derive it from the candidate's own diff against the project's declared delivery posture, not from a new ticket field. A derived answer cannot go stale the way a hand-set flag does, and it needs no schema change.
  4. Seeding cost, which is the practical blocker nobody has hit yet. awsf start copies the configured runtime.seed_paths into each attempt's tree; on this repository that is node_modules at 139 MB, and on a network-backed filesystem a single start takes many minutes. Eight sequential tickets is hours of copying before the first provider call. Away mode is not pleasant until seeding is shared or cached, and a deep plan that ignores this will produce a feature nobody uses overnight.
  5. Batch budgeting. Ceilings and spend are scoped to a task. Eight tickets are eight independent ceilings and no total, so a batch can exhaust a subscription without any single attempt exceeding anything. Away mode needs a notion of budget the lifecycle does not currently have.

Each of these is load-bearing, and away mode is compatible with all of them — the owner's own framing already respects the first.

  • No push path (invariant 8) and no skill in the execution path. A merge to a production branch is a local act the owner authorises.

Three findings from live drives that bear directly on this

  • Unattended recovery cannot lean on rework. Offered without recommended defaults, in the manner this plan's Questionables use, so that authoring the deep plan is a decision rather than a formality.
