In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it says the same things precisely, for the people — and machines — building it.

A fuel gauge you read before setting off, not a hand on the wheel

The owner pays for several assistants by subscription. Each one allows a certain amount of work inside a repeating window of time, and when the allowance runs out the assistant simply stops until the window resets. Today there is no way to see how much of each window is left without leaving the workshop and asking each provider by hand. This plan adds a gauge. The gauge only shows a number. It is never allowed to steer.

Why now, and why so narrow

An earlier review looked at a bigger promise attached to this idea and refused it. The promise was that reading the gauge before and after a job would tell you what that job cost. It cannot. The number is a whole-household reading: anyone else using the same account moves it, it is rounded to whole percentage points, and nothing in it says which job was running. So the gauge stays a gauge. The workshop already keeps a separate, exact record of what each job consumed, reported by the provider itself and stamped with the job's name — that is the record to build a cost figure on, and this plan points at it rather than competing with it.

Three pieces, and one wall

First, a report the owner reads before starting: for each assistant the project uses, how much of the window remains and how long until it resets. Second, a note written into the permanent record at each pause between stages of a job, labelled in the record itself as not attributable to this job, so nobody can later mistake it for a cost. Third, a stopping rule: if too little time remains before the window resets, the workshop finishes the stage it is on and hands the job back to the owner rather than starting the next one. Adding that handover is itself a change to the small set of moves the workshop is allowed to make, and only the owner can make that change — so this plan asks for it up front rather than discovering it halfway through. It then waits. There is no clock that restarts it and no automatic resumption — only a person can start it again. The wall is the fourth piece: a test proves that the part of the workshop which decides who does the work cannot see the gauge at all.

How anyone would know it worked

A real reading from the tool was captured once, stripped of anything private, and stored in the workshop so every test afterwards runs against those exact stored bytes and costs nothing. The report shows the correct figure even when a stored reading is deliberately built so that the raw parts disagree with the summary. An old version of the tool is refused by name. When the reading fails or times out, work continues and the failure is written down — a broken gauge never stops the car. The handover to the owner happens at the pause between two stages, and nothing restarts it. A handover triggered by a broken gauge is refused outright, which is a stronger promise than merely not acting on one. And there is one thing deliberately missing, written down as missing: the exact bytes the tool produces when it is itself being rate-limited cannot be conjured on demand. So the workshop keeps them by itself the next time it happens — it sets the unreadable reply aside in a private place nobody else can read, and notes where it put it, rather than relying on someone being at the desk that day.

Purpose

Give the owner one honest number before spending, and one honest note in the record while spending — and make it structurally impossible for either to become an input to a routing decision. Every rule below was produced by a failure rather than by a preference, which is why this workstream's contract arrived settled and this plan implements it rather than re-deriving it.

The workstream is small on purpose. It adds no task state, no legal transition, no daemon, no timer, and no dependency. Its largest single risk is not that it will be built wrong — it is that a plausible convenience (let the router prefer the provider with more headroom) will be built on top of it later, and this plan spends three of its nineteen tasks making that convenience turn a test red.

Problem

Four problems, and they are not the same size.

1 — There is no readout at all. Nothing in core/src reads a provider window. The owner's only current signal is a quota normalized event, which an adapter emits when a provider has already refused the call. That is an obituary, not a gauge.

2 — The headline claim of the source candidate is false and must not be rebuilt. The candidate called a phase-boundary snapshot "the leverage": a real denominator for the call ledger's proxy unit. An account-window percentage cannot be that denominator. Another client on the same account moves the same number, the figure is an integer percentage, and nothing in the payload carries task identity. The adjudication upheld the refusal. What is left is context, and it has to be labelled as context in the record, not in a comment.

3 — Two corrections the source left open. It pins quota-axi@0.1.29 while also recommending an unpinned npx -y quota-axi that may resolve elsewhere; and a probe that sits between two phases has no stated failure posture — no timeout, no fail-open rule, and nothing said about what is journalled when the read fails.

4 — The fixture-first rule is currently satisfied by captures held outside the repository, which is exactly the residual the rule exists to prevent. A rule whose evidence lives on one laptop is a rule with no witness.

Solution

One pure parser, fed by one injected process capability, read by two consumers, and surrounded by three fences.

The parser is pure and takes now as an argument. It never reads the clock, never touches the filesystem, and never spawns. Everything it needs arrives as bytes. That is what makes every test in this workstream offline and deterministic, and it is what lets a single scrubbed capture in the tree serve the whole parser surface.

The process capability is injected, not imported. node:child_process is importable in exactly one module by invariant 3, and runSystemCommand in core/src/execution/transport-broker.ts is already the shape this needs: executable, argv array, timeoutMs, explicit env, bounded maxBuffer. The quota module takes that function as a parameter. It therefore needs no fence exemption, and the hard timeout the failure posture requires comes for free from the capability that already has one.

Spawn on PATH, never fetch. The settled contract says spawn on PATH rather than import. npx -y quota-axi is neither: it resolves a package at run time over the network and can land on a version this parser has never seen. resolveExecutable("quota-axi", env) against the spec's own PATH is the whole resolution, and a missing executable is a named, journalled unavailability — not a crash and not a stop.

Two consumers, deliberately different. The preflight readout is interactive, renders for a person, and may take longer. The phase-boundary probe is on the critical path between two phases, has a tighter timeout, fails open, and writes a record whose own fields say it is not attributable to the task it sits inside.

The Runtime Contract

Settled by the spine and unchanged by review. This plan implements it; no task may re-derive it.

Render sourceFrom quotaSemantics.effectiveAvailability and never from windows[]. An account window can bound every model window, so a model window read in isolation reports headroom the account does not have.
State detectionStructurally, from state.status and quotaSemantics.status. Never by exit code. Exit 0 means only that at least one provider returned data fresh or stale, and a stale report keeps raw windows for diagnostics while its effective availability is unknown. Branching on the exit code reads a stale percentage as current headroom.
FlagsNever --refresh, never --tui, and — added here — never --once (a TUI flag) and never --full. The argv is exactly ["--provider", "<csv>", "--json"].
InvocationSpawn on PATH, never import. npx -y is not a PATH spawn and is barred by the same rule.
ParsingFixture-first, over scrubbed captures held in the tree.
FenceNothing under core/src/workflow/** and no routing resolver may reach the module.
Decision inheritedQ4, decided 2026-08-21: the unit is absolute time remaining — minutes to window reset — with the threshold configured per route. The upgrade ships named alongside it: compare the remaining window against the next phase's observed median duration.
Two additions this plan makes to the flag rule, with their reasons

--full is barred because it is the flag that exposes account.accountId, provider label/source, and per-source attempt paths. Invariants 1 and 9 both bite there, and the fixture would inherit the exposure. The check that makes this safe rather than merely cautious: every field this plan branches on is in default --json. The demoted set is window percentUsed/startsAt/windowSeconds, the pace cycle-progress inputs, quotaSemantics.description, and scope pace behindWindowIds/onPaceWindowIds. resetsAt, runway, state.status, quotaSemantics.status and unresolvedWindowIds are all present without it.

--once is barred because it belongs to the TUI, and a rule that names two TUI flags but not the third is a rule that will be defeated by autocomplete.

The derived-field rule — how minutes-to-reset is obtained without reading windows[]

The two settled rules appear to conflict: render only from effectiveAvailability, but report a reset instant that lives on a window. They do not. effectiveAvailability selects which window binds; the reset instant is then read from that named window and from no other. The scope's runway supplies limitingWindowId and, for a finite projection, usableRunwaySeconds and projectedExhaustedAt; boundedBy names every window included in the effective figure. The forbidden act is choosing a window by scanning windows[] — never the act of dereferencing the one the effective figure already named.

Written as a rule a test can hold: no code path may index windows[] except by an id that came out of effectiveAvailability. When runway.status is through_reset there is deliberately no synthetic deadline and the reset instant is the binding window's resetsAt. When it is unknown, minutes-to-reset is null — never zero, never inferred.

The Two Ordering Gates This Plan Introduces

G7-A — the permission amendment lands before M3 builds

Q4 requires the threshold to be configured per route. Every candidate home for it is a protected path. awsf.config.yaml and awsf.project.yaml are both listed under policy.protected_paths, and path-policy treats protected-path as an independent rejection, so no agent can write either one under any write-glob. This is the same shape as the spine's G2: one owner-authored commit, landed before the workstream that depends on it starts building.

It is not only a protected-path question. awsf.config.yaml's header and core/src/config/schema.ts's header both state the same durable intent: "no machine paths, no credentials, no PIDs, no quota fields." That line is documentation rather than a meta-test — core/src/config/load.ts enforces absolute paths and credential shapes and nothing about quota — but it is the file's stated contract and a plan that quietly widened it would be doing exactly what the fourth shared rule forbids.

The amendment restates the intent rather than deleting it. The reason "no quota fields" was written is that quota state is live, machine-local, and different every minute — invariant 1's territory. A per-route threshold is none of those: it is a durable policy number the owner chooses once. The amendment says so explicitly, so the boundary stays legible: measured quota state never appears here; a durable quota policy threshold may. That is a narrowing of an ambiguous sentence, not a loosening of a checked rule.

The gate is the permission, not the values — and the order matters more than it looks. RoutingSchema in core/src/config/schema.ts carries additionalProperties: false, and load.ts hard-fails on a schema mismatch. Writing a quota_stop block into awsf.config.yaml before the schema accepts it therefore breaks every AWSF command at load time — observed directly: config does not match awsf/v1: /routing/quota_stop: Unexpected property. So G7-A is the one-line durable-intent change and nothing else. The schema extension is T07's work and is agent-writable, because core/src/config/** is not a protected path. Actual threshold values are a separate, optional, later owner commit once T07 has landed: the block is optional, and absent means the stop is disabled, so the repository's own config need never carry one.

M1 and M2 do not wait on it. The fixture, the parser, the probe, the version floor and the failure posture are all independent of where the threshold lives. Only M3 onward is gated.

G7-B — the legal-edge amendment lands before M6 builds

Owner verdict, 2026-08-24: the stop gets its own legal edge. L26 — RUNNING → AWAITING_OWNER, actor host, not a spawn site, not interactive, not a correction edge. core/src/state/** is a protected path, so like G7-A this is one owner-authored commit landed before M6 starts building. Two files move in it: the edge in core/src/state/task-machine.ts and its guard in core/src/state/guards.ts.

Its cost, measured rather than estimated. The plan's first draft claimed this amendment would also move the SQLite check constraints. It does not. 0001-initial.sql declares from_state TEXT NOT NULL, to_state TEXT NOT NULL and edge_id TEXT NOT NULL with no CHECK on any of the three. No migration is touched, which also means the protected migrations/** directory stays shut and this remains one amendment rather than two. What genuinely moves is four things: the EdgeId union and LEGAL_EDGES (owner, protected); the guard, which Readonly<Record<EdgeId, …>> makes a typecheck error to omit rather than something anyone could forget; and two test-side files an agent may write — the mirror table in core/test/unit/_lifecycle-tables.ts, where the pair moves out of the illegal set, and assert.equal(LEGAL_EDGES.length, 25) at core/test/unit/transitions.test.ts:67.

The objection the source itself raises, and its answer. _lifecycle-tables.ts states why this pair was illegal: "RUNNING → AWAITING_OWNER skips gating." That reasoning is about advancing work without gating it. A quota stop does not advance work — it suspends it, with no candidate and no gate run. The question is therefore whether a task suspended this way could reach LANDING without gating, and it cannot: L20's guard already requires gatesPass, a 40-hex candidate, and a displayed SHA equal to that candidate. The bypass is closed by machinery that predates this workstream, which is exactly the check the spine's fourth shared rule demands before a plan proposes a new guarantee.

What the edge buys that the alternative could not. L26's guard is where INV-4 stops being a property of how the comparison is written and becomes a property of the machine: an unavailable, stale, or unknown reading cannot form a legal transition at all. A future edit that made the host try to stop on a broken gauge is refused by the state machine rather than by a code shape someone could refactor away. The rejected alternative — firing at L12/L15 — would have entangled quota with the tier fork out of GATING and with review-verdict consistency, putting a quota condition inside two guards that exist for other reasons.

M1 through M5 do not wait on it. Only M6 is gated.

DECIDED Q1 — Where may the stop legally land? There is no RUNNING → AWAITING_OWNER edge.

A multi-phase workflow spends its inter-phase boundaries inside the RUNNING sojourn, so the spine's "the stop lands at AWAITING_OWNER" and its "phase-boundary" could not both be taken literally without a new edge.

A cost this plan claimed and then measured, wrongly stated the first time. The first draft priced this option as "a twenty-sixth edge, the SQLite check constraints, the lifecycle tables, and a new way out of RUNNING." DECIDED Q5 — What is the version floor, and how strictly is it enforced?

Necessary and not sufficient, and the module says so. A 0.x minor bump can change a payload. The preflight readout is something a person asked for and will wait a moment for, and a timeout there is worse than a short wait.

Why not adapt on first use. An adaptive timeout is state, and the only places it could live are a runtime artifact (invariant 10) or the projection (a write path this workstream deliberately does not open). A configurable constant is the cheapest thing that is also honest about being a guess.

This is worth stating precisely, because the workstream's lost claim leaves an obvious gap and the obvious wrong way to fill it is to try again with better arithmetic.
