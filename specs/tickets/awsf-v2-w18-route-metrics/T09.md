## What this ticket is

An **implementation** UI ticket: the grouped table behind every tile, and the single-run view each run card opens. The Run view is where D4's override is prepared, as a command the owner runs, because the dashboard may not write.

The shared conventions (execution, the write boundary, the owner gates, the never-do list)
are in [`./README.md`](./README.md) and Section A of the build prompts, and apply unchanged.

The `## Handoff` section below is empty at authoring. The owner appends dated, numbered entries
(C1, C2, …) there at landing, from the findings earlier tickets return in their envelopes. It holds
no placeholder because a shift hands that section to the builder after the prompt as text that
wins over it. It sits above the prompt because the sync fence compares everything after the prompt
heading with Section B byte for byte.

## Handoff

### 2026-09-28 — from T03 (delivered as `b8402fc`)

**C1. The command to compose.** `awsf attribute <task> --attempt <n> --cause
<model|factory|environment|owner|unknown> --reason "<why>"`, built as `attributeCommand` in
`core/src/cli/commands/attribute.ts`; the causes are `ATTRIBUTION_CAUSES` in
`core/src/contracts/attribution-record.ts`. It refuses any attempt that is not BLOCKED
(`AttributeAttemptNotBlocked`), so show the pills only for BLOCKED runs. It refuses an empty or
credential-shaped reason, and it asks the owner for y/N at the terminal. Escape any `"` in the
composed `--reason`.

**C2. Repeatable, latest wins.** A second attribution of the same attempt is a correction: it is
appended, the latest is in force, and the earlier one stays on file. The panel should show the
record in force and still offer the pills.

**C3. Where the recorded override lives.** Role rows carry only `attribution`,
`attributionSource` and `heuristicAttribution`. The reason and date are on
`RunFacts.ownerAttribution`, and in the `events` row of type `attribution` (payload `attempt`,
`cause`, `reason`, `at`). If T05's payload does not expose them, T09 absorbs adding them there:
the dashboard cannot query the database itself.

**C4. Registration.** The command is unregistered until gate G18-C. A composed command fails as
an unknown command until the owner commits G18-C.

### 2026-09-28 — from T07 (delivered as `5f93651`)

**C5. The run route is wired.** `#/metrics/run/<sessionId>` parses to `route.view === "run"` and
`route.run`. `runsInLens(payload, route)` in `dashboard/src/metrics-lens.ts` is the picker's list,
newest first, lens applied; move between runs with `withRun`. The run branch of the view section in
`dashboard/src/routes/metrics.vue` is your placeholder.

**C6. The override record is already in the payload.** `MetricsRun.ownerAttribution` carries
`{ cause, reason, at }`, so C3's "absorb adding them" is not needed.

**C7. Ledger state goes in the hash.** Grouping, the column families and the sort are not in
`MetricsRouteState` yet. Add them to `parseMetricsRoute` and `metricsRouteHash`, writing only
non-defaults. T08's tile click opens the Ledger grouped by run, so the group key is shared.

**C8. The mini card's controls.** On the sessions board the metrics link and the archive button sit
in `.card-controls` beside the card's anchor, and the archive keeps its text form (O2). The Run
view's mini card is its own markup; do not copy the frame's round archive button.
