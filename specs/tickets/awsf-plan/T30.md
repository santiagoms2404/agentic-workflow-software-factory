## Scope note — why this ticket has two parts

Scope was amended on 2026-08-13, before any T30 call was spent. Driving-session preflight
found that **no live tier-2 execution path exists**, so the pilot could not have started:

| Missing | Evidence |
|---|---|
| Tier-2 admission | `production-run.ts:68` supports only `build`/`plan-build-test`; `:316` rejects `status.tier !== 1`; `rework.ts:74,294` the same |
| Inversion in production | `workflow/review-routing.ts` is imported by nothing outside `core/test` |
| `verdict_consistent` in production | `gates/review.ts` likewise |
| `journey_passes` in production | `gates/journey.ts` likewise; `journeyApproved` is hardcoded `true` at `production-run.ts:839`, `rework.ts:870`, `run.ts:46` |
| A writer for the inversion proof | `sessions.review_provider`/`review_verdict` are read at `api/routes.ts:346-347` and written nowhere |
| Review presence at landing | `requiredReviewPresent` is hardcoded `false` at `production-run.ts:838` |

This is unassigned scope rather than a defect: T20's checklist proves the opposite-provider
review **on stubs**, M5 closes by permitting real write-capable runs *"from M8's pilots only"*,
and the acceptance row for the delivered production seam names **T1** explicitly. T30 is simply
where the live wiring is first needed.

It is carried here rather than in a new ticket because the enforced ticket contract
(`core/test/unit/meta/ticket-plan-sync.test.ts`) requires zero-padded `T\d\d` ids forming a
contiguous prefix, with `depends_on` ordered by that number — so no task can be inserted
between T29 and T30, and appending one could not express the dependency. The alternative was
renumbering five existing tickets and every reference to them.

The guards that matter are already correct and fail closed — `guards.ts:284` refuses to land a
T2 attempt whose review is missing or whose journey is unapproved. Part 1 stops handing them
constants; it adds no new safety machinery.

## Scope note — the Part 2 prerequisite, added 2026-08-13 after the first Pilot 2 attempt

Pilot 2 was attempted and **stopped after one builder call**, exactly where a red deterministic
gate requires. The host ran the exact configured argv against the exact candidate and measured
240 total / 239 pass / 1 fail; the attempt reached `BLOCKED` through `phase-abort` with no
reviewer call, no journey, and nothing landed. Two defects made a retry the wrong move rather
than merely an expensive one:

| Defect | Consequence |
|---|---|
| No live same-session correction transport | `awsf retry` mints a fresh attempt from canonical HEAD with a fresh provider session, buying the whole builder again to rediscover a failure the host had already measured |
| Command evidence was `output.slice(-4000)` | The retained segment carried the 239/240 totals but began mid-test and omitted the failing test's identity — the one thing needed to correct it |

Both are now repaired, hand-built at **zero AWSF provider cost**, and recorded in the plan
Amendment `#t30-continuity-prerequisite-2026-08-13`. A deterministic configured-command failure
is now a correctable gate violation inside the phase that produced it, answered by the same
provider conversation, bounded by `risk.correction_allowance`, and priced in tokens rather than a
tier call — in **both** provider directions. Every candidate is re-gated in full, and the
opposite-provider review still runs only after green gates.

**This changed no marker.** The prerequisite is not Part 2. T30 remains `todo`, M8 remains
`[wip]`, and every T30 acceptance row remains unchecked until a real pilot lands. The next
driving session must configure the builder `harness.continuity: same-session`; without it the
route keeps the pre-continuity behaviour and a red gate blocks on L8 as before.
