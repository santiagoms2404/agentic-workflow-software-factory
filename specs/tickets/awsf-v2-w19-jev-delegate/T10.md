## Handoff

### 2026-09-29 — from T04 (delivered as `777f8a6`)

**C1. The facts hold one quota row, not the two windows.** `StopFacts.quota` in
`core/src/delegate/stop-facts.ts` is the newest `quota-snapshot` journal record: percent
remaining, minutes to reset, reason code, the completed and next phase keys, and `observedAt`
(the record's `recorded_at`). It covers one account window, the one the boundary's route
selected. The journal doesn't say whether that window is `five_hour` or `seven_day`, except
through `window` (the binding's `scope`), which is set only at a quota-pause checkpoint. So
`planResume`'s two-window input can't come from stop facts alone. Read the windows where this
prompt says (`parse.ts`/`readout.ts`), and treat stop facts as the record of which boundary
stopped.

**C2. Neither resets-at nor pace reserve is journaled.** No `core/src` file records a pace
reserve, and `parse.ts` turns the provider's `resetsAt` into `minutesToReset` before anything is
journaled. If `planResume` needs an instant, it works from the parsed readout it is given. Stop
facts won't supply one, because T04 was forbidden from inferring it.

**C3. `expectedDraw` samples exist.** Each boundary journals a `quota-snapshot` with
`completedPhaseKey`, `nextPhaseKey` and `effectivePercentRemaining`, and its journal stamp orders
the sequence. The drop between consecutive snapshots around a phase is the sample this prompt
describes. `evidenceOf`-style filtering over `JournalRecord<AttemptEvent>[]` is all it takes (see
`stop-facts.ts`).

**C4. Quota stops never fire in this repository today.** `routing.quota_stop` is unset in
`awsf.config.yaml`, so neither quota-pause nor L26 is ever reached here. T04 covers both with
synthetic fixtures only.
