### 2026-09-25 — from T11

**C1. SCOPE you can skip: `core/test/journeys/shift-blocked.test.ts` exists and passes.** It is task 13's
first row, built by T11 because T11's own DONE WHEN named it. Re-run it and flip the row with that evidence.
Do not rewrite it. It has two cases: a red gate (`exit 1`) on ticket 3 of 6, and a gate command with no exit
status on ticket 3.

**C2. CONTRADICTION: "blocks" is not the lifecycle `BLOCKED` state. The code wins.** `BLOCKED` is sealed and
`awsf resume` refuses it, so a red shift ticket stops at `RUNNING` under a `ticket-block` recovery checkpoint,
with `status.blocker` set. Assert `recovery.kind === "ticket-block"` and `blocker.source`, never
`lifecycleState === "BLOCKED"`. The plan's M4 diagram still draws `BLOCKED --> RESUME`. The 2026-09-25 task 11
Amendment is the correction.

**C3. FINDING for the ref rows: a ticket-blocked shift is not sealed.** Task 12's ref is written at seal time,
so none is written when a shift blocks at a ticket. Until the shift reaches a sealed state, its prefix commits
are held only by the worktree's detached HEAD. The "survives an aggressive pruning pass" row is about sealed
candidates. Do not extend it to a blocked shift without deciding that separately.

**C4. SCOPE limit: resume re-measures, it does not rebuild.** A resume re-runs the blocked ticket's gate phase
against the same candidate. A red caused by the ticket's own code re-blocks on every resume, at no call. A red
found inside the build still blocks terminally on L8, as does a measurement that throws. That covers a
same-session builder whose `verifyCandidate` correction is spent, a dirty tree, a moved candidate and a
command-ledger refusal. Only a cold builder's red reaches `t<NN>-tests`, and the fixture builder is cold.

**C5. OPTIONS rejected, not to be re-litigated:** an edge out of `BLOCKED` (it breaks the sealed-state
contract); rebuilding the ticket in place on resume (it repeats an accepted model turn, and collides with the
immutable per-phase envelope and the unique run id); `awsf retry` (a fresh attempt with no prefix); `rework`
(fenced by `shift-no-rework-import.test.ts`, because every rework phase is `maxCorrections: 0` and it rejects
credential-shaped output that a normal run scrubs).

**C6. FINDING: a re-measured gate phase writes rows under a later round.** The round is the count of earlier
`ticket-block` records for that phase. So a resumed `t03-tests` writes gate rows with id `…:t03-tests:1:…` and
command output `command-t03-tests-test-1.txt`. A red shift ticket also writes no test envelope. The accepted
green measurement writes the phase's only one, at round 0. A reader that keys gate rows by `:0:` misses the
resumed measurement.

### 2026-09-25 — from T12

**C7. SCOPE you can skip: task 13's rows 2, 3 and 4 are already built in `core/test/unit/candidate-ref.test.ts`.**
The ref is created, is not a branch, and a repeated write returns `unchanged`. Three chained commits survive
`gc --aggressive --prune=now` with reflogs expired, plus `prune --expire=now`, when the tip ref exists, and all
three are gone without it. A last case asserts invariant 8's two fences name no exemption. Re-run the file and
flip those rows on its evidence. Do not rewrite it.

**C8. CONTRADICTION with C3: seal time includes `AWAITING_OWNER`. The code wins.** The ref is written on every
`attempt.transitioned` into `CANDIDATE_REF_STATES` (`AWAITING_OWNER`, `BLOCKED`, `CANCELLED`, `PUBLISHED`), from
`persistAttempt` in `core/src/cli/commands/attempt.ts`. `AWAITING_OWNER` is not in `SEALED_STATES`, but task 14's
readout prints the ref in that state, and it is where an unattended shift waits. C3's other half still holds: a
ticket-blocked shift stays at `RUNNING` and gets no ref.

**C9. SCOPE already done: `core/test/journeys/shift-blocked.test.ts` asserts the ref.** It checks that no ref
exists at the ticket block, that exactly one ref exists at `AWAITING_OWNER`, at the tip commit in the canonical
repository, and that `shiftTicketCandidates` maps T01 to T06 onto their six commits. Do not duplicate these.

**C10. FINDING: the no-exemption test reads the two fence files.** It fails if `no-destructive-paths.test.ts` or
`no-land-route.test.ts` contains `candidate-ref`, `refs/awsf`, `exempt` or `allowed`/`allowlist`. An edit to
either fence that uses those words turns it red by design.
