### 2026-09-25 — from T04

**C1. SCOPE already green from T04.** `shift-compile.test.ts` (11 tests) covers phase shape,
ordering, `minimumCalls === N + 1`, earned descriptions, the `reducePhaseContext` chain and refusals.
The cross-process reproducibility check is done too: `core/test/unit/_shift-compile-child.ts` compiles
in a fresh `node` process and the test compares its `serializeShiftRecipe` output byte for byte. T07
still owns the induced-violation proofs for T05's and T06's rules.

**C2. CONTRADICTION: the plan's task 4 wording on `{previous_envelope}` is wrong, and the code wins.**
The plan says ticket n's builder receives ticket n-1's build envelope as `{previous_envelope}`.
`reducePhaseContext` returns `previous` = the last accepted envelope, which is ticket n's own
`t<NN>-brief`. Ticket n-1's build envelope is only `schemas.get("awsf.build-output/v1")` (last wins,
asserted). The test asserts the real behaviour, including that "built t02" is absent from t03's
rendered builder prompt. This is the right behaviour: the builder needs its own ticket's prompt, and
n-1's work is already in the tree. Do not reorder phases to make the plan's sentence true.

**C3. FINDING for the first ticket that runs a shift through `production-run.ts` (M4/M5).** Two
runner behaviours defeat the brief as it stands:
(a) the `engineer` branch ignores `phase.execute` and emits `requestOutput(status)`, so a brief would
carry the attempt's request instead of its ticket's prompt. A shift brief must emit its phase's
`intent` (`ShiftBriefPhase.intent`, already built at compile time).
(b) review `intent` is `schemas.get("awsf.plan-output/v1")`, and last wins, so `shift-review-context`
would see only the last ticket's brief. It needs every `t<NN>-brief`.
Neither is in M2's scope. Carry both forward to T11 or T14's Handoff when M2 closes.

**C4. C2 and C3 are now in the plan.** The 2026-09-25 amendment rewords task 4's
`{previous_envelope}` row to the measured behaviour and moves C3's two runner gaps into task 11 as
checklist rows, with a matching entry in T11's Handoff. Nothing is left for you to carry forward.

**C3. FINDING to carry forward when M2 closes: no task binds a selection to an attempt.** `awsf start`

has no field for a sealed manifest. T08 writes the manifest and M4's runner compiles the recipe, but
neither ticket names the binding. Put it in the M2 close Amendment and in T11's Handoff, so the first
ticket that runs a shift adds the field and replaces the refusal with `compiledWorkflow(id).compile`.

**C4. Test isolation.** `shift-catalog.test.ts` builds its enabled and disabled configs from the real
one either way, and `workflows.test.ts`'s headroom loop now skips compiled ids. Both stay green before

M2 test independent of whether the real config enables `shift`.

### 2026-09-25 — from T06

**C1. SCOPE already green from T06, including the induced proof.** `core/test/unit/shift-inversion.test.ts`
(6 tests) exists. Three violations were induced in `compiler.ts`, watched red, and reverted (`cmp` against
the saved file): the provider check disabled (tests 3 and 4 red), the zero-producer throw removed (test 5
red), and the old single-phase rule restored (tests 1 to 4 red). With T05's C1, both amended M2 rules now
have their induced proof. Cite them in the close Amendment. You do not need to redo them.

**C2. CONTRADICTION: your Testing Strategy row says a *compiled* workflow with builders on two providers
is refused. The code wins.** The compiler cannot see providers. `compileWorkflowStructure` refuses only
zero build producers. The two-provider refusal is `reviewWorkerProvider(compiled, providerFor)` in
`compiler.ts`, which the runner calls in its inversion preflight. It throws `ReviewBuildProvidersDisagree`.
A test that only compiles a shift never sees that refusal, so point the row at `shift-inversion.test.ts`
tests 3 and 4.

**C3. T04's pinned test is replaced, and the single id is null for N ≥ 2.** In `shift-compile.test.ts`,
"more than one ticket carries its review through compileWorkflowStructure" now asserts `minimumCalls === 4`
and the three `reviewBuildPhaseIds`, per T04's C1. `reviewBuildPhaseId` is `null` for two or more builders.
That was decided on purpose, and the plan's 2026-09-25 task 6 Amendment says why.

**C4. FINDING to carry forward when M2 closes (to T14's Handoff, the readout).** The worker route a run
records is its last build. `review-record.ts` keeps the last `purpose: "build"` agent record as the worker,
and the projector overwrites the session's worker columns on each build record. For a shift the provider
is the same on every build, by rule, but the model need not be. A readout that shows "the worker model"
for a shift shows the last ticket's model.
