In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it says the same things precisely, for the people — and machines — building it.

What this is about

There is a machine that takes a job you describe in ordinary words, hands it to an assistant working inside a sealed copy of your project, runs your own checks on whatever comes back, and then holds the result in a waiting room until a person personally signs for it. It works. One person knows how to drive it, and that person built it.

This is the plan for the guide that lets somebody else drive it — and, at the same time, the plan for putting the machine through its own final exam.

The guide is one file with two halves inside it. The front half is a walked route: six steps, plain words, no jargon, from a computer with nothing installed to the moment a human signature is required. You never type anything to the machine yourself — you talk to an assistant that drives it for you, and the guide teaches you what to ask for and how to read what comes back. The back half lifts the curtain: what that assistant actually did on your behalf, which stages the work passed through, which checkpoint decided what, and what each thing costs.

Why now, and the thing we found while looking

The guide comes last because the thing it describes had to stop changing first. Four separate pieces of work each added or altered something a reader would use. All four are finished, so the ground has stopped moving.

Then, while writing this plan, something turned up that changed it. Three facts written down in this project are simply wrong — not opinions, countable things. The front page says the machine tracks ten stages; it tracks eleven. It says twenty-five connections between them in one place and twenty-four in another; there are twenty-seven. A note at the top of a safety script says it blocks six actions; the script itself blocks seven.

None of those were sloppy. Each was true when written, and then something was added and the sentence stayed behind. Nobody noticed, because the existing automatic check only asks "does this instruction exist?" — it has no opinion about a count, or about something missing entirely.

And one of the wrong numbers has already spread. The "six actions" from that stale note was copied, as if true, into a second document. Nobody transcribed a mistake; something read a stale line and believed it. That is not a hypothetical argument about documents going out of date. It is the thing happening, in this project, right now, twice over.

What we are building

Think of the guide as a route card for a building. Not a floor plan of every room — one walked route, with a note at each place a person actually gets stuck, written by watching somebody get stuck there. The back half is then a set of labelled panels along that route, each showing the machinery behind that particular stretch of wall.

The order is what makes it earn its keep:

  1. Drive the machine first, with no guide at all, and write down every single time you have to go and look something up somewhere else in order to carry on. Each of those is a place the guide will have to answer.
  2. At the same time, build the checks — and make them stronger than the ones that missed those three wrong facts. The new rule is that the guide's list of stages must be exactly the same as the machine's real list. Not a subset. Exactly. So if the guide invents something, the check fails — and if the guide is missing something, the check fails too. Add a new stage to the machine next year and the whole thing goes red until somebody updates the guide. That is how you promise "this covers everything" and can actually prove it.
  3. Then write it. Both halves, into one file.
  4. Then take the exam. Drive two real, useful jobs all the way through the machine using nothing but the guide.

An earlier draft of this plan had the guide existing twice — a plain text version and a designed one — with a program to build the second from the first and a check to keep them matching. That whole apparatus is gone. There is one designed file, written by hand, and nothing generated. One file cannot disagree with itself, and a program that does not exist cannot go wrong. The plan lost a chunk of work and gained a guarantee. The file loads nothing from the internet, so it opens on any computer, offline — which also happens to solve the awkward question of how somebody reads the guide before they have installed anything.

How we know it worked

It worked if two real jobs go all the way through the machine, driven by a person following the guide and nothing else, each reaching the signature with everything that signature needs.

There is a catch, and it is written into the plan rather than hidden in it. The person driving is the person who built the machine. He cannot be surprised by his own work, so he cannot prove the guide is understandable to a newcomer. What he can prove is narrower and still worth having: every time he has to look something up outside the guide, that is a hole, and holes do not care who found them.

Doing it twice buys something one run could not. The number of times he has to look elsewhere should drop between the first job and the second. If it does not drop, the guide is not teaching anything, and that is a finding about the guide rather than about him. If it drops to nothing, we check whether he was reading it or remembering it, and write down which. The guide is deliberately not edited between the two runs — otherwise the difference would be measuring the edit.

Underneath all that, several things are checked by machine instead of by anyone's judgement: every instruction the guide shows really exists; the six things it claims to cover completely really are complete, checked in both directions; the guide's contents list matches its actual sections; it really does open with the internet switched off; and it really does say, before showing a single instruction, that you are not meant to type any of them.

Three things are deliberately left out, and each is written down rather than assumed. The guide changes nothing about the machine — anything a reader needed that does not exist yet is handed to whoever owns that part, named, and left undone here. The guide does not plan the exam's two jobs — the machine plans them, because that is the entire point of the exam. And nothing goes in the back half that cannot be checked automatically. If some part of the machine has no way to be checked, that is a finding about the machine, and the honest answer is to say so rather than write the section anyway and hope.

Purpose

Produce the document that lets a person drive this factory through marimba — describing what they want rather than typing commands — and that also shows them what marimba did on the other side of the curtain. One file, two registers: a plain walkthrough a person follows, and a reference that shows the mechanism, every fact class of it bound to its source by a test.

W12 is last in v2 because every command it describes had to stop moving first. W03, W07, W08 and W11 all read [x], so the surface is settled. It is also the factory's graduation. The owner drives two real tasks through the factory by following this document, and what those runs need is what the document has to contain.

Problem

Three problems, and the third is the one that decided how the document is checked.

One — "every command and flow" has no finish line

Taken literally it produces a second copy of the routed command tree, a tree that already has an owner. Two documents claiming one truth drift apart at the first change, and this repository has already paid to learn that: invariant 12 exists solely because a plan and its tickets could disagree. Acceptance therefore stays a walkthrough. The owner's review asked for the behind-the-curtain half anyway and asked for it to be complete, which means the drift objection has to be answered mechanically rather than by refusing the content. That answer is the third problem below.

Two — the test that catches an invented command is partly blind

doc-reconciliation.test.ts extracts commands with /(?:^|\s)awsf (db rebuild|[a-z]+)\b/. It sees awsf land TASK and just awsf land TASK. It does not see npm run awsf -- land TASK, because the token after awsf is --. Measured 2026-08-27:

"npm run awsf -- land TASK"    CLI: []        JUST: []
"just awsf land TASK"          CLI: ['land']  JUST: ['awsf']
"awsf land TASK"               CLI: ['land']  JUST: []

README.md's install, usage and verification blocks are written entirely in the invisible form, so every awsf command in the README is checked by nothing today, and the test passes because it finds nothing to check.

Solution

Keep the walkthrough as acceptance. Answer the drift objection with set equality against the source, per class of fact, in both directions. And author one file, so there is nothing for a second copy to drift from.

The document has two halves, and only one of them is written in plain language

The walkthrough half is six legs a person follows: install, prime, ask marimba for one job, watch it, read a refusal, stop at the act only a person may perform. No acronyms, no state names, no ids. The reference half is behind the curtain: what marimba invoked, which states the work passed through, which gate decided what, what each act costs. It is written for a reader who wants to look, and it is the half the fences bind.

Six fact classes, set-equal to their sources, both directions

This is what turns "document everything the factory can do" from an unbounded promise into a test. For each class, the document's set and the source's set must be equal — so an invented entry fails, and a missing entry fails too. A lifecycle state added next year makes the suite red until the document mentions it.

Why this is stronger than what was originally planned, and why it is affordable
The first draft of this plan proposed one fence: every command the document names must exist. That would have caught none of the three stale facts measured above. Set equality catches all three, catches the next one automatically, and costs six extractors and twelve assertions — because every source is already an export or a loaded config. Nothing here parses prose or guesses. Each class is marked in the document with a machine-readable attribute, so extraction from the document is exact rather than a prose scan.

One authored file, and nothing generated

The document is docs/cheatsheet.html: hand-authored, self-contained, themed in both modes, with a sticky index and hand-drawn figures. There is no markdown twin and no renderer. An earlier draft proposed authoring markdown and generating the HTML from it, with a rebuild-and-compare test to keep them honest; the owner took the stronger option instead — one file cannot drift from itself, and a generator that does not exist cannot emit a non-deterministic byte. The plan lost a milestone's worth of work and gained a guarantee.

Two things the vanished generator was doing still need doing, and both become fences instead of code. The index was going to be generated from the headings; it is now hand-written and held to the sections by set equality, the same shape as the six fact classes. And the file was going to be self-contained by construction; it is now self-contained by assertion — no external reference of any kind, so it opens on a machine with nothing installed and no network. That last property is also the answer to how the reader gets the document in the first place.

The reader does not type the commands, and the document says so before it shows one

Because the reader drives a session rather than a terminal, the commands in this document are mostly illustrative of what marimba runs. An earlier draft banned command-shaped text from prose entirely, on the grounds that a reader who cannot tell an example from a sentence will type both. The owner's answer removes the premise: the document states up front that these are not for typing, so prose keeps the exemption the driving tree already grants it, and the warning carries the weight the ban was carrying.

A warning that a later edit could quietly delete would be worse than the ban it replaced, so the warning is itself asserted: it must exist, and it must appear before the document's first command block.

What This Builds, and What It Refuses to Build

Why acceptance is still a walkthrough, even though the document is now larger

The review expanded the content and kept the acceptance test, and those are separable
  1. Coverage as acceptance is still refused. "Complete" is not a finish line a session can check by reading. The finish line stays: real tasks go through the factory, driven by a person following this document.
  2. Coverage as content is now funded, because it became checkable. The six set-equality fences make completeness a mechanical property of six named classes rather than an unbounded claim about everything. The rejected thing was an unbounded promise; what is being built is a bounded, tested one.
  3. Duplication is prevented by joining, not by omitting. The reference half restates facts that live elsewhere, and every one is tied to its source by a test that fails in both directions. A restatement that cannot drift is a rendering, not a second owner.

What an author-driven run can still measure, and it is more than it first appears
The owner cannot measure "did I have to ask?". He can measure something observable and nearly as sharp: every time he consults anything other than this document in order to proceed — the source, the plan, a previous transcript, or his own memory of how it works. Each consultation is a place the document was insufficient, it is recorded when it happens, and it does not depend on being surprised. That converts an unrunnable test into a runnable one, and it is what M1 and M5 both measure.

Two runs give it a second dimension. Consultations should fall between the first graduation task and the second. If they do not, the document is not being learned from — and if they fall to zero because the driver has memorised it rather than read it, that is visible too and gets recorded rather than counted as success.

The residual limit is real and stated: an author-driven run cannot prove the document is comprehensible to somebody new. Only a second reader can, and Q7 defers that rather than faking it.

The Mechanical Half

The spine's requirement: "A cheatsheet that names a command the factory does not have fails a test, not a review." The owner's review raised the bar: a cheatsheet that omits something the factory does have should also fail. Five legs make both true, over one file.

Leg one — see all three invocation forms

Normalizing npm run awsf -- X and just awsf X to awsf X ahead of the existing matcher closes the blind spot in one place, for every document the fence already covers. Its first effect is on the README, not on the cheatsheet.

The suite may go red on a file this workstream did not write, and that is the point
Record every offender before changing anything, and never narrow the matcher to restore green. A narrowed matcher looks exactly like a test fix and leaves a weaker guarantee than the one it replaced.

Leg two — six fact classes, set-equal in both directions

Each class extracts a set from the source and a set from the document, and asserts equality. Both failure directions must be proven by induction: remove an entry from the document and watch it go red; add an invented one and watch it go red. A fence proven in only one direction is half a fence, and the missing half is the one that catches staleness.

Leg three — commands are checked where they are shown, and prose keeps its exemption

Commands appear in <pre> blocks and every one of them must resolve. Inline <code> in prose is exempt, exactly as the driving tree exempts markdown prose and for the reason its header already gives: a regex over explanatory prose produces false positives that teach authors to stop marking up commands at all. The residual gap is named and accepted, and what pays for it is the warning — the document states, before it shows a single command, that the reader does not type these. That statement is asserted to exist and to precede the first command block, so it cannot be edited away by someone tidying an introduction.

Leg four — the index is set-equal to the sections

With no renderer, the sticky index is hand-written, which makes it the one part of the document that can silently disagree with the rest of it. It is held by the same mechanism as the fact classes: every index entry resolves to a section, and every section has an index entry. A new section without a nav entry fails; a nav entry pointing nowhere fails.

Leg five — nothing external, so it opens anywhere

No http or protocol-relative URL, no script source, no external stylesheet, no remote font, no remote image. This is what makes the file a real handover: one attachment, no installation, no network. It is also what the owner's own design rules already require of this family of documents.
