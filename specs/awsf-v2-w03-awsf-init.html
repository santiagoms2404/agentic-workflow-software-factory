Plan: AWSF v2 W03 — awsf init

Greenfield's chicken-and-egg — you cannot check a design against a repository that does not exist yet — is removed by never asking a provider to solve it. This is a deep plan, one workstream of the v2 spine (Milestone M3). It carries the whole of awsf init: a minimal config derived from the schema rather than hand-guessed, a host-only command that creates a directory, runs git init through the one broker allowed to spawn a process, writes that config, and produces a baseline commit under the owner's own identity — reusing the commit helper this repository already has rather than writing a second one. Authoring it wrote no implementation code, changed no invariant, and flipped no marker. It did run one real fixture — a throwaway git init plus a real loadConfig round trip plus a real commitAsHost call, in a temporary directory, deleted afterward — and its output is quoted verbatim below, which is what turns "no provider is needed" from a design claim into an observation.

In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it says the same things precisely, for the people — and machines — building it.

Starting a brand-new project needs somewhere to stand, and there isn't one yet

Every other command this workshop offers assumes a project already exists: a folder, a rulebook file inside it, a history of changes. That is a reasonable thing to assume for all of them except one — the very first command, the one that has to create that folder in the first place. Ask a helper to do it and you hit an odd little trap: the helper is normally supervised by reading the rulebook file inside the project it is working on, but there is no rulebook file yet, because there is no project yet. Something has to make the first move before any supervision is possible.

Why now

The next real project this factory needs to build lives in folders that don't exist as AWSF projects today. Before any of the other new workshop capabilities can be tried against something real, that first folder has to come into being, correctly, every time, without anyone needing to remember a checklist.

What we are building

A single, entirely mechanical starting move — no helper involved at all, just the workshop's own hands. Given an empty spot to work in, it lays down the folder, starts a change-history for it, writes the smallest possible rulebook that the rest of the workshop already knows how to read, and files that rulebook away as the very first entry in that project's history — signed with the owner's own name, the same way every other entry in every project this workshop touches is signed. Nothing is asked, nothing is guessed, and no outside advice is consulted at any point, because none of that is needed to lay a floor.

How we know it worked

Point the workshop at an empty spot, give it a name for the project, and it hands back a folder with a change-history already begun and one entry in it, signed by the owner, holding a rulebook the rest of the workshop can read without complaint. Do this a second time in a spot that already has something in it, and it refuses rather than mixing unrelated things together into that first entry. And the whole time, from the first step to the last, nothing outside this machine was ever asked a question — which is checkable, because the plan proves it by listing everything the starting move is allowed to reach and showing that no outside advisor is on that list. What this deliberately does not do: decide what the project is about, sketch a design for it, or write any plan for what comes next. Those are separate, later moves, made once there is a floor to make them on.

Purpose

Give AWSF one deterministic, host-owned command — awsf init — that creates a directory, initialises it as a Git repository, writes the smallest awsf.config.yaml that satisfies the existing awsf/v1 schema, and produces a baseline commit under the owner's own identity. No provider is contacted at any point, before or after the baseline exists. That is the entire scope. Making the command host-only is not a workaround for the absence of a pre-repository execution mode — it is the reason no such mode is ever needed: nothing about creating an empty, valid project requires a model, so the command simply never calls one.

Scope discipline. This workstream stops the instant a valid baseline commit exists. It does not produce a plan, a design, or a ticket — those are W05's governed phase outputs, running later, against the repository this command created, and W05 is the workstream that consumes them. A deep plan that reaches past the baseline commit has widened W03 into W05's job.

Problem

The source record that fed this workstream (specs/awsf-v2-candidates-fuse-version.md §2.3) held two shapes for how a brand-new project comes into being, and they contradict each other. One put the plan for the new project inside the baseline commit — the very first commit would already contain a design document. The other created the baseline first, empty of any plan, and produced the plan afterward as the output of a later, governed phase. Only the second shape has somewhere for that later phase to run: a governed phase needs a repository, a config, and a place to write its output, and none of those exist before the baseline commit does. The first shape is circular — it asks for a plan to be produced by a phase running inside a repository whose own first commit is that plan.

A second problem, found by reading the code this workstream must reuse rather than reinvent

core/src/git/commit.ts already exports commitAsHost() and HOST_AUTHOR = "Santiago Marin <santiagomarinsuarez@me.com>" — the exact mechanism a baseline commit needs. It stages everything with git add --all, commits with an explicit user.name/user.email override and --author, and asserts the tree is clean before and after. But every existing call site — run.ts and rework.ts — calls it against a worktree that already has a HEAD. Nothing in the tree had exercised it against a repository with zero prior commits before this plan was authored. That gap is closed in What Was Measured below, with real output rather than an assumption.

A third problem, found the same way: git add --all is a hazard the moment the target directory is not guaranteed empty

commitAsHost's first git call is add --all. If awsf init is ever allowed to run against a directory that already holds unrelated files, every one of those files is swept into the "baseline" commit alongside the config this command wrote — silently, because add --all does not distinguish "written by this command" from "was already there". This is a correctness finding, not a style preference, and it is why the command's own precondition — refuse a non-empty target — is not a nicety but the thing standing between "baseline commit" and "baseline commit plus whatever happened to be lying around". It is carried forward as Q2 because the exact boundary of "non-empty" (an empty directory that merely exists, vs. one holding dotfiles, vs. one holding an unrelated .git) is a real design choice, not a foregone one.

Solution

Three pieces, each reusing something the tree already has rather than adding a parallel mechanism. A schema-derived config builder that is validated by round-tripping it through the loader that will read it back later — never a hand-written YAML string trusted on faith. A host-only command that sequences mkdir, git init (through the transport broker, the one file in this repository allowed to import node:child_process), the config write, and commitAsHost. And two mechanically-enforced fences: one proving the command's own import graph never reaches a provider, and one proving the command stops at the baseline commit rather than reaching into W05's territory.

Why the config is built as a typed object and round-tripped, not hand-written once

AwsfConfigSchema (core/src/config/schema.ts) is not small: twelve top-level keys, several of them further-nested objects, several checked structurally by TypeBox and several more checked by hand in load.ts — absolute-path rejection, credential-shape rejection, seed-path containment, known-reference membership (adapter kind, workflow id, gate id, protected-operation id), call-ceiling bounds, no_fallback === true, persist_thinking_text === false. A hand-typed YAML string that merely "looks right" is exactly the kind of artifact that silently drifts the day the schema changes. buildMinimalConfig(slug) instead constructs a plain object typed as AwsfConfig, so the compiler itself rejects a missing or misnamed field, and its own test round-trips it — stringify → loadConfig → deepEqual — so the thing this command writes is proven loadable by the exact function that will load it back, not by inspection.

Why git init goes through systemGitRunner, not a new call site

AGENTS.md invariant 3 is absolute: node:child_process is imported nowhere except core/src/execution/transport-broker.ts, enforced by the child-process fence meta-test. core/src/git/changes.ts's systemGitRunner(repository) already wraps runSystemCommand for exactly this purpose, and commitAsHost already uses it. initCommand reuses the same runner for the one additional call the existing helper never had reason to make — git init — rather than opening a second door into the broker.

What "minimal" settles on, and what stays a Questionable

The fixture below proves a config holding one claude-code adapter, an empty agents array, workflows.enabled: [intake], and empty gates/protected_operations loads cleanly and produces a non-empty commit on its own — no README, no .gitignore, nothing beyond the config file was needed to satisfy commitAsHost's refusal to create an empty commit. That is the whole of what gets written. Which adapter, which workflow, and how the target path and project slug are supplied are still open — see Questionables.

Questionables

Q1 — Does awsf init take an explicit target-path argument, or does it only ever operate on the current working directory?

DECIDED 2026-08-21 A path argument, defaulting to cwd when omitted, created if absent — mirroring git init [<directory>]'s own long-standing shape. The spine's own W03 scope language is literally "create the directory", which only makes sense if the directory may not exist yet; every other AWSF command instead assumes cwd already is the project, because a project already exists by the time any of them run. init is the one command for which that assumption cannot hold on entry.

Q2 — What counts as "the target is not usable" — how strict is the non-empty refusal?

DECIDED 2026-08-21 Refuse whenever the directory exists and is non-empty, full stop. Problem names the concrete hazard: commitAsHost's git add --all would otherwise sweep pre-existing, unrelated files into the "baseline" commit with no signal that it happened. The narrower option — refuse only when .git already exists — tolerates that hazard for the sake of letting init run against a directory holding stray files, which is not a real use case this workstream needs to serve.

Q3 — Invariant 11 and the no-agent-coauthor fence: precisely what do they guarantee for a repository this command creates elsewhere?

DECIDED 2026-08-21 — APPROVED The framing below was confirmed to read correctly, with no revision requested. core/test/unit/meta/no-agent-coauthor.test.ts scans this repository's own git log --all, scoped by repoRoot(). It has no jurisdiction over a commit awsf init makes inside a brand-new target-project repository somewhere else on the owner's machine — that repository is never this repository's history. So the guarantee this workstream must uphold is by construction, not by an inherited fence: reusing commitAsHost/HOST_AUTHOR rather than any ad hoc identity-setting is what keeps every baseline commit, in every project awsf init ever touches, carrying the owner's identity — and Milestone M2's own integration test proves it directly, on the actual commit produced, rather than relying on a fence that cannot see it.

Q4 — Does the minimal config declare workflows.enabled: [intake], or an empty list that presumes nothing about what the new project will do next?

DECIDED 2026-08-21 [intake] only, matching project.default_workflow. It is the narrowest workflow already known to KNOWN_WORKFLOW_IDS that a freshly created, otherwise-empty project can meaningfully run without any further scaffolding. This is very likely to be revisited once W04's registry and W05's design-to-plan recipes land — noted here rather than silently baked in as permanent.

Q5 — Is the baseline commit's message fixed text, or can the owner supply one?

DECIDED 2026-08-21 Fixed: "chore: awsf init baseline". This is a deterministic, host-owned command with no interactive step by design (Purpose) — accepting free text here would be the first crack in that determinism for no benefit the workstream's scope requires.

Q6 — If awsf init is run a second time against a directory it already initialised, does it refuse or silently succeed as a no-op?

DECIDED 2026-08-21 Refuse, via the same non-empty-directory precondition Q2 settles — a .git directory already being present makes the target non-empty. A silent no-op risks masking the caller's actual intent (did they mean to re-run init, or did they mean something else entirely and land here by mistake); an explicit, named refusal costs nothing and is easy to soften later if real usage shows the friction is not worth it.
