In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it says the same things precisely, for the people — and machines — building it.

Getting the finished work off the workbench and into the shared cabinet

The workshop currently finishes a piece of work and puts it on its own shelf, in its own building. That shelf is the end of the road: there is no way for the workshop to move anything to the shared cabinet elsewhere, deliberately, because moving things outside the building is the one thing it has never been allowed to do. The owner does it by hand instead. That works, and it leaves no record — nobody can later ask the workshop which piece went to the cabinet, when, or whether the bench was tidy at the time.

Why now

This is the last step the current round of work is aiming at. "Finished" for this round means the work exists in the shared cabinet and the workshop's own logbook says how it got there. Every earlier step built toward a piece of work that is approved, sealed, and sitting on the shelf. This step is the one that carries it across the yard, and it is the only step in the round that needs the workshop's rulebook changed before it can be built at all.

What we are building, and the one rule that must change

A single instruction the owner types, which does exactly one thing: it takes a piece of work that is already finished and already approved, and it copies that exact piece — not the shelf it sits on, not whatever happens to be on the bench — into one shared cabinet, on one shelf, both named in advance in a list the owner wrote. Before it moves anything it checks a list of conditions in a fixed order and stops at the first one that fails, saying which one. Doing the same thing twice changes nothing the second time.

The rule that must change is the workshop's own standing order: nothing here may ever carry anything outside the building. That order is checked by a machine that reads the workshop's blueprints looking for the phrase. The replacement says: nothing may carry anything outside the building unless the piece is already finished and approved — a condition, where before there was a flat refusal. Only the owner can change the standing order, and this plan asks for it in writing rather than changing it. There is an honest alternative that needs no change at all: leave things exactly as they are and let the owner keep carrying pieces across the yard by hand. What that costs is the logbook.

One thing was measured while writing this, and it changes how the trade should be read. The machine that checks the standing order looks for the phrase written the way a person types it at a keyboard. The workshop does not write instructions that way — it writes each word of an instruction as a separate item on a list, for a different safety reason entirely. So the phrase never appears, and the check would not have noticed the very thing it exists to forbid. The old rule was partly decorative. Three further spellings of "throw something away" slip past it in the same manner, and the replacement catches all three.

How anyone would know it worked

Everything is proved against a shared cabinet built on this same machine, in a temporary folder, with nothing reaching outside it at any point. A finished, approved piece arrives in that cabinet. The piece is then marked as delivered, and because delivered is the end of its life, asking for it to be delivered again is refused rather than quietly repeated. Every stage a piece can be in before it is finished is refused by the fixed list of conditions rather than by luck. The workshop uses whatever pass the owner already keeps for the cabinet and never looks at it: the pass appears in no instruction the workshop assembles, in no logbook entry, and in nothing the workshop writes down. The logbook entry afterwards names the piece and the shelf and nothing else: no address, no error text, no borrowed phrasing.

Two things had to change in the workshop's own paperwork to make "delivered" a real stage rather than a note in the margin, and both are the owner's to sign. One adds the stage to the list of stages a piece can be in. The other widens a form that only accepts the ten stage names it was printed with. Neither can be done by anyone but the owner, and this plan asks for both in writing rather than doing them.

And one thing is deliberately not being built, and is named here so it is not smuggled in: putting the work into service somewhere. That is a separate job, it is written down as a separate job, and this plan touches none of it.

Purpose

Give the owner one command that moves an already-landed, already-approved revision to one allowlisted remote branch, refuses everything else by a stated rule rather than by an unreached code path, and leaves a record in the journal that names what the remote accepted. That record is the whole reason this workstream exists — a hand-typed push does the same mutation and produces no evidence at all.

The workstream is small and its risk is concentrated in one place: it is the first thing in this repository permitted to change something outside the machine, and the permission arrives by weakening a rule that currently reads as an absolute. Most of this plan is spent making the replacement condition mechanically checkable in more places than the absolute ever was.

Problem

Four problems, and the second one is not the one the spine expected to find.

1 — Landing is the end of the line, and the line stops inside this machine. completeLanding in core/src/git/land.ts performs a local merge --ff-only and then proves canonical HEAD equals the approved candidate. Nothing after that exists. The journal's last word on a task is LANDED, and whether that revision ever reached a remote is a fact this repository neither records nor can be asked.

2 — The scan invariant 8 rests on does not catch the thing it forbids. Invariant 8 is enforced by a nine-pattern text scan over core/src, whose push clause is /git\s+push/. This repository never writes those two words adjacently: invariant 4 bans shell: true, so every Git invocation is runSystemCommand("git", [...argv]) and the push token is the string "push" inside an array. Measured, not reasoned — the nine patterns were run against six specimens:

The only push the scan catches is one written in prose. This reframes the amendment: part of what is being traded away was already unenforced, and two destructive spellings — the + prefix and the empty-source delete — go unenforced today with no amendment at all.

3 — Git spells "delete this branch" as a well-formed exact-revision push. Measured against a local bare remote: git push origin 0000000000000000000000000000000000000000:refs/heads/main printed - :refs/heads/main [deleted] and exited 0. An all-zeros object id is Git's deletion sentinel, so a refspec whose source is forty hex characters can still be a deletion. "Non-delete" therefore cannot be checked as "the source is non-empty."

4 — The source candidate specifies the state check and nothing else. §2.4 of the candidate record settles post-LANDED, human-initiated, exact-revision publication and names a state-aware meta-test. The adjudication upheld that this is necessary and not sufficient: an allowlisted remote and branch, canonical HEAD at the landed candidate, a clean checkout, a non-force non-delete refspec, credential non-persistence, idempotent retry, and a scrubbed record are all absent from the candidate. Seven of the fourteen refusal rows below come from that list; none of them exists in the source.

Solution

One pure ordered truth table, one branded value that only the table can produce, one argv site that accepts nothing else, and a record with a closed field vocabulary.

The table is pure and total. authorizePublish(status, repository, remote, refspec) reads four records of already-observed values. It performs no I/O, reads no clock, and resolves nothing. Every input either authorizes or names exactly one of fourteen refusal codes, and the codes are ordered in the manner core/src/state/guards.ts and core/test/unit/rejection-order.test.ts already establish for lifecycle transitions: for every adjacent pair there is an input violating both, and the earlier one must fire, so a rejection always names the real defect.

The authorized value is the only key to the argv site. authorizePublish returns a branded AuthorizedPublishPlan carrying a unique symbol no other module can name. publishArgv in core/src/publish/argv.ts takes that type and nothing else, and is the sole place in core/src where the push token exists. The fence asserts three things: locality (one file), derivation (the argv builder's only parameter type originates in authorize.ts, and no other module constructs or casts to it), and condition (the table refuses every member of TASK_STATES except LANDED, enumerated from the imported constant rather than a copied list).

The allowlist keys on remote name, and that is forced by code rather than chosen. core/src/registry/catalog.ts runs assertNoAbsolutePaths over every string leaf of the catalog, so a bare-remote path like /tmp/x.git or C:\x.git is rejected outright, and every test in this workstream needs exactly such a path. A remote name is machine-independent; the URL stays in the repository's own Git config where it already lives. The consequence is a security property rather than a compromise: no URL ever enters the argv, so a credential embedded in a remote URL cannot reach the process arguments, the journal, or an error message.

The owner's credential helper is inherited, and no credential value passes through AWSF. Q3, decided 2026-08-25. The push carries no -c credential.helper=, so an https remote works exactly as it does when the owner types the command themselves. What AWSF guarantees is narrower and still checkable: no URL enters the argv, nothing the helper returns is read, held, logged or journalled, and AWSF itself writes no credential configuration and no credential file. GIT_TERMINAL_PROMPT=0 stays regardless — the subprocess is spawned through spawnSync with captured stdio and has no terminal, so a prompt would hang until the timeout rather than reach anybody.

Publication is a lifecycle transition to a new terminal state. Q2, decided 2026-08-25. PUBLISHED joins TASK_STATES as an eleventh state and L27 — LANDED → PUBLISHED as a twenty-seventh legal edge. That requires splitting one predicate that currently does two jobs: TERMINAL_STATES keeps its meaning — this attempt's work is over, which is what retry, raise, watch, sealing and endedAt all read — and gains PUBLISHED, while a new SEALED_STATES = {BLOCKED, CANCELLED, PUBLISHED} is what transition()'s step 2 and the journal's write protocol consult. LANDED becomes terminal-for-work and not sealed, and exactly one edge and one journal record may follow it.

The seal, and a correction to what this plan told the owner before they chose

A landed attempt's journal is sealed, and nothing can be appended to it. persistAttempt in core/src/cli/commands/attempt.ts validates with if (current !== null && isTerminalStatus(current)) throw new SealedAttempt(...), and its sealWhenTerminal hook marks the lock sealed so every later withLock throws too. LANDED is in TERMINAL_STATES, so a LANDED attempt accepts no further record of any kind.

This plan's first draft was wrong about the consequence, and the error favoured the option it recommended. Q2's original answer priced the no-edge design at one owner-authored commit and the PUBLISHED design at two. The seal was not read. In fact the no-edge design was also blocked by it — journalling a publish evidence record on a LANDED attempt throws SealedAttempt — so the seal had to be opened either way, and the real comparison was one owner commit plus a seal change against three owner commits plus the same seal change. The owner's decision stands; the arithmetic they were shown did not.

What the split buys, and it is the reason it is a split rather than a deletion. Removing LANDED from TERMINAL_STATES would have been the obvious move and it breaks six things: retry refuses a non-terminal prior attempt, raise would start accepting a landed one, watch would never stop, endedAt would stay null forever, and both seal sites would stop firing. Keeping TERMINAL_STATES intact and adding SEALED_STATES beside it leaves all six reading the predicate they were written against.

The hole the split opens, and what closes it. An unsealed LANDED attempt would accept any further write, not only the publish transition. So the write protocol's validate gains one condition rather than losing one: refuse when the current state is sealed, and refuse any event on a LANDED attempt whose next state is not PUBLISHED. That is INV-7, and it is asserted directly rather than inferred from the edge table.

What This Workstream Is Not

Publication is source publication

This plan moves one already-landed revision to one Git remote branch. Nothing else. It does not put anything into service, does not read or write any environment's configuration, runs no migration, cuts no release, and has no notion of a target that is not a Git remote. The word "deploy" appears in this document only here and in the two rows below.

W13 is the deploy workstream and it is declared, not built. The spine names the accidental widening of W08 into W13 as the single most likely in the whole set, because the two words sit one apart and the source record already had to be corrected for conflating them. Environment configuration, release migrations, rollback orchestration and operational acceptance are explicitly out of scope for v2 and belong to W13's own amendment and its own deep plan.

The mechanical form of this rule. Nothing in core/src/publish/** may take an environment name, a target descriptor, a release identifier, or a host endpoint as an input; the catalog's publish block carries a remote name, a branch name, and an optional hostname, and its schema is closed with additionalProperties: false. A field that would be needed for deployment cannot be added without failing the schema test that pins the block's exact key set.

The Invariant 8 Amendment — Drafted, Not Landed

No agent can write AGENTS.md. core/src/policy/path-policy.ts treats protected-path as a rejection independent of the write globs, and awsf.config.yaml lists AGENTS.md under policy.protected_paths. Ordering gate G2 makes the amendment an owner-authored commit that lands before this workstream starts building. This section drafts it in the five-part shape the intent's decision 4 requires — the invariant, what it blocks today with evidence, the replacement guarantee in still-mechanically-checkable form, its cost, and the alternative that avoids the amendment entirely — and does not land it. Do not invent a mechanism that routes around the protected path; that is the boundary working.

Part 1 — the invariant, as it reads today

   Landing is local fast-forward only; `awsf gc` lists, never deletes. Enforced

Part 2 — what it blocks today, with evidence

It blocks the words, not the act. The push clause is the pattern /git\s+push/ in core/test/unit/meta/no-destructive-paths.test.ts, run over the text of every file under core/src. Because invariant 4 bans shell: true, every Git call in this repository is an executable plus an argv array — systemGitRunner is literally runSystemCommand("git", ["-C", repository, ...argv]) — so a push is the string "push" inside an array and the two words are never adjacent.

Measured on 2026-08-24, the nine patterns against six specimens: the argv-array push passes, the argv-array push through runSystemCommand passes, a +-prefixed force refspec passes, an empty-source delete refspec passes; the two that are caught are a comment containing the words and an explicit --force flag. A seventh measurement, taken against a real local bare remote, shows why the third and fourth matter: git push origin 0000…0000:refs/heads/main printed - :refs/heads/main [deleted] and exited 0, and git push origin +<sha>:refs/heads/main printed (forced update) and exited 0.

So the clause being amended is the one that was already least enforced, and two destructive spellings are unenforced today under an invariant that reads as absolute. That is the evidence, and it cuts both ways: it weakens the case that something valuable is being given up, and it strengthens the case that the current text is misleading and should not be left standing whatever the owner decides about publication.

Part 4 — the cost, stated before it is asked for

What is traded. A reader could previously satisfy themselves about the push clause by reading one regular expression. After the amendment they must read three tests and understand a brand. An absence is checkable by anyone; a condition is checkable by anyone who understands the condition. That is a real loss of legibility and it is the honest core of the cost.

What is not traded, and this is most of it. The force and delete clauses stay absences and get three new patterns. The no-land-route fence is untouched — the dashboard still has no write path to the lifecycle, and publish is added to neither the API route table nor any surface the browser reaches. Invariant 9 is untouched and gains a measured mechanism. Nothing in core/src/state/** moves.

The residual, named rather than hidden. A unique symbol brand is defeatable by a cast, and the derivation leg detects a cast by scanning for one. A sufficiently indirect construction — a helper that launders the type through unknown across two files — could evade the scan. The locality leg is what still holds in that case, because the laundered value still has to reach an argv site, and there is only one. Stating the ceiling is the point: this is a strong fence, not an impossible one.

The second-order cost. Once one conditional exception exists, the next one is easier to argue for. W13 will ask for an amendment of exactly this shape. The mitigation is that both are named in advance in the spine, each is an owner-authored commit, and each must produce a replacement guarantee that is mechanically checkable — the bar this one clears with three legs rather than one.

Part 5 — the alternative that avoids the amendment entirely

Keep landing as the end of the line and let the owner push by hand. Invariant 8 stays as written, core/src/publish/** is never created, and the owner types the push themselves after each landing. It costs nothing to adopt and it is available today.

What it costs, stated precisely rather than dismissively. The journal ends at LANDED. Nothing records which revision reached which remote branch, at what time, with what result, or that canonical HEAD was at the approved candidate and the checkout was clean at the moment of the push. The remote's reflog holds part of it and AWSF never reads it. The allowlist does not exist, so which branch and which remote are checked by the owner's attention rather than by a rule — and the two most consequential mistakes here, a mistyped branch and a force flag typed while tired, are exactly the mistakes attention is worst at catching. That evidence trail is the entire product of this workstream; the mutation itself is one Git command either way.

The counterweight, because the alternative is genuinely reasonable. A hand-push is safe, cheap, and already understood. If the owner's honest answer is that the evidence trail is not worth a conditional exception to the strongest-reading invariant in the file, closing W08 unbuilt with that reason recorded is a legitimate outcome — and the spine's own §2 note about a declaration becoming a parking space does not apply, because the reason would be a decision rather than a deferral. One thing should happen regardless of the answer: part 2's measurement means invariant 8's current text overstates what it enforces. A one-line correction restoring the force and delete clauses to what the scan actually catches is worth landing whether or not publication is ever built.

What the owner is being asked to do, exactly

One commit, one file, one paragraph. Replace invariant 8 in AGENTS.md with part 3's text. Nothing else in that commit. It lands before task 15 and blocks milestone M6 only — M1 through M5 build against the invariant as it stands today, because none of them creates a push argv site. The Truth Table

Written before the function, and every row checked by hand against a local bare remote on 2026-08-24. The spine names this as the cheapest unused upgrade — an hour, no network, and the only way to learn whether the table is total before code depends on it being so. It was taken during authoring rather than deferred to the build, and it changed three rows.

The four inputs

statusFrom AttemptStatus: lifecycleState, candidateSha, landingApproval. Values only — the table never reads a journal.

What the bare-remote transcript settled

Idempotence is Git's, not ours. A second push of the same SHA to the same branch printed Everything up-to-date at exit 0; under --porcelain, = <sha>:refs/heads/main [up to date]. Nothing needs implementing, and the plan's job is to prove the property rather than build it.

Exit code is not the signal, twice. git ls-remote origin refs/heads/absent returns empty stdout at exit 0 — an absent branch is not an error, it is a creation. And git config --local --get-regexp '^credential\.' exits 1 when there are no matches, which is the good outcome. Both are the same lesson W07 learned about quota-axi's exit code and both are branch points a naive reading gets backwards.

--porcelain gives a closed one-character vocabulary on stdout. Measured: * new branch, = up to date,   (a space) fast-forwarded, ! rejected, + forced, - deleted. The fast-forward flag is a space, so trimming a line before splitting it loses the flag — the single most likely parsing bug in this workstream. The first stdout line is To <url> and the last is Done; prose and the URL-bearing error text go to stderr.

A hostile local config cannot silently widen the push. With remote.origin.mirror=true, push.default=matching, push.followTags=true and remote.origin.push=+refs/heads/*:refs/heads/* all set, the explicit refspec produced fatal: --mirror can't be combined with refspecs at exit 128 and every other branch on the remote survived. Git refuses rather than reinterpreting, which closes a hole the truth table could not have seen.

The credential posture works and the helper never runs. A configured helper that appends to a marker file ran on the baseline invocation and returned a password; with -c credential.helper= prepended the marker file was never created and Git failed with terminal prompts disabled at exit 128. The GIT_CONFIG_COUNT environment form behaves identically.

Three Ordering Gates, All Owner-Authored

Q2's decision took this workstream from one owner commit to three. Each is a protected path no agent can write, each is one commit doing one thing, and each blocks exactly one milestone. The bill below was measured rather than estimated, and two of the three were not visible until the state machine and the schema were read.

G8-A — the invariant 8 amendment lands before M7 builds

The spine's G2, instantiated. One owner-authored commit replacing invariant 8 in AGENTS.md with the text drafted above, landed before task 19. M1 through M6 do not wait on it — none of them removes the old scan or adds the new fence.

Read that ordering carefully, because it is the one thing in this plan that could be got wrong quietly. Task 6 creates core/src/publish/argv.ts containing the push token, and no-destructive-paths.test.ts as it stands today does not catch it — that is problem 2, measured. So the suite stays green through M6 whether or not the amendment has landed, and nothing forces the gate. Task 19 is therefore an explicit verification step with a written failure posture: read AGENTS.md, confirm the amended text is present, and mark the task [f] and stop if it is not. A workstream whose gate is enforced only by a test that cannot see the violation is a workstream with no gate.

G8-B — the PUBLISHED state and the L27 edge land before M5 builds

core/src/state/** is a protected path. One owner-authored commit touching two files: task-machine.ts gains PUBLISHED in TASK_STATES, PUBLISHED in TERMINAL_STATES, a new SEALED_STATES = {BLOCKED, CANCELLED, PUBLISHED}, step 2 of transition() reading SEALED_STATES instead of TERMINAL_STATES, L27 in the EdgeId union, and one row in LEGAL_EDGES — L27 — LANDED → PUBLISHED, actor human, not a spawn site, interactive, not a correction edge. guards.ts gains L27's guard, which Readonly<Record<EdgeId, …>> makes a typecheck error to omit.

Why the actor is human and the edge is interactive. Publication is human-initiated by the settled contract, and L20 — the other edge a person drives — is exactly this shape. A host-actored edge would let a future scheduler publish.

DECIDED Q1 — Does the allowlist name a remote, or a URL?

Decided 2026-08-25 — as recommended: remote name and branch, with an optional host checked against the resolved push URL. Applied in task 4; the derivation rule is recorded in the ticket README so a reviewer edits the rule rather than re-deriving it.

The constraint is code, not preference. core/src/registry/catalog.ts runs assertNoAbsolutePaths over every string leaf of the catalog, and ABSOLUTE_PATH_PATTERN refuses /tmp/bare.git and C:\bare.git alike. Every test in this workstream needs exactly such a path, so a URL-keyed allowlist could not express the local bare remote the spine requires the whole thing be tested against. The one spelling that would slip through — file:///tmp/bare.git — passes only because the pattern anchors on / and a drive letter, which is smuggling a machine path past a check rather than satisfying it.

What the choice buys beyond compliance. Because the argv carries a remote name, no URL enters the process arguments at all — so a credential embedded in a remote URL cannot reach argv, the journal, or an operator message, and that property holds without any scrubbing code. The URL stays in the repository's Git config, which is where it already is and where the owner already manages it.

The cost, and the mitigation that is deliberately optional. A remote name is a local, rewritable binding: git remote set-url origin <elsewhere> redirects the push and the catalog never notices. The optional host field closes that when declared, by comparing the resolved push URL's hostname. It is optional for the same reason W04's identity.root_commit is optional — a local bare remote has no host and a required field would make the mechanism unusable for the only target the tests can reach. The consequence is that this verification is opt-in and its absence is silent, which is the same honest limitation W04 recorded for its identity check and is stated here rather than discovered later.

Why not remote name only. It is simpler and it is what the tests need, but it means the allowlist constrains a label and nothing about where that label points. The optional field costs one schema property and one comparison, and a project publishing to a real forge will want it.

DECIDED Q2 — Does publication need a lifecycle edge?

Decided 2026-08-25 — against this session's recommendation: a new PUBLISHED state after LANDED. Implemented as decided in milestone M5.

What it constrains. PUBLISHED joins TASK_STATES; L27 — LANDED → PUBLISHED joins LEGAL_EDGES with actor human, not a spawn site, interactive, not a correction edge; TERMINAL_STATES gains PUBLISHED and keeps LANDED; and a new SEALED_STATES = {BLOCKED, CANCELLED, PUBLISHED} becomes what transition()'s step 2 and the journal's write protocol read. Two owner-authored commits — G8-B and G8-C — and two agent-writable preconditions in task 11.

The correction this decision forced, stated before its cost. The original answer priced no-edge at one owner commit and this option at two. That comparison was wrong in a way that favoured the recommendation: persistAttempt's validate throws SealedAttempt when the current status is terminal, and LANDED is terminal — so the no-edge design could not have journalled its evidence record either. The seal had to be opened whichever option won. What the decision actually costs over the alternative is one further owner commit and the state-machine ripple below, not the whole of it.

The bill, measured rather than estimated. Three owner-authored commits in total for this workstream: the invariant (G8-A), the state and edge (G8-B), and a migration nobody had counted (G8-C). The migration is the surprise. W07 established that a new edge is free because transitions.from_state, to_state and edge_id carry no CHECK. A new state is not: sessions.lifecycle_state is declared CHECK (lifecycle_state IN (…)) with the ten current values, SQLite cannot alter a CHECK, and core/src/observability/migrations/** is protected. Verified directly: inserting PUBLISHED against the current schema fails with CHECK constraint failed.

And the migration does not run against the current runner, which is the finding that would have been discovered mid-build. node:sqlite defaults foreign_keys to ON, seven tables reference sessions with ON DELETE RESTRICT, and runMigrations hoists only journal_mode and synchronous out of its transaction. A rebuild inside BEGIN IMMEDIATE fails with FOREIGN KEY constraint failed; PRAGMA defer_foreign_keys = ON fails identically because RESTRICT is not deferrable; hoisting PRAGMA foreign_keys = OFF works, with every child key intact and foreign_key_check empty afterwards. That hoist is agent work in core/src/observability/sqlite.ts and must land before the owner's migration commit, or every command fails to open the database.

What the decision buys, and it is more than the recommendation credited. Idempotence stops being a property of Git's behaviour and becomes a property of the machine: a second publish is refused because the attempt is sealed, before any argv is built. L27's guard gives the human-initiated requirement a second, independent home — an attempt that never reached LANDED through L23 cannot form the transition whatever the publish module later says. And awsf status can answer "did this reach the remote" without reading the evidence stream, which the no-edge design could not do at all.

What it costs beyond the commits. The lifecycle matrix widens from 100 ordered pairs to 121, the class partition moves from 27 / 10 / 6 / 31 to 30 / 11 / 6 / 47, and four test files plus a duplicated literal in the simulation harness move with it. Three dashboard files gain an eleventh state. L25 and L26 were single-cell amendments and L27 is not — it adds a row, a column, and moves a source out of the sealed set — and the existing arithmetic comment in _lifecycle-tables.ts has to say so, because the next reader will assume the pattern held.

The option set, retained so the road not taken stays readable. No edge was the cheapest and it was recommended on an incomplete reading; its real cost was one owner commit plus the same seal change, and its real limitation was that publication would have been invisible to the lifecycle — awsf status reporting LANDED whether or not the revision ever left the machine. A self-edge LANDED → LANDED is rejected by the source twice over: step 2 throws TerminalAttempt for a terminal source and step 3 throws AlreadyInState for a self-transition, both before pair legality is consulted.

DECIDED Q3 — What happens when the remote requires a credential?

Decided 2026-08-25 — against this session's recommendation: inherit the owner's configured helper. Implemented as decided in milestone M4.

What it constrains. The argv carries no -c credential.helper=. GIT_TERMINAL_PROMPT=0 stays, for a reason that is not about credentials: spawnSync captures stdio, so the subprocess has no terminal and a prompt would hang until the timeout rather than reach anybody. credentials-required narrows to the case where the helper chain produced nothing. INV-4 and AC-5 are both restated, and task 10's stub-helper test inverts.

What the decision gives up, said plainly. AWSF no longer guarantees that no credential is read during a publish. The rejected option made that guarantee structural — measured: with the helper chain cleared the stub helper's marker file was never created, so the helper genuinely did not run. Inheriting the chain means the helper runs and whatever it persists is persisted. That guarantee is gone and this plan does not pretend otherwise.

What is left, and it is what INV-4 now says. No credential value passes through AWSF: nothing the helper returns is read, held, logged or journalled; no URL enters the argv, because the allowlist keys on a remote name and Q1 kept it that way; and AWSF itself writes no credential configuration and no credential file. All four halves are assertable, and task 10 asserts them with the stub helper now proving the helper ran and that its answer went nowhere.

What it buys, and the recommendation understated it. An https remote works. The rejected option supported ssh remotes and local paths only, and refused everything else by name — a real restriction on a real workflow, imposed to protect a boundary that the config declares and does not enforce. Publishing that only works for some of the owner's remotes is a ceiling this workstream exists to remove, and the recommendation traded the ceiling for a guarantee whose enforcement was voluntary anyway.

The consequence that must not be absorbed silently. credential-access is one of the six operations awsf.config.yaml lists under policy.protected_operations, and a publish now performs it. That vocabulary is loader-checked for membership and enforced nowhere — core/src/config/load.ts validates the names and no code consults them — so nothing stopped this and no boundary was bypassed. But a plan that quietly performed a declared-protected operation without saying so would be doing exactly what the spine's R1 names, so it is said in M4's own card, in INV-4, and here. Whether that vocabulary should become enforceable is a question for whichever workstream owns the config surface, and this plan does not answer it.

Still rejected: a token from the environment. It puts a credential in the process environment of a command that constructs argv and writes a journal, which is three places invariant 9's intent would have to be re-argued. The decision to inherit the helper does not reopen it — a helper is the owner's own machinery invoked by Git, and an environment token is a secret AWSF would be holding.

DECIDED Q4 — Is a failed push's stderr retained, as W07 retains an unreadable payload?

Decided 2026-08-25 — as recommended: never retain. Closed reason codes only, and the bytes are discarded. Applied in tasks 9 and 16. Q3's decision makes this one stricter, not looser: with the owner's helper inherited, a failed push's stderr can now carry material the helper supplied, so discarding it is the only posture consistent with INV-4.

Why this differs from W07 deliberately. W07's Q9 made retention automatic because the bytes it could not parse were the evidence gap the workstream had named, and a quota-axi payload carries no credential by construction. Git's stderr is the opposite on both counts. Measured: a failed push to an unreachable host printed fatal: unable to access 'https://example.invalid/x.git/' — the URL, in prose, in the failure path. A credential-bearing URL would appear the same way, and prose is exactly what per-value redaction cannot reach.

What is lost, and it is not nothing. A push that fails for a reason the closed vocabulary does not cover produces git-failure and no detail, and diagnosing it means re-running the command by hand. That is a real cost to an operator at an awkward moment. The mitigation is that the closed vocabulary is built from measurement rather than guesswork — remote-unknown, remote-unreadable, credentials-required and mirror-configured each correspond to a failure observed during authoring — so the uncovered residual is smaller than a vocabulary invented at a desk would leave.

Why not retain after scrubbing. It sounds like the balanced option and it is the weakest. scrubCredentials replaces a value that matches a pattern; it does not rewrite prose, and a URL inside a sentence is not a value. Shipping a scrub that reads as safe while leaving prose intact is the half-closed hazard W01's guard header already refuses by name.

DECIDED Q5 — Where does the fast-forward verdict come from?

Decided 2026-08-25 — as recommended: observe with ls-remote before deciding, so row 14 is the table's refusal rather than the remote's. Applied in task 7.

The spine's requirement is what decides this. Its stop condition says every pre-LANDED state must be refused "by the truth table rather than by a code path that happens not to be reached", and the same reasoning applies to every other row. Measured: a non-fast-forward push is rejected by the remote with exit 1 and porcelain !. Relying on that produces the correct outcome while making the rule an emergent property of Git's behaviour rather than a stated condition — and the moment someone changes the remote's receive.denyNonFastForwards, the rule silently stops existing.

What it costs. Two round trips to the remote instead of one. Against a local bare remote that is free; against a real forge it is one extra fetch of a single ref, which is the cheapest operation Git has. Measured offline: ls-remote against a bare path returns in the same breath as any other local command.

The trap this row must not fall into. ls-remote of an absent branch is empty stdout at exit 0, not an error. Reading the exit code as the signal makes a branch creation look like a successful read of a branch that exists, and the resulting fastForward would be computed against nothing. The observation must read the output, not the status.

DECIDED Q6 — Where in the catalog does the block go?

Decided 2026-08-25 — as recommended: a sibling publish object inside each repository entry, leaving delivery exactly as W04 shipped it. Applied in task 4.

W04 drew this line explicitly and it should be honoured rather than reinterpreted. Its plan states that delivery records posture only — service, mobile, docs, none — and carries no remote, endpoint or credential field, because "W08 owns delivery policy and its invariant 8 amendment, and this workstream must not pre-empt either". A sibling key is the shape that leaves W04's field meaning what it meant.

Why not widen delivery. It is currently a string enum. Three derived rules that a later reader would otherwise reconstruct wrongly

The all-zeros deletion sentinel

A refspec source of forty zeros is a deletion, not a push of a nonexistent object. Measured: git push origin 0000…0000:refs/heads/main printed remote: warning: deleting a non-existent ref and - :refs/heads/main [deleted] at exit 0. So "non-delete" is not "the source is non-empty", and a check written that way would pass a deletion that also passes a forty-hex-character validator.

The porcelain flag is one character and one of them is a space

The vocabulary is * created, = up to date,   fast-forwarded, ! rejected, + forced, - deleted. The fast-forward flag is a literal space, so line.trim().split("\t")[0] silently converts a fast-forward into the ref name. Read the first character of the untrimmed line, then split. The first stdout line is To <url> and is dropped; the last is Done and is dropped; prose and the URL-bearing failure text are on stderr and are never read.

Two commands whose exit code means the opposite of what it looks like

git ls-remote <remote> refs/heads/<branch> exits 0 with empty stdout when the branch does not exist — that is a creation, not a failure. git config --local --get-regexp '^credential\.' exits 1 when nothing matches — that is the outcome the credential test wants. Both are read from output, never from status. This is the same lesson W07 recorded about quota-axi's exit code, arriving from a different direction, and it is why neither test asserts on a status.

A fourth derived rule, added by the review: a new state is not a new edge

W07 established that adding a legal edge needs no migration, because transitions.from_state, to_state and edge_id carry no CHECK. It is easy to read that as "the lifecycle has no schema constraints" and it is not what it says. sessions.lifecycle_state does carry one, listing all ten current values, so a new state needs a table rebuild in a protected directory. The two facts sit four lines apart in the same file.

Downstream of that: node:sqlite's DatabaseSync defaults foreign_keys to ON, where raw SQLite defaults it off, so a rebuild of a table seven others reference with RESTRICT fails inside the migration transaction. PRAGMA foreign_keys = ON at the top of 0001-initial.sql is a no-op — it runs inside BEGIN IMMEDIATE, where SQLite ignores it, and the setting is per-connection and unsaved anyway. The behaviour is right by accident of the driver's default rather than by that line.
