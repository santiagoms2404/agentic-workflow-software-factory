In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it says the same things precisely, for the people — and machines — building it.

What this is about

Every time the factory runs a task, it keeps a detailed log of everything that happened — every message the AI wrote, every tool it used, every cost it incurred. The owner reads that log to understand what the AI actually did. Right now, most rows in that log are unreadable: instead of showing what happened, a row shows the technical category it belongs to, printed twice. A row about token usage says "usage." A row about a tool call shows a wall of escaped computer code instead of the plain English summary that was sitting right next to it. The one thing you can actually read is a coincidence, not a design.

Why now

This is the surface the owner watches while everything else in the factory runs. Every other improvement in the wider plan gets judged through this same log, so a log nobody can read makes every other improvement harder to trust. The good news: nothing needs to be invented. The plain-English version of almost every row already exists somewhere in the system — it is simply being thrown away by one function that guesses instead of asking each kind of row what it actually has to say.

What we are building

Think of the log today like a delivery manifest where every package is labelled only "package" instead of what's inside — except for one package that happens to have a proper label by accident. This plan writes a proper label for every kind of package: a token-usage row shows the token counts, a tool-call row shows which tool ran and what it did, a cost row shows the cost. Separately, the log is flooded with thousands of tiny fragments — a long AI response arrives one syllable at a time, and today each syllable is its own full row. This plan folds a run of those fragments into one row that says "the model streamed a response, 128 pieces, 12 seconds" — click to see the whole thing, nothing hidden, nothing thrown away. And every row gets a friendly, readable view next to the technical one, with the friendly view shown first. Finally, a handful of the summary cards elsewhere on the same screen were getting visually cut off; this plan fixes that too, because it is the same screen the owner is reading.

How we know it worked

Every kind of row shows something a person can act on at a glance — no row's plain-English label is just the row's own category name. A long streamed response folds into one row that can be expanded to the exact original text, and a test proves that fold can never accidentally swallow a tool call or the end of a run. If a secret value happens to be split across two of those tiny fragments — which can happen — it is still caught and hidden after they are joined back together, proven by a test built specifically to try to sneak one through. And none of this changes what is stored in the database; it only changes how the existing log is shown. What is explicitly not in scope: nothing is deleted from storage, and no new evidence is invented — this plan stops the log from discarding what it already has.

Purpose

Make the dashboard's event log show what actually happened during a run, using data the system already records and formatters the codebase already exports — with no change to what is stored, and no new evidence added to the system.

Problem

EventLog.vue's summary() is a five-key fallback chain — inputSummary, message, detail, reason, resolvedModel — and anything that matches none of those five falls through to item.name || item.type. That single line explains every symptom: a text.delta row shows the literal string "text.delta"; a usage row shows "usage"; a tool_call row shows escaped JSON because inputSummary is first in the chain and wins over the far more useful resultSnippet, which is hidden until the row is expanded. Only quota rows read correctly, and only because message happens to be third in the chain — which is what proves the mechanism rather than excusing it.

Measured read-only against the live projection on 2026-08-20: 85.3% of all projection rows are text.delta (92.2% in the worst phase — 1,282 of 1,390 rows), and by payload bytes the deltas are 918 KB against 742 KB for everything else combined. The largest observed run reassembles to 5,490 characters across 1,282 chunks — about four characters of information per row, each wrapped in roughly 165 bytes of envelope fields. Every one of those four-character rows costs a line on screen, for a reader who is trying to find the two or three rows that actually mattered.

Solution

Four pieces, built and shipped in order of leverage. (1) Per-kind summarisers replace the guess chain with one function per kind that reads the fields that kind actually has. (2) A contiguous run of text.delta folds into one expandable row, closing the volume problem the measurement above quantifies. (3) A rendered view sits beside the existing raw JSON, defaulting to rendered. (4) The run cards elsewhere on the same dashboard screen stop clipping their fifth metrics row. None of this touches storage, the projector, or the wire format beyond one new field on folded rows — reassembly is a display-time operation on data the API already sends.

[x] Milestone M2: Delta compaction (fold, reassemble, re-redact)

Fold a contiguous run of text.delta rows into one expandable row. Folding happens entirely client-side, over the already-fetched, already-accumulated EventItem[] array EventLog.vue builds today — no new API endpoint, no change to pagination or cursors, no storage-layer change. This is the phase Collision 1 and Collision 2 both bind.

The correction that bounds this phase
Reassembly is semantically equal to the stored phase output and NOT byte-identical to it: the store holds the parsed-and-reserialised envelope, the deltas hold what the model actually emitted, pretty-printed, and the two differ from the second character (measured 2026-08-20: 5,490 reassembled characters against 4,236 stored characters for the same phase, both parsing to the same canonical JSON). A folded row's rendered text may say it reconstructs the phase's output; it must never claim to be the stored envelope. The deltas are also the only surviving record of the model's own formatting — nothing here proposes dropping them from storage, and nothing in this phase deletes a row from the database. Folding hides rows in the client's rendering; it deletes nothing.
Collision 1 — redaction is per event, reassembly crosses events
stringifyRedacted runs once per event, at projection time, before the row is ever written. A credential-shaped value split across two delta chunks matches no pattern in either chunk alone, so it is stored unredacted in both halves — and is reassembled into full, matching text by any concatenating renderer. This is a new exposure created by folding, not a pre-existing one, because before this phase no renderer ever concatenated two rows' text. Adaptation: foldTextDeltaRuns runs the same credential-matching predicate over the reassembled text, in the same function that does the concatenation, before the folded row is ever handed to the template. The split-credential fixture (a synthetic pair of chunks whose credential-shaped value is invisible in either chunk alone but complete once joined) is the cheapest unused upgrade named in the spine and the fuse-version record, and it lands here as a required test, not a check, because it cannot be run against a live projection — it needs a crafted stream.
Collision 2 — invariant 9, thinking is never persisted
thinking.delta is excluded from the events table entirely by isPersistableKind upstream, so it structurally cannot reach EventLog.vue today. The risk this collision names is future: a fold rule written over "delta kinds" as a category is one edit away from also folding — and thereby rendering — reasoning content, the moment a second delta kind exists. Adaptation: foldTextDeltaRuns's run-start and run-continue predicates both test the literal string item.type === "text.delta", never a pattern, a prefix match, or an enum of "delta-shaped" kinds. The test suite includes a fixture EventItem with type: "thinking.delta" — which cannot occur from a real API response today — asserting the fold function refuses to start or extend a run on it, so the guarantee is pinned at the function boundary rather than only at the (already-tested) server boundary.

DECIDED Q1 — Where should the credential-matching logic the fold's re-redaction step needs actually live?

Decided 2026-08-21: option A — a shared module in dashboard/shared/ — owner verdict via the exported plan-sota-review v1 block. See Amendments.

What it constrains: task 2 is unblocked. CREDENTIAL_PATTERNS, containsCredential and scrubCredentialString move into dashboard/shared/credential-patterns.ts, and core/src/policy/redaction.ts imports them from there instead of declaring its own copy; dashboard/tsconfig.json's include list widens only if the import actually requires it. scrubCredentials (the recursive object-redaction wrapper) stays in core/src/policy/redaction.ts — only the pure string-matching primitives move.

Today core/src/policy/redaction.ts's CREDENTIAL_PATTERNS, containsCredential and scrubCredentialString are pure, dependency-free string functions with no Node-specific API — nothing stops them from running in a browser bundle. dashboard/shared/ is already the established two-way seam: core/src/api/routes.ts, responses.ts and backlog.ts already import EventItem and friends from there, and dashboard/tsconfig.json already includes it. This is a smaller diff than option C (which would need new pagination-aware fold plumbing in queries.ts/routes.ts, since a fold spanning two fetched pages needs to be reasoned about server-side in a way it does not client-side, where EventLog.vue already accumulates every page into one array before rendering), and it avoids option B's single-source-of-truth risk on exactly the code this plan is most worried about not drifting. Option D ships value sooner but leaves the volume problem — 85.3% of rows — unsolved.

DECIDED Q2 — Should the rendered view show only the one-line summary, or a fuller per-kind detail panel?

Decided 2026-08-21: option A — one-line summary only — owner verdict via the exported plan-sota-review v1 block. See Amendments.

What it constrains: task 4 builds the rendered view as a direct call into summarizeEvent() / reassembledText — the same function the collapsed-row summary already calls — with no second per-kind formatting surface to design or keep in sync. Reopen only if the owner finds the one-line rendered view insufficient once task 4 ships; the trigger is named so it is not rediscovered as a surprise.

Reusing summarizeEvent() for the rendered view means the collapsed row and the expanded rendered view can never say different things about the same row — one function, two call sites. A richer <dl> panel per kind (mirroring PhaseInspector.vue's usage section) is more informative but is a second formatting surface per kind to keep in sync with the summariser, doubling task 1's surface area for a readability gain this plan's measured evidence does not show is needed — the five-key chain's defect was rows saying nothing, not rows saying too little.

A fixed height that fits five rows on every card keeps all three cards in a grid row visually level regardless of which ones actually show partial-metric — the alternative (B) would let cards with the fifth row grow taller than their row-mates unless align-items: stretch is added at the grid level too, which is a larger, less-tested change to .sessions-grid for a cosmetic fix. Option C (tooltip) hides information the owner is specifically trying to see more of, which cuts against this whole workstream's purpose.

Notes

What this plan deliberately does not touch

  • Storage-layer compaction is not proposed anywhere in this plan. Folding happens at render time, over data the API already sends; the database keeps every individual text.delta row exactly as it does today. The candidate record this plan is grounded in explicitly separated "the case is stronger than it looked" (85.3% of rows, worth compacting on screen) from "the deltas are the only surviving record of the model's own formatting" (not worth deleting from storage) — this plan only ever acts on the first half.
  • No screenshot, run id, or session id from the twelve captures this workstream's diagnosis rests on is quoted anywhere in this repository — not in this file, not in a fixture, not in a commit message. Invariant 1. Every fixture in phases 2 and 3's test files is synthetic, built from the schema in normalized-events.ts, never copied from a real capture.
  • No frozen candidate record was read while authoring this plan. Only specs/awsf-v2-candidates-fuse-version.md §10 and §2.9 — the current, fused source — and the spine's own W02 block were consulted.

The events table's actual type vocabulary

Twelve kinds are defined in NORMALIZED_EVENT_KINDS, but thinking.delta never reaches the events table (filtered by isPersistableKind), and tool.requested/tool.completed collapse into one tool_call row. The projector also writes two literal types no normalized-event kind names directly: compiled_prompt and ceiling_grant. So EventItem.type actually takes twelve distinct string values in practice, and phase 1's summariser dispatch table covers all twelve — tool_call, text.delta, usage, quota, notice, run.started, model.resolved, run.completed, run.failed, run.cancelled, compiled_prompt, ceiling_grant — plus the fallback for anything the table does not yet name, kept as a safety net rather than a case anyone expects to hit.

Why the fold lives client-side rather than as new API plumbing

EventLog.vue's existing paging loop (load()) already fetches every page with after=cursor and pushes new events into one growing events array before phaseEvents (a computed filter) ever renders anything. By the time a fold would run, the full ordered set for a phase is already in memory — a server-side fold would have to solve the same problem (a run spanning a page boundary) with strictly less information than the client already has for free. This is the concrete reason Q1 frames server-side folding as the more expensive option rather than the more "correct" one.

Rejected: fixing summary() in place rather than replacing it

An earlier framing considered lengthening the five-key chain (adding text, usage as strings, etc.) rather than dispatching by kind. Rejected because the chain's actual defect is structural — it tries every key against every kind regardless of whether that kind could ever have it, which is exactly how usage's object-shaped value slipped through silently (the chain only accepts strings) and how inputSummary beat resultSnippet for tool calls. A longer chain repeats the defect with more keys; per-kind dispatch removes the category of bug.
