In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it says the same things precisely, for the people — and machines — building it.

What this is about

This project hires outside helpers to do work. Each helper is a separate program made by a different company, and before this project will send one any real work, it has to know two things: can it read what the helper says while the helper is working, and can it stop the helper from doing something it was not asked to do. There is a third helper on the shortlist that has never been trusted with anything. Nobody had ever kept a written record of what it actually says, so the file that would connect it to this project is a placeholder that refuses every request. Someone has now sat down, run that helper a handful of times, and saved exactly what came out, word for word. Those saved recordings are the reason this plan can be written at all.

Why now

Two reasons, and the second one is the important one. The first: the recordings exist, so the reading half of the question can finally be answered from files on a disk instead of from memory, and answering it costs nothing — no further calls to the helper, no further spending. The second: the recordings also answered a question nobody had asked. When this helper starts up it announces the list of things it is able to do, and that list turned out to have fifty-seven entries on it. Four of them let the helper hire helpers of its own. That is the part that changes the decision, because everything this project uses to supervise an outside helper works by watching the one program it started. A helper that quietly starts more programs is doing work in a room nobody is watching.

What we are building

Think of it as fitting a window and a lock to a room, and discovering that only the window can be fitted. The window is a reader: a small piece of software that turns the helper's stream of chatter into the same tidy vocabulary every other helper here already speaks, so that anything watching the work sees one consistent picture rather than three dialects. That part is entirely buildable today, it is checked against the saved recordings rather than against anyone's memory, and it never needs the helper to run again. The lock is the other half, and the recordings show there is nothing to fit it to: this helper offers no setting that limits what it is allowed to do. So instead of a lock this plan fits a sign, and makes the sign honest. Wherever the project would otherwise have quietly assumed some limit was in place, it now refuses out loud and says which missing setting it was relying on. The room stays closed at the end of this work. Opening it is a decision only the owner can take, deliberately, in a file no automated helper is allowed to touch.

How we know it worked

Someone can run the project's own checks, with no internet connection and without paying anyone, and see three things. Every one of the saved recordings — including the one where the helper failed, and the one where it printed several lines of ordinary English before its final answer — is read correctly and turned into the shared vocabulary without anything being discarded as gibberish. Every place where the project used to imply a limit it does not have now states the limit is missing and refuses rather than proceeding. And the helper is still switched off, provably, through three separate doors, so no accidental edit can turn it on. What is deliberately not here: this helper does not get to do any real work at the end of this plan, not even the safest kind. Anyone can check that by looking — no job in the project's settings names it. And one question is left open on purpose because the answer was never recorded: whether one particular setting on the helper would have provided the missing lock. This plan says exactly what would have to be run to find out, and refuses to guess in the meantime.

Purpose

core/src/adapters/antigravity.ts is seventy-eight lines of deliberate refusal. Its header names the only procedure by which it may graduate: run one short agy session with a small read-only prompt, capture stdout and stderr without editing either, read the captured output, then implement fixture-first. That procedure has now been run. specs/fixtures/agy/ holds five streams, a help dump and a version string, captured 2026-09-15 from agy.exe 1.1.15, unedited but for one scrubbed OAuth URL. This plan is what the header asked for: the fixture-first implementation, written against those bytes and no others.

It has a second purpose, and by the end of the evidence review it is the larger one. The spine records this route as detection-bounded and lists two absences that would have to close before its permission half could graduate. The capture closes one of them and widens the other. This plan is therefore also the place where the containment picture gets written down accurately, so that the decision to leave the route disabled is made on measurements rather than on a shrug.

Scope, split in two — the spine's own division, kept

Parser graduation is fixture-first work that proceeds now with the route left disabled. Permission graduation waits for captured bytes proving either a provider tool-scoping flag or an OS boundary, and when it graduates it graduates for the documenter role only. Milestones M1 through M5 deliver the first and deliberately do not attempt the second. If the second never arrives, the ladder still runs on the two verified routes — which the source conditions already permit.

Problem

Three problems, in the order the evidence forces. The first is small and now solved. The second is the one the spine named and the capture answered. The third is the one the capture found, and it is larger than anything the spine recorded.

1. The spine's W09 block is wrong in four places, and the capture is why

The block was written before any bytes existed. It is corrected here rather than worked around, because every one of the four corrections changes what gets built.

The spine saysThe bytes sayWhat changes
“A separate portability run found the executable does not resolve under the configured name on this machine at all.” True but misleading. agy is not on PATH; agy.exe is installed under AppData\Local\agy\bin\ and reached through a shell alias. It is a configuration finding, not an absence. The binary exists and runs. What cannot work is executable: agy for a spawned child: an alias is shell-local, and ENV_ALLOWLIST passes only PATH, HOME and TMPDIR. T12 turns this into a test.
“It requires a Windows-accessible working directory” — read by every later reader as a WSL-native worktree cannot work. stream5 and stream6 ran from /home/… with init.cwd reported as \\wsl.localhost\Ubuntu\home\…. The earlier failure from that path was an authentication failure, proved by stream4 succeeding from D: minutes later on the same token. AWSF's worktrees are on WSL-native ext4 and the adapter can run in them. The requirement is real but weaker than recorded: the path must be reachable from Windows, and \\wsl.localhost\ is. Correctness is settled; throughput is not (see problem 4 below).
“The stream emits a four-event NDJSON protocol…” Three event kinds: init, step_update, result. The fourth thing the spine counted is step_type, which is a field inside step_update, not an event. A parser written to a four-case switch would carry a dead branch and, worse, would imply the taxonomy lives at the wrong level. The real shape is three kinds crossed with four step types and two states.
“…with stream-authoritative model identity.” There is no model identity anywhere in the capture. init carries exactly three keys — cwd, tools, permission_mode. A scan of all five streams for the substring model returns zero matches. model.resolved from this route must carry provenance: "route-attributed". This is the second adapter whose “stream-authoritative” claim collapsed on inspection; core/test/fixtures/providers/codex/PROVENANCE.md records the first, and reaches the same value for the same reason.

2. The open item the spine called its cheapest unused upgrade — answered, with its limit stated

The spine: “Does a tool event arrive before or after the provider has executed that tool? Detection cannot claim timely abort without event-order evidence, and no fixture establishes it.” stream2 establishes it. run_command appears at step_index: 2, state: "ACTIVE", carrying its full parameters (CommandLine: "(Get-Location).Path"), and again at state: "DONE" 8.198992 seconds later with its output. view_file does the same with AbsolutePath. Parameters arrive before the result.

The limit, stated precisely — this is not prevention

ACTIVE precedes completion. It is not proven to precede initiation. Nothing in the capture shows whether the CLI emits ACTIVE before it hands the call to the tool or after. So what the ordering buys is detection with latency — a host that reads the stream learns the parameters of a call that may already be running. It buys no abort that is provably timely, and the spine's own rule applies with full force: the route is detection-bounded, and describing it as prevention is not the owner's to accept.

3. The containment picture is worse than recorded, and this is the centre of the plan

The spine says detection “says nothing about shell execution, messaging, scheduling or web search, three of which are external-mutation shaped.” init declares 57 tools and the surface is wider than four names:

The decisive finding — a first-class obstacle, not a footnote

The tool spawns its own agents. AGENTS.md invariant 3 confines node:child_process to core/src/execution/transport-broker.ts, and child-process-fence.test.ts holds it. That fence confines AWSF's spawns. invoke_subagent means the tool creates spawn sites on the far side of it: no broker registration, no reservation id, no GO, no cancellation handle, no per-child worktree, no attribution. This is W10's decisive finding repeating in a second adapter — there, only the outer process of a composite crossed the broker; here, only the outer process of a turn does.

The same class of problem shows in the run's own error channel. stream2's stderr carries "root agent idle; waiting for 1 background task(s) (bounded by --print-timeout)" — work outliving the turn. Read carefully, that line is partly reassuring: the CLI waits. But it waits only until --print-timeout, and what happens to a still-running background task when that timeout fires is unmeasured, as is whether such a task shares the process group AWSF's cancellation kills across the WSL interop boundary.

Evidence discipline: that stderr line is quoted in specs/fixtures/agy/README.md and no stderr file is retained beside the streams. The claim rests on a quotation, not on bytes in the tree. T01 records that as a named fixture debt; it is the one gap in the capture that a second short session would close for no model spend.

And the default is weaker than its name. permission_mode: "request-review" is declared in init, it is the default, and under it the agent executed a PowerShell command unprompted — the prompt asked where it was, not for a shell call. Every capture here was taken without --dangerously-skip-permissions, so what is recorded is the guarded behaviour.

4. One constraint nobody has measured

A WSL-native worktree means init.cwd is a UNC path. Every file operation the provider performs, and every host gate command it triggers, would cross \\wsl.localhost\. Correctness is established; throughput is not. This plan names it as an unmeasured risk with a settlement that costs no quota, and does not assume ext4 performance on the far side of a network-filesystem redirector.

Solution

Five milestones. The first is a decision milestone that can legitimately end the workstream; the next three build the parser, the descriptor and the containment proofs; the fifth proves the route is still off and writes the dossier that a future session would need to reopen permission graduation. No milestone enables the route, and no milestone spends quota.

Questionables

Seven. The first four are the ones the spine and the owner's brief explicitly asked to be surfaced; the last three came out of the bytes. Each carries a recommendation, and every recommendation is the plan's default if the owner takes no other answer.

Q1. May a route whose tool can spawn its own unsupervised subagents carry any role — even documenter, even with a proven OS boundary?

Recommendation: never, at any evidence level, until the subagent surface itself is contained. The spine's graduation condition was written before anyone had read init.tools, and it asks for evidence of “a provider tool-scoping flag or an OS boundary”. Both of those are properties of the process AWSF starts. define_subagent, invoke_subagent, manage_subagents and browser_subagent are a mechanism for creating processes AWSF does not start — so an OS boundary around the parent is evidence about the wrong object unless it demonstrably encloses the children too, and nothing in --sandbox's one-line description says it does.

The counter-argument is real and should be recorded rather than dismissed: the documenter role writes only README.md and docs/**, its work is reviewed before it lands, and the post-return fingerprint would catch a write outside those globs. That argument is sound about writes. It says nothing about send_message, schedule, search_web, call_mcp_tool, read_url_content or execute_browser_javascript, four of which are external-mutation shaped in the config's own protected-operations vocabulary — and a documenter phase has no legitimate use for any of them, which is exactly why the absence of a way to switch them off matters.

What would change this answer: captured bytes showing a subagent launch refused under some flag, or showing that subagent execution is confined to the parent's namespace. Neither exists, and neither is cheap — the probe would have to provoke a subagent, which is a different and riskier capture than stream7.

Q2. Is detection-with-latency worth building at all, against a 57-tool surface?

Recommendation: do not build in-stream detection in this workstream. The event ordering is settled and it is genuinely useful evidence — but three separate facts say the mechanism built on it would not pay for itself here.

One: the parameters arrive in Windows and UNC spellings that path-policy refuses by design and for a stated reason, so a detector would need an adapter-local mapping that does not exist and that must fail closed — meaning it refuses on ambiguity, meaning it is noisy exactly where it matters. Two: ACTIVE is not proven to precede initiation, so an abort fired on it cannot be described as timely without claiming something the capture does not show. Three, and decisively: a detector reads the parent's stream. A subagent's tool calls are not in it. A mechanism that covers the visible path while the invisible path stays open is worse than no mechanism, because the badge it produces gets believed.

What the workstream keeps instead: the tool.requested events themselves, with parameters, in the journal, where a human or a later gate can read them. That is evidence and observability, and the plan never calls it containment. What would change this answer: Q1 resolving in favour of some role — detection becomes worth building the moment the route could actually run something.

Q3. Should the unmeasured UNC throughput question gate the workstream, or merely be recorded?

Recommendation: record it, gate nothing. Throughput is a property of a route that runs, and at the end of this workstream this route does not run. Gating twenty offline tasks on a filesystem benchmark for a disabled route inverts the cost.

It is recorded with teeth rather than as a footnote: T15 names the measurement, the comparison and the command, and T17 either records the numbers or marks the row [f]. The measurement is cheap — a timed file-heavy loop from the Windows side against a worktree-sized tree, versus the same work on ext4 — and it involves no agy and no quota, so whoever wants the number can have it in an hour without this plan's permission.

What would change this answer: Q1 resolving in favour of a role. A route that carries a documenter phase against a worktree with a full node_modules in it would feel this immediately, and finding out then is finding out late. The honest framing: it gates graduation, not this workstream.

Q4. Should W09 end unbuilt, with its evidence retained?

Recommendation: build M1 through M5, and understand that as building the reading half and closing the permission half — not as a route on its way to service. The spine permits closing unbuilt, and the capture has made that outcome more defensible rather than less. So the case for building has to be made on what the build produces, and it is narrower than it first looks.

What building buys, concretely. The bytes move inside the fences that already exist — today specs/fixtures/ is reached by no sweep in the repository. The probe's single blanket refusal becomes typed refusals that name their causes, so “we have not looked” stops being spelled the same way as “we looked and it cannot be contained”. The roster becomes a test that goes red if a future agy changes it, which is the only realistic trigger for revisiting the decision. And three mechanisms elsewhere in the tree stop overstating — the badge fix in T14 is a correctness fix that outlives this workstream entirely.

What it costs, stated fairly. Roughly five to seven hundred logical lines of decoder and adapter that nothing calls, in a directory with an advisory budget. The loc-budget meta-test warns and never fails, so this is a judgement rather than a gate — but a parser for a route no role may use is genuinely dead code until Q1 changes, and calling it anything else would be dishonest.

The middle option is real and is not a compromise for its own sake. Stopping after M1 retains the bytes, pins the obstacle, extends the sweep and closes the workstream — four tasks, no runtime code, and the spine's checklist row “scrubbed fixtures for every event and terminal state exist in the tree” is satisfied. What it forfeits is the spine's other stop condition, which says the parser is fixture-complete. An owner who takes this option should say so explicitly in the spine Amendment, because it closes the workstream against a condition the spine did not write.

Q5. Where do the retained bytes live canonically — specs/fixtures/agy/ or core/test/fixtures/providers/agy/?

Recommendation: copy to core/test/fixtures/providers/agy/ and add a byte-identity test, leaving the owner's directory in place. Two locations that can drift is a real hazard, and a test that asserts they cannot is cheaper than a decision about someone else's files.

The reasons for the second location are not aesthetic. The credential sweep walks core/test/fixtures; every other provider capture lives there with a PROVENANCE.md beside it; and the suite's fixture-integrity rule is expressed in terms of that convention. The reason for keeping the first is simpler: the owner put the bytes there deliberately and this plan's brief names that path as the target. Deleting an owner-placed directory is the owner's call, not a task's — so the plan makes it Q5 and ships the byte-identity test as the interim answer, which makes the eventual deletion a one-line change either way.

Q6. The prompt travels in argv. Accept the ceiling, or spend one live call to settle the stdin path?

Recommendation: accept the ceiling and refuse above it, for now. This is the one place in the plan where a live call would answer a question the retained bytes genuinely cannot, so it deserves a straight answer rather than a reflex.

What the call would buy: --input-format=stream-json reads one NDJSON message per line from stdin and requires --output-format=stream-json. If it works, the prompt leaves argv entirely — no command-line ceiling, and no prompt in the process table where any other process on the machine can read it. That is a real improvement over the captured shape, and the message envelope it expects is documented nowhere in help.txt, so it cannot be derived by reading.

Why it still waits: the benefit accrues to a route that runs, and this route does not run. The refusal costs nothing to write and is strictly honest — a prompt too large to send is refused before a child starts, rather than truncated into a confident answer to a question nobody asked. If the owner is spending a session on agy anyway, this should ride along with the stream7 probe in Q7, because two questions in one authenticated session is the efficient shape and the two captures are independent.

Q7. The --sandbox probe was asked for and never arrived. What now?

This plan was briefed with a placeholder for the --sandbox result and the placeholder arrived unfilled; there is no stream7 in specs/fixtures/agy/. Nothing here guesses which way it went.

Recommendation: close graduation now, and fold the probe into a later session alongside Q6. The spine's condition is that permission graduation waits for captured bytes. Absent bytes means it waits — that is the condition operating correctly, not a gap in this plan. Recording graduation as “closed for want of evidence” is therefore the accurate state, and it is materially different from “pending someone's attention”: the first is a decision a reader can rely on, the second rots.

The probe is specified in full anyway, in T19, with the reading of each outcome fixed before the bytes arrive so that a future session cannot read a favourable result more generously than it deserves. And the ceiling on that reading is stated in the same place: --sandbox is described as “terminal restrictions”, which on its face reaches run_command and nothing else. Even a clean refusal leaves write_to_file, twenty browser tools, four external-reach tools and all four subagent tools untouched. A green stream7 would be necessary and nowhere near sufficient — which is also why it does not deserve a session of its own.

Notes

What this plan deliberately does not do

  • It does not enable the route, and it does not edit awsf.config.yaml. That file is protected; path-policy rejects protected-path independently of the write globs, and inventing an owner-authorized change mechanism to route around it is the boundary working.
  • It does not describe detection as prevention, anywhere, in any tense. The route is detection-bounded; the bare adjective does not describe it, and T17 makes that a grep rather than an intention.
  • It does not claim per-role supervision the broker never saw. One process crosses the broker. Anything the tool starts beyond it is unregistered, unreserved, uncancellable and unattributed.
  • It does not spend quota re-capturing what is already retained. Five streams, a help dump and a version string are in the tree. Every assertion in M2 replays them.
  • It does not read either frozen candidate record — awsf-v2-candidates.md or the GPT version — whose own headers mark claims in them as false.
  • It does not treat invoke_subagent as a footnote. It is INV-2's second half, T03's test, T16's comment, Q1's whole content, and the reason Q4's recommendation is narrower than “build the adapter”.
