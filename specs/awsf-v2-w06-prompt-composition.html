In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it gives the precise build instructions.

Three workers prepare the same instruction packet three different ways

Today, the normal worker, a replacement checker, and a repair worker each assemble their instructions separately. That makes it easy for one path to miss a rule or use changed wording while the record still says the settings were unchanged.

A new kind of worker is about to arrive

The earlier workstream has designed two new jobs. Its final stage waits here because adding those jobs before instruction assembly is unified would create another copy of the problem.

Build one packing desk, then add the common note

First, all instruction packets go through one packing desk without changing a byte. Second, that desk adds a short common note suited to each job and seals the complete packet into the same permanent record as the job's own instructions. The independent checker keeps its full duty to disagree and show evidence. Shortcuts used only in conversation never enter these worker packets.

Compare repeated like-for-like work

Automated checks prove all three paths receive the same private packet and reject changed instructions. A separate paid comparison then repeats the same work with and without the common note. It records words sent, words returned, repair rounds caused by malformed answers, and how specific the independent checker's evidence is. One run on each side proves nothing, so this workstream cannot close on that basis.

Purpose

Replace three independent headless system-prompt composition implementations with one host-owned composition boundary, append a reviewed shared per-role block without weakening role-specific contracts, bind every resulting byte to immutable route evidence, and assess the prompt effect with a pre-registered repeated matched-task benchmark.

Problem

production-run.ts, review-phase.ts, and rework.ts each resolve configured prompt paths and construct route objects independently. The adapter boundary is already safe and append-only, but the bytes handed to it can diverge before that boundary. The config snapshot records prompt paths rather than prompt contents, so a later rework or replacement review can read changed bytes under a snapshot that still compares equal. Adding W05's designer and architecture-reviewer before centralisation would add another prompt path.

Solution

Create one prompt-bundle boundary that resolves contained committed prompt paths, credential-checks the inputs, composes the system bytes, and returns the user prompt plus immutable component evidence. Migrate all three command paths to it with no shared block present. Only after byte-parity and a source-count fence are green, add the shared per-role block through that boundary. Persist the role, shared, and composed digests beside the full composed system bytes in the existing immutable compiled-prompt evidence, and refuse rework or replacement review when current composition differs from the route on record. Keep writeSystemPromptFile, assertPrivateSystemPrompt, and both adapters unchanged.

Composition contract

composePromptBundle({ configRoot, agent, sharedPolicy }) → {
  userPrompt,
  systemPrompt: roleSystemBytes + separator + renderedSharedBytes,
  evidence: {
    roleSystemDigest,
    sharedBlockDigest,
    composedSystemDigest,
    compositionVersion
  }
}
  • The composition function owns the separator and newline rule. Callers may not concatenate prompt text.
  • Phase M1 uses an empty shared component and must reproduce today's system bytes exactly. No fourth copy is created while centralising.
  • The full composed system prompt remains the compiled-prompt text. Optional component digests extend that same evidence record for legacy journal compatibility rather than creating a receipt or manifest.
  • The API accepts no interactive-alias input. Absence from the type and call surface is stronger than asking each caller to remember a filter.
  • Role-specific system prompts remain authoritative. Shared style never replaces role contracts, output schemas, write policy, or reviewer dissent/evidence duties.

Questionables

All five decisions were settled by the owner on 2026-08-23. They remain here with their option sets so the implementation and the roads not taken stay reviewable. No status marker moved.

DECIDED Q1What is the shared block's committed source shape and exact reviewer treatment?

Decided 2026-08-23: one common file plus a closed reviewer overlay. One common committed file carries universal style; the composition module owns a closed role policy that appends a reviewer-preservation overlay. The approved common clauses require plain and specific language, each fact once, detail matched to task, exact output-contract compliance, and brevity only when no required fact or evidence is lost. The reviewer overlay makes dissent, findings, limitations, locations, observations, and consequences outrank brevity. Unknown roles fail closed and no interactive alias text enters the headless block.

DECIDED Q2What deterministic floor defines reviewer evidence specificity?

Decided 2026-08-23: structural four-point rubric plus the explicit omitted-evidence rule. The four points are candidate-relative file, line or explicit file-wide scope, observed mechanism or condition, and concrete consequence. The output must also name a limitation when host evidence is bounded or omitted and the missing surface cannot be checked. A clean review may have zero findings, so the gate judges findings that exist and required limitations rather than rewarding finding count. Fixtures cover detailed concern, legitimate clean accept, deletion-only, omitted evidence, vague evidence, and tersely agreeable output.

DECIDED Q3How large is the repeated matched-task benchmark, and which task classes enter?

Decided 2026-08-23: three tasks × five paired repetitions per arm, 30 route runs. The fixed task classes are bounded source change, contract/envelope change, and evidence-heavy defect review. Each task completes five baseline and five candidate runs, with arm order alternated by pair. Task inputs, route config, provider/model identities, and deterministic gates stay identical between arms except for the shared composed bytes. An incomplete pair or fewer than five repetitions on either side is no result.

DECIDED Q4What predeclared thresholds decide whether the shared block stays?

Decided 2026-08-23: safety non-inferiority is binding and token deltas are descriptive. Candidate parse-correction total may not exceed baseline, candidate median reviewer-specificity score may not decrease, and no task may lose a required reviewer limitation. Input/output token deltas are reported by task and arm without an adoption threshold because the shared block necessarily adds input bytes and no credible effect size exists yet. Token savings cannot offset either safety regression.

DECIDED Q5Where is the benchmark result retained without creating a committed runtime artifact?

Decided 2026-08-23: journal detail plus a handle-free aggregate Amendment. Detailed rows remain in the existing journal/status store. This plan receives only an aggregate Amendment with protocol version, completed repetition count, metric summaries, invalidated-pair count, and threshold verdict. It names no task, attempt, session, provider handle, or journal path. No external analysis location or committed benchmark report is added.

Rejected approaches

  • Write the shared block first. Rejected because it creates a fourth copy before removing three.
  • Put the block in each role's system file. Rejected because “shared” becomes eight independently drifting copies and later roles recreate the problem.
  • Change adapter flags. Rejected because both adapters already append private prompt files and assert them at launch.
  • Add prompt bytes to committed config. Rejected because config is a tuning surface and protected path; immutable route evidence already exists in the journal.
  • Use one baseline and one candidate call. Rejected because model variance dominates a two-call comparison.
  • Put the paid benchmark under npm test. Rejected because an offline suite may not spend quota or depend on provider availability.
  • Commit a benchmark report. Rejected by invariant 10; detailed evidence belongs in the journal.
