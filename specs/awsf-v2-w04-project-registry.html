Plan: AWSF v2 W04 — Project registry v1

A factory that can build this repository knows one project by knowing nothing about projects at all. Pointing it at a second one needs two records that must never be the same record: a catalog of what a project is, committed and durable, and a placement layer of where its clones sit, machine-local and never committed. The split is forced by code, not chosen — core/src/config/load.ts refuses absolute machine paths outright, so a committed catalog physically cannot hold a clone location. This is a deep plan, one workstream of the v2 spine (Milestone M4), and the spine's hinge: W05, W07 and W08 all wait on it. It carries the two schemas and the rejection each makes of the other, the join between them, the content-addressed cross-repository contract Questionable Q1 settled, the redefinition of AGENTS.md invariant 12 that a separate plan repository forces, and the v1 ticket move that belongs here and nowhere else. Authoring it wrote no implementation code, changed no invariant, committed nothing, and flipped no marker. It did spend the workstream's named cheapest unused upgrade — a read of the owner's real multi-repository project — and that reading changed the schema in five places before it froze. What was measured is quoted below.

In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it says the same things precisely, for the people — and machines — building it.

The workshop only knows how to build one thing, because it has never been told there is more than one

There is a workshop that builds software. Today it can only work on the single body of work it lives inside, the way a workbench with one job clamped to it never needs a label. The moment the owner wants it to work on a second body of work — and the owner has one, a health project made of several separate pieces kept in separate places — the workshop has no way to be told which one it is working on, where each piece is kept, or which pieces belong together.

The obvious fix is to write all of that down in one list. That fix is wrong, and it is wrong in a way the workshop already refuses to allow. Two very different kinds of fact get mixed into one list. One kind is true forever and true for everyone: this project has a piece that holds the written plans, and two pieces that hold working parts, and this part is checked by running these particular checks. The other kind is true only on one computer, today: on this machine, that piece is kept in that drawer. Written together, the second kind poisons the first — the list stops being a description of the project and becomes a description of one desk. Hand it to a second machine and it is wrong everywhere it matters.

The workshop already refuses the mistake, which is why now

This is not a preference anyone has to be talked into. The workshop's existing settings reader already rejects anything that looks like a location on a particular machine — it will not accept the setting at all. So the mixed list is not merely a bad idea; it cannot be written. The separation is forced. What is missing is only the second list, the one that is allowed to say where things are because it never leaves the machine it describes.

The second reason for now: the health project is real, it is already split across several pieces, and one of those pieces contains a hand-written table of where the others are kept, complete with the exact drawer names on the owner's own computer — and that table has been shared publicly and has already gone out of date. It is the mistake this plan prevents, already made, already committed, already stale. Building the fix against that real project rather than an imagined one is what an hour of reading bought, and it changed the design in five places.

Two lists, a rule that keeps them apart, and a fingerprint that catches copies drifting

Think of a touring theatre company. The programme says what the show is: which people are in it, which scenes belong to which act, what has to be true before the curtain goes up. It is printed once and it is the same programme in every city. The get-in sheet says where everything is in tonight's building: which door, which room, which corridor. It is written fresh in each city and thrown away after. Nobody prints the corridor numbers into the programme, and nobody expects the get-in sheet to explain the plot.

This plan builds both, and — this is the part that makes it real rather than tidy — it makes each one refuse to hold the other's content. A location written into the programme is rejected outright, not warned about. A fact about what the show is, written into the get-in sheet, is rejected too. Neither can quietly become the other over time, which is how this sort of separation usually dies.

Then there is a third thing, and it is the one with the most value hidden in it. When a project is made of several pieces that have to agree with each other — one piece produces a description of how to talk to it, another piece has to hold a copy of that description — the two copies drift apart silently, and nothing notices until something breaks in front of a user. The fix is a fingerprint. Each piece keeps its own copy and the fingerprint of what that copy is supposed to be, and a check that reads nothing but that one piece's own contents can say whether it still matches. Copies drifting stops being a hazard nobody is watching for and becomes a failed check, immediately, in the ordinary run of work. The owner's health project already keeps two copies of exactly such a description; today one side is checked automatically and the other side is checked by nobody, and the instruction for keeping them in step assumes the two pieces sit side by side on disk — which, for several of the working copies actually in use, they do not.

Finally, there is a promise the workshop already makes and enforces by machine: a written plan and the individual work items cut from it must never disagree. That promise is currently kept by a trick — the plan and its work items are always found in the same place, so they are found together. Once a project keeps its plans in a piece separate from its working parts, that trick stops working. This plan replaces the trick with something stronger rather than weaker: the pairing is looked up deliberately instead of assumed from where the files happen to sit, and two new ways of getting it wrong — a set of work items whose plan cannot be found, and a plan written in a form the checker does not know how to read — become loud failures instead of silent ones.

How anyone would know it worked

A second project can be described to the workshop and located on this machine, and neither description can be made to hold the other's kind of fact — attempting it is refused with a named reason, not accepted with a warning. The existing housekeeping commands still see one place for all projects rather than one place each. The two copies of a shared description are proved to match, and the check is proved to fail when one copy is deliberately altered by a single character — a check nobody has watched fail is decoration. The plan-and-work-items promise still holds, is still enforced by machine, and has also been watched to fail on a deliberately introduced disagreement across a boundary it could not previously see. And the workshop's own existing work items keep listing exactly as they do today after they are moved, which is the one part of this that is easy to break silently and would be noticed by nobody.

Deliberately not part of this: any single job spanning two pieces at once. A job takes one piece, and finishing it is all-or-nothing within that piece. Work that genuinely touches two is a parent note plus two separate jobs with an agreed description between them — because a half-finished job across two pieces has no way to be undone, and nothing here would be able to write that story honestly.

Purpose

Turn "a factory for this repository" into "a factory for the owner's projects" by giving AWSF a project it can name, describe, locate and resolve — without letting a single machine fact reach a committed file, without teaching doctor, gc or db rebuild to walk more than one state root, and without letting any task own more than one repository.

Three consumers are waiting on the result and shape what v1 must contain. W05 needs a plan source it can resolve, because its AC/INV coverage gate extends the same fence this workstream redefines. W07 needs per-repository scope for its quota readout. W08 needs per-repository delivery policy, because the spine states plainly that its allowlist "has to live in the catalog". W04 is the hinge: the longest path in the spine runs through it.

And one obligation that is this workstream's alone. Invariant 12 currently assumes a plan and its tickets share one checkout. A separate plan repository breaks that assumption. This plan owes a new mechanically-checked source-of-truth relation — redefined, never relaxed — proven to fail on an induced drift, and an owner-authored amendment to the invariant's text that lands before the build starts.

Problem

AWSF has exactly one notion of "which project": const project = parsed.flags.project ?? config.project.slug. A slug, read from the committed config of whatever repository the command was run in, or overridden by a flag. Everything downstream — the attempt directory, the journal, the status store — is already namespaced by that slug. The storage layout is already multi-project; the vocabulary is not. There is nowhere to say that a project has more than one repository, nowhere to say which of them holds its plans, nowhere to say what each is checked with, and nowhere to say where any of them are.

The obvious fix is one list, and one list is the thing the loader refuses

core/src/config/load.ts holds ABSOLUTE_PATH_PATTERN = /^(\/|[A-Za-z]:[\\/]|\\\\|~)/ and walks every string leaf in the parsed document — object keys and values, array items included — throwing ConfigAbsolutePathError on the first offender. Its comment states the reason as a rule rather than a check: "A committed config is 'durable intent' — it must never encode where anything lives on any one machine." A committed catalog carrying a clone location is not discouraged. It is unrepresentable. That is the forcing, and it is not negotiable.

The mistake has already been made, in the owner's own project, and it is public and stale

The owner's health platform keeps its plans in one repository and its code in others. That plan repository's agent-facing document carries a five-row table — alias, path, role — and the path column holds absolute Windows paths. It is committed. It is pushed to a public remote. It is a catalog and a placement layer fused into one file, which is exactly the artifact this workstream exists to replace, and it is already wrong: it records one of its five repositories as "not yet under git", and that repository is on a branch. A hand-maintained placement table drifts. That is measured, not predicted. The same repository's engineering document additionally hardcodes an absolute path to the plan repository in prose, so a reader who moves either clone gets a document that points at nothing.

Invariant 12's fence is held together by directory adjacency

core/test/unit/meta/ticket-plan-sync.test.ts pairs a ticket set with its plan by filesystem convention: specs/tickets/<stem>/ resolves to specs/<stem>.html, and the build prompts are looked for beside the plan. That works while every plan and every ticket lives in one checkout, and it is what breaks the instant a project's plans live in a repository separate from its code. The store has the same shape of assumption pointing the other way: ticketStoreFor(repository) resolves <repository>/specs/tickets, so awsf ticket list run inside a code repository of a multi-repository project finds nothing at all.

Three separate reasons a deep plan's tickets are already invisible to the store

Found by reading the code this workstream must not break, and worth stating precisely because two of the three are invisible from the fence's side. TicketStore.load() filters /^T\d\d\.md$/, so a W-numbered file is rejected by name. It calls readdir with no recursion, so a subdirectory is never entered. And TicketSchema requires tier, workflow, outcome, context, acceptance and non_goals, all of which the v2 ticket sets omit by the sync fence's own already-decided rule. Moving v1's flat tickets fixes none of the three by itself, which is precisely why the fuse record reversed that move and re-homed it here.

Solution

Two documents with two loaders, each rejecting what the other must hold; one join with four named rejections; a content-addressed contract that lets a child repository check its own agreement without reading anyone else's tree; and invariant 12's relation resolved through the registry instead of through a directory listing.

The catalog — awsf.project.yaml, at the plan repository's root

Durable project intent, versioned awsf.project/v1, and narrow by Q2's decision: project identity, one entry per repository carrying its role, default branch, gate commands and delivery posture, and the declared contracts between them. It is a separate document with its own schema and its own loader, never an extension of AwsfConfig — Q2 refused config loading outright, and the refusal is structural: a precedence rule between a project's config and the protected awsf.config.yaml is a route around path-policy that needs no amendment to take.

It lives in the plan repository because that is the one repository a project with a plan is guaranteed to have, and because it is the repository whose whole job is already cross-cutting description. For AWSF itself the case is degenerate and instructive: this repository is its own plan repository, so its catalog names one repository whose role is both.

The absolute-path rejection is inherited, not re-implemented. Task 1 extracts isAbsoluteMachinePath and the string-leaf walker out of load.ts into a shared module, leaving loadConfig behaviourally identical, and the catalog loader calls the same function. The guarantee "a committed catalog cannot hold a clone location" is then the same code path that already holds for the config, not a second, weaker sibling of it — which is the fourth rule the spine's Shared Invariants section imposes, applied here deliberately.

The placement layer — <state-root>/projects/<slug>/placement.yaml

Machine-local by construction, because the state root is machine-derived: resolveStateRoot(env, platform) reads XDG_STATE_HOME, or falls back per platform, and is configured in no committed file anywhere. A placement document written under it is outside every repository and therefore cannot be committed by accident.

Per project, not one shared file, and that is the existing grain: attemptDir already resolves <state-root>/projects/<project>/tasks/<task>/<attempt>/, and discoverAttempts already walks <state-root>/projects/* filtering to directories, so a file beside those directories is skipped by the walk it must not disturb. It is also the pattern this repository has held to elsewhere — TicketStore's own comment says there is intentionally no database, cache or index, and one mutable file every project must contend for would be exactly that.

Placement carries paths and nothing else, and its schema enforces the mirror-image rule: a relative path is a rejection, because a relative path resolved from a different working directory is a different location. Catalog refuses absolute; placement requires it. Each layer refuses what the other must hold, and a meta-test asserts the two schemas' property sets are disjoint but for the join key.

Per-repository worktree roots, because per-project cannot describe the real case

Placement carries a project-level worktree_root and a per-repository override. This is not a generalisation for its own sake: the measured project's two code repositories keep their worktrees under two different filesystems — one repository's are all siblings of the clones on the Windows-mounted projects root, while the other's are split, with the most recent three moved onto the Linux home filesystem. A placement layer offering one root per project cannot describe that project. Resolution order is per-repository override, then project default, then defaultWorktreeRoot(stateRoot) — which is join(dirname(stateRoot), "awsf-worktrees"), a sibling of the state root and never inside it.

The state root is in neither layer, and the reason is a working command, not a preference

doctor, gc and db rebuild each take one stateRoot, and discoverAttempts(stateRoot) already iterates every project inside it. Project namespacing is not something this workstream invents; it exists in platform-paths.ts today. Putting a state root in either layer would give a project its own root and require teaching three working commands to walk several. The catalog cannot hold one, the placement layer does not need to, and a meta-test asserts neither schema has a property that could become one.

Recorded, not resolved — what Q2's consequence means in code

The catalog's gate entries carry the same shape awsf.config.yaml's already do — argv as an array with at least one element, plus timeout_seconds — keyed by an id in KNOWN_GATE_IDS. Resolution stays exactly where it is: commandsPass(output, configured, context) in core/src/gates/commands.ts joins on gateId and asserts argv exact against host-generated evidence. The catalog becomes a second source for the same triple; it gains no resolver, runs nothing, and interprets nothing. An argv array rather than a command string is also invariant 4 holding: executable plus argv, never shell: true.

Q1 as decided — the contract is content-addressed and committed in each child

The catalog's parent coordination record names, per contract, the producing repository, each consuming repository, the repository-relative path in each, and one sha256: digest. Each participating repository also commits awsf.contracts.yaml, a small projection naming only the contracts that repository participates in and the digest each is expected to hash to.

Why the projection exists, and why it is forced rather than chosen
Q1 requires two things at once: the parent record names the digest, and a child's gate reads its contract from inside its own worktree. A gate that had to read the parent record would have to reach into the plan repository — across exactly the boundary path-policy exists to hold, which is the hole the parent-owned option was rejected for opening. The only shape satisfying both is a copy of the digest inside each child. It cannot live in that child's awsf.config.yaml, because that file is a protected-path no agent can write and a contract revision must be committable as ordinary work. So it is a separate file, and the cost — the digest now has N+1 copies, not just the artifact — is paid by the second fence below.

Two fences, and the division of labour is the point. The local fence runs inside one repository, reads only that repository's awsf.contracts.yaml and the files it names, and asserts each hashes to its recorded digest. It needs no registry, no placement, and no second tree — it is the gate a child's worker phase runs. The central reconciliation, awsf project verify, runs over a resolved project and asserts every child's projection agrees with the parent record and every artifact agrees with both. It is driver-side, it is allowed to use placement, and it is what makes the N+1 copies safe.

Invariant 12, redefined per registered plan source

The catalog declares which repository holds the plans and where inside it they live. A plan source is {project, repository-id, plans-root, plan format}, and it resolves to a machine path only through placement. The fence pairs each ticket set with its plan through that record instead of through readdirSync on a fixed directory, and the store's ticketStoreFor(repository) is joined by ticketStoreForPlan(resolved, planStem), which resolves into the plan repository rather than the working one.

The redefinition has a second half the phrase "registered plan source" does not cover
Resolution is only one of the two adjacency assumptions. The other is grammar. The fence matches /<h3><code class="status">\[([^\]]*)\]<\/code> Milestone (M\d+):/. The measured project's real plan writes its headings as <h3><code class="status">[…]</code> Phase 24.5 — Phase, not Milestone, and a decimal ordinal, not M plus digits. Of the 219 status markers in that one file, zero would match. Resolving the plan source correctly and then parsing it to zero tasks is a worse failure than not finding it, because the fence's first assertion still compares ticket numbers against ticket numbers and passes. So a plan source declares its format, and the fence refuses by name a format it does not implement rather than parsing it to nothing. v1 implements exactly one format and says so.
The fence must stay hermetic in a fresh clone — the constraint that fixes the resolution rule
Placement is machine-local and uncommitted, so a fresh clone has none. A fence that required placement to resolve any plan source would fail on a machine that had never registered anything, which would make invariant 12 unenforceable exactly where it is most needed. The rule that resolves this: a repository that is its own plan repository is self-placed — the catalog beside the checkout resolves to repoRoot() with no placement consulted. AWSF's own project is that case, so the existing 38-ticket check runs unchanged and offline. A foreign plan source is checked only where placement locates it, and its absence is not a failure — another machine's clones are not this checkout's business. The asymmetry the fence already has is preserved: a ticket set with no resolvable plan is a hard failure; a plan with no ticket set is not, because AWSF did not author it.

What this fixture does not settle

Read, not run
This was a read of a real project, not an execution against it. Amendment Required Before the Build

Ordering gate G2 in the spine's Shared Invariants section: an invariant or protected-config amendment lands as an owner-approved commit before the workstream that depends on it starts building. No agent can write AGENTS.md — path-policy rejects protected-path independently of the write globs — and inventing an owner-authorized protected-change mechanism to route around it is the boundary working, not a bug to fix. Neither of the two amendments below is a task in this plan. They are stated here, with their sequence, so the build does not discover one of them as a refused write mid-task.

Why an amendment is owed at all, when the guarantee is not being weakened
Invariant 12's guarantee — a plan and its tickets never disagree — is unchanged and is strengthened by two new failure modes. But its text names two literal paths, specs/tickets/ and specs/awsf-plan.html, and task 20 moves v1's tickets to specs/tickets/awsf-plan/. After that commit the invariant's own text is false about where the thing it governs lives. An invariant whose text is false is worse than one that is merely narrow, so the text must land corrected before the move, not after it.

The amendment, written out so the owner commits text rather than an intention

Replace AGENTS.md item 12 with:

12. **A plan and its ticket set never disagree, and the pairing is resolved
    through the registered plan source rather than through directory
    adjacency.** Every ticket set belongs to exactly one plan. The plan's
    status markers are the source of truth; a ticket's `state` mirrors them
    and is flipped in the *same commit*, never a later one. A ticket's build
    prompt stays byte-identical to its build-prompts § Section B block — the
    tickets are a re-cut of that file, never a fork of it. A ticket set whose
    plan cannot be resolved is a hard failure, not a skip; a plan whose

    task coverage, milestone grouping, `state` against both the milestone

What the digest fence does not cover
It proves bytes at a declared path equal a declared digest. It does not prove the contract is correct; it does not prove the producer regenerated it after changing the thing it describes — the measured project's own producer-side check does that, and it is a different check; and it does not prove any consumer actually uses its copy. In the measured project the application could ignore its contract snapshot entirely and every fence here would stay green. It also assumes a contract is one file: a contract that is a directory, a generated set, or a pair that must agree structurally rather than byte-for-byte is outside v1 and is not smuggled in by treating the first file as representative.

DECIDED — APPLIED Q-A — Spine Questionable Q1: how this plan implements the content-addressed cross-repository contract, and what that costs

The decision, restated so it is not re-litigated here: the contract is an immutable, content-addressed artifact committed in each child repository; the parent coordination record names {child repository, contract digest}; a meta-test asserts each child's copy hashes to what the parent names. Taken by the owner on 2026-08-21. W04 owns the mechanism; the shape is settled.

How this plan implements it. The parent record is a contracts list in the committed catalog — durable, path-free, and the natural home for what Q2's own floor calls "the relationships between them". Each participating repository additionally commits awsf.contracts.yaml, a projection naming only the contracts it takes part in and the digest each must hash to. Two fences follow from that: a local one taking exactly one repository root, reading only that repository's projection and the files it names — the gate a child's worker phase runs — and a central one, awsf project verify, running over a resolved project and reconciling every projection against the parent record. M4's testing strategy watches all three drift modes go red.

Why the projection is forced rather than chosen — the part worth defending. Q1 requires two things simultaneously: the parent names the digest, and a child's gate reads its contract from inside its own worktree. A gate that fetched the digest from the parent record would have to reach into the plan repository — across exactly the boundary path-policy exists to hold, and the hole the parent-owned option was rejected for opening. A copy of the digest inside each child is the only shape satisfying both. It cannot live in that child's awsf.config.yaml, which is a protected-path no agent can write while a contract revision must be committable as ordinary work.

What it costs, stated plainly. The digest now has N+1 copies, not just the artifact. Q1 accepted N copies of the artifact and priced them at a meta-test; this implementation adds one copy of the digest per participant and pays for it with the central reconciliation, which is the only reason the extra copies are safe. Concretely: a contract revision now costs a new digest, an edit to the catalog, and a coordinated commit in every participating repository — one more file per repository than the decision's own description implies. That is the honest price and it is visible in M4's task 12. One alternative was considered and rejected: encoding the digest in the artifact's own filename, which removes the projection entirely and is content-addressing in the most literal sense. It was refused because every contract revision would then rename a file, changing every consumer's import path — churn on each revision in exchange for removing one small file, and an unstable path for tooling that has to find the artifact.

DECIDED — APPLIED Q-B — Spine Questionable Q2: how this plan keeps the catalog narrow and versioned, and what that costs

The decision, restated: the catalog stays narrow and versioned — plan repository, target repositories, per-repository default branch and gate commands. Config loading is refused, because it creates a precedence question between a project's config, the machine's config, and the committed awsf.config.yaml, which is a protected path no agent can write; a precedence rule letting a project config override it is a route around path-policy that needs no amendment to take. Taken by the owner on 2026-08-21.

How this plan implements it. awsf.project/v1 is a separate document with its own schema, its own loader and its own error hierarchy — never an extension of AwsfConfigSchema, never merged into it, and never consulted by loadConfig. There is no precedence rule anywhere in this plan because there are no two documents describing the same thing. The version is a required literal and an unknown version is a rejection rather than a best-effort parse, which is what "versioned" has to mean if it is to be worth anything later.

The consequence carried, so it is not mistaken for a gap. The catalog records per-repository gate commands and does not resolve them. Concretely, it stores the same {argv, timeout_seconds} shape awsf.config.yaml already stores, keyed by an id from KNOWN_GATE_IDS, and ResolvedProject.gatesFor(id) hands commandsPass a record it already knows how to consume. The catalog gains no resolver, runs nothing, and interprets nothing.

What it costs. The measured project has six checkable commands per repository where the recorded vocabulary has three. Narrowness is not free and this is where the bill arrives — a real repository's contract-drift check, seed-integrity check and migration check have nowhere to be recorded. Two mitigations, both honest: the contract-drift check is subsumed by Q-A's local fence, which does the same job through a different mechanism; and the remaining two are surfaced as Q5 rather than silently dropped or silently accommodated. A second, smaller cost: a project that would genuinely benefit from its own tuning cannot have it, and the workaround — a second awsf.config.yaml per repository — is the shape that already exists and is unchanged by this plan.

The framing error in the spine's Q2, recorded rather than hidden. Its third option bundled per-project worktree roots with state-root reach. Per-project worktree roots are in, in the machine-local placement layer, and this plan goes further on measured evidence — they are per-repository, because one project's two code repositories keep their worktrees on two different filesystems. State-root reach is out, and this plan's M2 makes the exclusion mechanical rather than merely intended. Neither half was ever open here and neither is treated as undecided.

Q1 — Does the catalog become a protected path, so no agent can rewrite it?

DECIDED 2026-08-22 Protect it. The catalog names each repository's gate commands and the set of repositories the project consists of. An agent that can rewrite its own gate commands can disable its own gates, and an agent that can add a repository can widen the project's reach — both without touching a single line of the policy that was supposed to bound it. That is precisely the boundary-erosion pattern risk R1 names, arriving as a convenience. The cost is real and small: every catalog edit becomes an owner commit, and catalog edits are rare by construction because the catalog is narrow. Note the ordering consequence if this is taken: adding awsf.project.yaml to policy.protected_paths means editing awsf.config.yaml, which is itself protected — so it is a second owner-authored commit under gate G2, landing before the build. The case against: a growing project adds repositories, and every addition becoming an owner ceremony is friction that will eventually be routed around — and a boundary people route around is worse than one that was never claimed. If that is the owner's read, the honest alternative is to leave it writable and say so, rather than protect it and quietly grant exceptions later.

The consequence this decision carries, found while applying it and not visible when the option was written. path-policy matches protected_paths globs against a path, independently of whether the file exists — so protecting awsf.project.yaml rejects creating it just as firmly as editing it. Task 10 is the task that creates this repository's catalog. The protected-config amendment therefore lands after task 10, not before the build, which is the reverse of the ordering gate G2 normally imposes and is stated here so it is not discovered at task 10 as a refused write. The invariant 12 amendment is unaffected and still lands before task 16. Both are recorded in Amendment Required Before the Build, now with their sequence.

Two further consequences, so the decision's reach is legible. Every later catalog edit is an owner commit — including the fields W05, W07 and W08 will each want to add, so those three workstreams inherit an owner act they would otherwise have discovered themselves. And the contrast with Q-A's projection is now load-bearing rather than incidental: the catalog is protected because rewriting a gate command disables a gate, while awsf.contracts.yaml is deliberately not protected because a contract revision must be committable as ordinary work in every child. Two files, one repository, opposite answers, and each for its own stated reason.

Q2 — Where does the catalog live, and what happens to a project that has no plan repository yet?

DECIDED 2026-08-22 The plan repository's root, exactly one per project. It is the one repository a project with a plan is guaranteed to have; it is the repository whose whole role is already cross-cutting description; and it makes the schema's "exactly one role: plan" rule and the file's own location agree, which is what the self-placement rule in M5 depends on. One copy per repository is the option to avoid: it turns a single description into N copies with no reconciliation, which is exactly the drift Q-A had to build a fence for and would be a self-inflicted second instance. In the state root makes the catalog machine-local, which destroys its whole purpose — it must travel with the project. The genuinely open part, which is why this is a Questionable at all: a project created by awsf init has one repository and no separate plan repository, so its single repository carries role: plan and holds the catalog. When such a project later grows a second repository, the catalog stays where it is and the original repository keeps role: plan — meaning the plan repository is decided at registration and moving it later is a manual migration this plan does not automate. That is a real limitation and the alternative is a mechanism nothing yet needs.

Q3 — How does the fence handle a plan whose markup grammar it does not implement?

DECIDED 2026-08-22 Declare the format in the catalog and refuse an unimplemented one by name. This is the option grounded in a measurement rather than a guess: the fence's grammar requires Milestone M<digits>, and the owner's real plan writes Phase 24.5 — a different noun and a decimal ordinal. Of that file's 219 status markers, zero would match. The failure mode being prevented is worse than a missing check: resolving a plan source correctly and then parsing it to zero tasks leaves the fence comparing ticket numbers against ticket numbers, so parts of it pass while asserting nothing. A declared format turns that into a named refusal. Generalising the grammar is cheaper today and is guessing at the shape of every plan format that will ever be registered — and it would have hidden this very finding rather than surfacing it. Both is the worst of the two: a generalised grammar that silently half-matches a foreign plan is exactly the vacuous pass the declaration exists to prevent. The cost of the recommendation, stated: v1 implements one format, so any project whose plans use another grammar gets a refusal rather than a check — a visible gap instead of a hidden one, which is the trade being proposed.

Q4 — Does this workstream align TicketSchema with the sync fence's already-decided vocabulary, or name the gap and defer?

DECIDED 2026-08-22 Leave it alone, and name the gap precisely. The two have already diverged, deliberately and on the fence's side: the fence accepts Wnn ids and treats tier and workflow as optional, while TicketSchema requires ^T[0-9]{2}$ plus six fields the v2 ticket sets omit. The gap that is left after this workstream, stated so it is not discovered later: awsf ticket list --plan awsf-plan returns v1's 38 tickets exactly as today, and a v2 spine set returns nothing because TicketStore.load() filters on Tnn by filename, while a v2 deep-plan set would return records the store reports as invalid, since it deliberately exposes retained files it cannot validate rather than hiding them. Why not fix it here: widening the id pattern without also relaxing the six required fields makes the second case worse — nine clean empty results become nine invalid-file reports — and relaxing all six touches awsf ticket new, awsf ticket refine, the backlog query and the dashboard's ticket view, which is a blast radius this workstream has no reason to absorb while it is also redefining an invariant. The case for aligning now: the divergence is already load-bearing and every month it stays makes the store less able to see the plans the factory actually runs on. That is a fair argument and the reason this is a Questionable rather than a footnote.

Q5 — The measured project declares six checkable commands per repository where KNOWN_GATE_IDS has three. Does the vocabulary widen?

DECIDED 2026-08-22 Record only the three. commandsPass joins on gateId against host-generated evidence and asserts argv exact; an id with no consumer is a recorded command nothing runs, which is precisely the decorative outcome Q2's own consequence warns against. Two of the measured project's three extras are project-specific integrity checks that AWSF has no contract for and would be asserting on evidence it cannot interpret. The third disappears rather than being dropped: the backend's contract-drift check is doing Q-A's job by another route, so the local digest fence subsumes it and no new id is needed. Widening KNOWN_GATE_IDS means inventing a taxonomy to fill a field — the exact thing the ticket-authoring convention forbids — and every new id needs a consumer before it means anything. Free-form ids in the catalog only is the worst shape: two vocabularies for one concept, one of them unchecked. The cost: a real repository's full check set cannot be described here, so the catalog is a partial description of how that repository is verified, and a reader must not mistake it for the whole. That belongs in the catalog's own documentation and is called out in Notes.

Q6 — Does awsf project register discover clone locations by probing the filesystem, or must the owner state each one?

DECIDED 2026-08-22 Require an explicit path per declared repository; probe nothing. Placement is the layer where a wrong value silently sends work to the wrong tree, and a probed value is one nobody stated and therefore one nobody can be held to. The measured project makes the hazard concrete: its directory names, declared aliases and remote names are three different strings, one remote carries a spelling error the directory does not, and two of its repositories have no remote at all — so any probe matching on name would mis-associate at least one repository, and any probe matching on remote would fail on two. The case for probing is genuinely strong on ergonomics: a six-repository project means six flags, and git worktree list would find the split worktree roots this plan had to discover by hand. If the owner prefers it, the third option is the safe form — probe and print what was found, then require the operator to pass those values explicitly — because it keeps the ergonomic win without letting an inference become a durable record. The recommendation stays at "state it" for v1 on the grounds that the cheapest thing to add later is convenience, and the most expensive thing to remove later is a silent default.
