In Plain Language

This section explains the whole plan without technical vocabulary. Everything after it says the same things precisely, for the people — and machines — building it.

What this is about

You use AI assistants to write software for you, and you have built two different systems to manage them. The first one is a strict supervisor: it has a rulebook that says exactly which step may follow which, it refuses every shortcut, it cannot start an assistant without writing that down first, and nothing joins your real project until you personally sign for it. The second one — inspired by another engineer's factory you studied on video — is a glass-walled workshop: you can watch every worker on one webpage while it happens, see what each step did, what it checked, how long it took, and what it cost, down to the cent.

Each one is missing exactly what the other has. The supervisor is blind: between "work started" and "work finished" you cannot see anything happening, and its safety equipment silently stops working the moment you move it off the one kind of computer it was built on — it would tell you "everything was cleaned up" without ever having looked. The glass workshop has no rulebook: nothing stops work from skipping steps, nobody has to sign before work is accepted, and — the deal-breaker — it can only talk to one of your three AI subscriptions. The one you value most, it cannot reach at all.

Why merge them, and why now

You are about to change machines: a new Mac laptop is coming and a Linux desktop is planned, alongside the Windows machine you use today. The supervisor's silent-failure problem stops being theoretical the day you copy it onto the Mac. And you are about to do bigger work, where "I can see what every assistant is doing and what it costs" stops being a luxury. So instead of patching either system, this plan builds one new factory — AWSF — that keeps the supervisor's rulebook and the workshop's glass walls, and fixes the known defects of both while the walls are open.

The factory, as a factory

Picture one building.

  • The rulebook is bolted to the wall. A fixed list says which step may follow which — ten stations, and every allowed move between them written down. Every forbidden move is also written down, with the exact reason the factory gives when it refuses. The rulebook is a machine, not a person: it cannot be argued out of anything.
  • Every worker clocks in before touching a tool. The factory physically cannot start an assistant without first writing its name in the logbook. If the note cannot be written, the worker never starts. If the building loses power halfway through hiring, no half-hired worker is left wandering — that is tested by deliberately cutting the power.
  • The glass wall shows everything. One webpage: a card per job, a colored dot-trail per worker, the money and time counters, and a step-by-step log. The page can look but never touch — there is deliberately no button on it that approves, cancels, retries, or changes anything. Looking is safe; touching happens only at your keyboard.
  • The logbook is the truth; the display is a copy. If the display's records are ever damaged or deleted, they are rebuilt from the logbook, identically. Losing the display loses nothing.
  • The quality bench measures the actual part. Your real tests run against the exact finished work, by machine, outside any assistant's control. Failures go back to the same worker at the same bench — cheap, because that worker still remembers the job — before anything more expensive happens.
  • You sign at a real desk. Accepting finished work into your real project happens only when a human types the command in a terminal. There is a waiting room with no clock: work waits for you forever, and no timer may ever throw it out.

What using it will actually feel like

You type one short command describing the job and which assistant should do it. The factory sets up the sealed copy, writes the worker into the logbook, and starts it. You open the webpage: a new card appears with the job's name, a dot-trail per worker growing in real time, a step log scrolling on the right, and three small counters — money, time, and volume of words processed. When you have three jobs running, you have three cards, and a glance tells you which is building, which is testing, and which is waiting for you.

When the work passes its tests — and, for risky jobs, after the other company's assistant has written its opinion — the card turns into a summary: what changed, what was checked, what the second opinion said, and the exact command to type if you accept it. You type that command in a terminal; the factory double-checks everything one last time and folds the work into your real project. If you do nothing, it waits. If you decline, the work is kept exactly where it is. Nothing in this factory ever deletes anything automatically.

Using both AI companies on purpose — and who picks

You pay for two working subscriptions — Claude, and GPT through the Pi tool — and each has its own monthly allowance. Either company's assistant can do the building work, and you choose which one, per job, when you start it. The program never chooses for you, and one rule sounds pedantic but is load-bearing: the factory is forbidden from picking an assistant because the other one is running low. "I picked GPT for this job" is a judgement about who fits the work; "the program picked GPT because Claude was at 80%" is a budget decision wearing a judgement's clothes, and a month later you cannot tell which jobs got the right worker. If the assistant you chose is unavailable, the job stops and tells you — it never quietly swaps.

The second opinion on risky work always comes from the other company — two assistants from the same company tend to make the same mistakes, so an opinion from the same house is worth much less. A pleasant side effect: sending building work to one company automatically sends reviewing work to the other, so your two allowances balance themselves without any scheduler.

Your third subscription — Google's — gets a reserved parking space in the design. But its door stays closed and marked "not verified" until someone actually starts it once and reads what comes out. This factory does not build around equipment nobody has switched on.

How you will know it worked

  • The pull-the-plug test. Kill the factory at the exact worst moment, between "worker hired" and "worker started" — no ghost process survives. On every machine.
  • The delete-the-display test. Delete the webpage's database mid-week, rebuild it with one command, and every screen comes back identical. The old file is kept, not thrown away.
  • The waiting room has no clock. Work waiting for your signature waits forever. No timeout may ever move it.
  • The money labels never lie. A Claude job says "— subscription", never "$0.00". An estimate says it is an estimate. A total mixing known and unknown costs says "partial".
  • The webpage cannot act. A test literally reads the list of things the webpage's server can do and fails if an accept, cancel, retry, or settings-change action ever appears on it.
  • Nothing is ever deleted automatically. Not work, not records, not sealed copies, not even the replaced database file.

What is deliberately not being built

No AI manager, AI inspector, or AI repairman — the rulebook, the bench, and a diagnosis command are machines, not conversations. No automatic restarts. No background watchers. No paperwork pipelines that generate reports about reports. No way for the webpage to change anything. No sending your work anywhere — the factory cannot even push to the internet; that ability simply is not built. These are not postponed features: removing that machinery is the point, because most of it existed to catch problems the machinery itself created.

The one-paragraph version
Merge your two systems into one factory: the strict supervisor's rulebook — ten stations, every move written down, workers who cannot start without clocking in, and your signature required at a real keyboard before anything joins your project — behind the glass wall of the workshop you admired, where one webpage shows every worker, every check, and every honestly-labelled cent, live. Let either AI company build, chosen by you and never by whoever has allowance left; let the other company give the second opinion on risky work. Build it in nine milestones — rulebook first, permanent records second, the dangerous start/stop machinery third and most carefully, real assistants only after pretend ones prove the plumbing, and the webpage near the end because it only watches. Prove every safety property by deliberately breaking things: pull the plug, delete the display, kill workers mid-job. Then run two real jobs, count what they cost, and only claim "it works on the Mac" after it has run on the Mac.

Purpose

Build AWSF — a single-operator agentic software factory that fuses the two working systems: my-agentic-workflow's deterministic control plane (guarded state machine, PID-before-spawn barrier, human-TTY-only landing) and super-simple-software-factory's observable execution pipeline (typed phases, runtime-validated envelopes, postcondition gates with same-session corrections, live SQLite-backed dashboard). One sentence governs the fusion: the state machine governs the task; the phase engine governs the sojourn inside the executing states (awsf-architecture-proposal.md §7.1).

The target is TypeScript on Node ≥ 22.12, two npm workspaces (core/ with no build step under native type-stripping, dashboard/ as Vue 3 + Vite), a pinned dependency allowlist enforced by a meta-test, and roughly 11,000–15,000 production lines plus 10,000–15,000 test lines. This plan decomposes the accepted architecture into nine milestones and thirty bounded tasks, each sized for one worker in one fresh session, each with explicit entry conditions, outputs, proofs, and stopping criteria.

Problem

Both parent systems work, and neither is sufficient. The defects below were verified read-only in the actual repositories at the cited lines on 2026-08-04; they are the concrete reasons a fusion is being built rather than either system extended in place.

MAW — a control plane that is blind and non-portable

  1. No observability layer. Between RUNNING and GATING the operator sees a one-line heartbeat at most. There is no per-phase trace, no event log, no cost/usage surface, no live view of tool activity. MAW has nothing to project into — no equivalent of SSSF's seven-table trace exists anywhere in src/.
  2. No typed inter-phase contracts. Worker output is a RESULT line parsed by prefix from stdout (run.mjs:122); there is no schema, no validation, no retained invalid payload, no typed handoff between phases.
  3. Process supervision is Linux-only and fails silently elsewhere. processGroupMembers() returns [] when process.platform !== 'linux' (run.mjs:19-24), so on macOS every cancellation reports "no survivors" without having looked. MAW's own README calls this out as the single most important thing to test on the destination machine (README.md:72-75) — the defect class this whole redesign exists to eliminate.
  4. Prompts ride process arguments. claudeCommand() appends the prompt as the final argv element (providers/claude-code.mjs:6) — visible to every process lister, subject to OS argv length limits, and a leak channel. Prompts must travel on stdin.
  5. No durable landing state. Landing goes AWAITING_OWNER → LANDED in one step (state.mjs:127); a crash mid-fast-forward leaves a world that is neither. Recovery is a guess, and this system forbids guessing.
  6. Acceptance records can be written into the canonical checkout after landing — a post-landing mutation of the thing gates already signed off on.

SSSF — an observable pipeline with no spine, locked to one provider

  1. Cannot reach Claude Pro at all. Config validation rejects any agent whose coding_agent != "pi" (agents.py:61-63), and Claude Pro cannot be used through Pi. Santiago's most valued subscription is structurally unreachable; the default model is google/gemini-3.6-flash (sssf.config.yaml:5).
  2. No state machine and no spawn barrier. Phases run in whatever order a script calls them; nothing refuses an illegal sequence, nothing registers a PID before a process exists, and there is no human gate anywhere — work lands on the active branch with no worktree isolation.
  3. diff_matches_claims checks one direction only. It verifies every claimed file exists (gates.py:61-68) and never notices a file the agent changed and did not report. The gate's own name promises set equality; it delivers a subset check.
  4. Permissions are enforced only after mutation. The change-set fingerprint comparison (permissions.py:50-75) is excellent — it caught a real agent running git checkout to revert the quality check judging it (permissions.py:5-8) — but it is the only layer; there is no worktree, no OS sandbox, and the write has already happened by the time it is seen.
  5. The trace schema has no version marker and no indexes. Additive ALTER migrations with no user_version (tracer.py:92-99) force the read side to probe PRAGMA table_info per table (db.ts:97-120); with no indexes, every 500 ms dashboard poll is a full scan.
  6. tracer.event() has no error boundary. A locked or corrupt SQLite file aborts the running phase — observability can kill the work it observes, the exact inversion of "the journal is truth, the DB is a copy".

Solution

One system, six pillars, four load-bearing fusion decisions — all settled in awsf-architecture-proposal.md and treated as immutable by this plan.

The four fusion decisions

  1. Two-tier correction economics with reservations. Intra-phase corrections re-prompt the same provider session — context intact, cheap, and they do not consume tier calls (SSSF's insight, agents.py:107-110). Only an exhausted phase escalates to a state transition, which is counted, rationed, and evidence-gated (MAW's insight, state.mjs:118). Calls are reserved before launch, converted to spent on GO, released if registration fails; spend carries across attempts.
  2. Spawning centralized in a host TransportBroker. Adapters build pure ProcessSpec descriptors and parse streams; they may not import node:child_process or call fetch — enforced by an architecture test. An adapter that can spawn can bypass the barrier, so no adapter can spawn.
  3. LANDING is a persisted state. A crash mid-fast-forward recovers unambiguously or blocks; it never guesses.
  4. One language, one runtime, two workspaces. The highest-severity defect in the current stack is portability, and portability is a process-supervision problem solved once, in one place, contract-tested per machine.

Trust boundaries

  • Host code is trusted. It owns transitions, spawning, Git, gates, and landing.
  • Model output is untrusted data. Envelopes are parsed, size-capped (256 KiB), schema-validated, path-normalized and containment-checked; invalid ones are retained with violations, never repaired silently.
  • Provider streams are untrusted input. Line-framed with per-instance decoders, sequence-numbered by the host; provider timestamps advisory; provider tool IDs never reach a normalized event (the host mints t1, t2, …); unrepresentable model identities fail closed (E_MODEL_UNRESOLVED).
  • The dashboard is a read-only consumer on a readonly SQLite connection, loopback-only, with exactly one write (archive flag). Its absence — even its corruption — may never affect a task beyond the degraded-observability hold at GATING.
  • The human is the only landing authority. AWAITING_OWNER → LANDING demands an interactive TTY; every other route to LANDED throws HumanGateBypass.
  • Credentials cross no boundary. Env is an allowlist (PATH, HOME, TMPDIR + injected locale pins); an allowlisted key holding credential-shaped bytes is a hard E_REDACTION error (launch.ts:44-62); journals, SQLite, API responses, and fixtures are credential-free by meta-test.

Spawn sites — five edges, and only five
L4, L10, L11, L16, L19 — precisely the edges entering RUNNING or REVIEWING. Any other pair attempting a spawn raises IllegalSpawnSite. Each spawn consumes a reservation made before launch, converted to spent on GO, released if registration fails. MAW's three-site rule (run.mjs:9) generalizes here because AWSF adds the owner-rework edges; the closure "spawn ⇔ entering an executing state" is what makes the rule testable rather than enumerative.

L21 is deliberately narrow. AWAITING_OWNER has no timeout, so no clock may produce this edge — only a corrupt record or an unreadable worktree, exactly as MAW enforces today (state.mjs:55-60). A task waiting on the owner waits forever; that is the point.

L16 requires a concrete defect. A style note is not a defect: if it authorized re-work, "the reviewer had opinions" would be indistinguishable from "the code is wrong" (state.mjs:89-95). This is why ReviewFinding carries severity — SSSF's review envelope has no such field, which is why SSSF cannot express the rule.

Validation and parse-retry

  • Final assistant content must be exactly one JSON object; prose and code fences are rejected — the parser strips fences and takes the outermost {…} before rejecting.
  • Maximum envelope size 256 KiB. Unknown fields rejected. Paths normalized and containment-checked against the worktree.
  • ≤ 2 JSON fix attempts, in the same session, sharing the correction allowance.
  • Invalid envelopes are retained with their violations so the trace shows what the model actually said. Valid envelopes are written immutably to disk, appended to the journal, then projected.
  • Downstream phases receive validated payloads by host rendering into {previous_envelope} in the compiled prompt — never via conversational memory.

Why a permission breach is not a gate violation
A gate violation is work an agent can be asked to redo; a breach cannot be corrected by re-prompting because the write already happened (permissions.py:23-25). A breach aborts the phase and names every offending path. The mechanism — fingerprint the working tree's change-set before the agent runs, compare after (permissions.py:50-75) — catches what a write-watcher misses: an agent that runs git checkout to revert a file it was being judged by. That is not hypothetical; it happened to SSSF's author (permissions.py:5-8). AWSF keeps this as the last of seven layers (managed worktree · clean start · adapter tool allowlist · OS sandbox where available · post-run change-set comparison · exact write-glob enforcement · canonical repo outside the sandbox root), not the only one. And two configuration rules learned the hard way carry over: tools is a capability list, not a sandbox — writes is the enforced statement; and --tools filters extension tools too, so an agent whose harness extension registers a tool must name it or the tool is silently filtered out. writes: [] restricts the repository, never the session runtime — every agent can always write its own report under the attempt directory.

Observability Contract

The pipeline, end to end — every stage host-owned, every stage bounded:

Projection-failure policy — degraded mode

A projection failure never kills a running model
It emits a sqlite-projection-failed notice, marks the session observability_degraded, and the run continues — the journal already has the event. But the attempt may not advance past GATING while degraded; the CLI reports it loudly and awsf db rebuild must succeed first. Truth is preserved, invisible completion is impossible, and no provider is ever killed for a dashboard's sake. (Contrast SSSF, where tracer.event() has no error boundary and a locked DB aborts the phase.) If projection fails before provider release, the provider simply never executes — that is the barrier working.

Tool-call folding and token accounting

  • tool.requested creates one projected tool_call row in running; updates do not create rows; tool.completed updates it with result snippet, duration, and outcome. The canonical journal retains request and completion separately.
  • Context occupancy is not a sum: it is occupancy after the last turn, while spend accumulates across all turns. The two dashboard numbers are different on purpose.
  • persist_thinking_text: false is not a setting to flip lightly — it is invariant 9 (thinking streamed, never persisted).

idx_events_cursor is the load-bearing index: the poll query is WHERE session_id = ? AND event_row > ? Migrations, concurrency, and the rebuild guarantee

  • Migrations: numbered SQL files plus PRAGMA user_version, each applied in BEGIN IMMEDIATE. Startup refuses a database newer than the binary — the explicit fix for SSSF's marker-less additive ALTER list (tracer.py:92-99) that forces its reader to probe PRAGMA table_info on every request (db.ts:97-120). Migrations never rewrite canonical journals and never invent missing usage, cost, or model identity.
  • Concurrency: one writer per workflow process; the API reads on a readonly: true connection with every query a SELECT, except the single archive write on its own lazily-opened connection.
  • Rebuild guarantee: awsf db rebuild writes a fresh DB from journals and atomically swaps it after validation; the previous file is retained, not deleted; every dashboard view over the rebuilt DB is byte-identical to the pre-deletion state — an M2 acceptance test, not an aspiration.
  • Driver boundary: node:sqlite sits behind observability/sqlite.ts with a startup feature probe, so its relative youth is contained and a corrupt DB is disposable by design.

Explicitly Not Built

These are removals, not postponements, and meta-tests fail if any grows back. The reasoning is counter-intuitive and worth stating once: most of the removed machinery existed to detect problems that the machinery itself created. The pilot's watchdogs patched the timing races of its own coordinators; its receipts triggered verifier relaunches against unchanged product; its doctor diagnosed states its orchestrator had corrupted. Remove the machinery and the problems it was catching stop happening. What genuinely protected the work — isolation, real tests on the real result, explicit human approval, never deleting anything — is all kept, and it was never the expensive part.

  • LLM orchestrator, supervisor, or doctor agent — diagnosis is a deterministic read-only command
  • Automatic restart of any model process — BLOCKED is a resting state
  • Background monitors or watchdog daemons
  • Receipt/manifest/digest pipelines — Git and the journal are the evidence store
  • Any dashboard write path to the lifecycle — no landing, approval, retry, cancel, or config-mutation route, asserted by meta-test
  • WebSockets or any push transport — cursor polling only
  • Any push implementation — landing is local fast-forward only
  • Automatic deletion of anything — worktrees, attempts, logs, DB files; awsf gc lists only
  • Provider fallback or substitution — a failed declared route blocks
  • Quota-aware routing — the runner never picks a provider by remaining allowance
  • Shell parsing — executable + argv array, shell: false, structurally
  • Conversational evidence — no transition may cite terminal text, checklists, or markers
  • Non-loopback dashboard binding (out of MVP; would require an explicit one-use bearer token)
  • Persisted chain-of-thought — reasoning counts only, never content

Rejected alternatives — and why they stay rejected

  • Python (extend SSSF). Its own code is pi-only (agents.py:61-63) — adopting the runtime means rewriting its entire provider layer anyway, for a stack that cannot reach the most-valued subscription.
  • Hybrid Python + TS. The envelope schema defined twice will drift; SSSF already invented shared/types.ts to stop exactly this — extend the idea one hop and the second runtime disappears.
  • Zero-dependency core with a hand-rolled validator. The schema must be machine-emittable as JSON Schema for prompt injection; a bespoke validator would grow that capability badly. The discipline survives as a pinned, meta-tested allowlist instead.
  • PLANNING/BUILDING/DOCUMENTING as lifecycle states. They are phases; promoting them makes the matrix workflow-dependent and untestable.
  • PREPARING/READY split. A transient distinction that adds an edge class without adding a guard — collapsed into PREPARED.
  • Adapter-owned spawn(). An adapter that spawns can bypass the barrier; the broker centralization is the single most important structural correction in the fusion.
  • WebSockets. Cursor polling matches SQLite insertion order, serves live and history through one mechanism, survives restarts, and works after the workflow process exits.
  • Hard LOC caps as CI failures. The old 1,500-line cap began producing homemade YAML parsers and line-compression tricks; fitness functions catch real defects, budgets stay advisory.
  • Native Windows write support in v1. Claiming suspended-process parity without a native helper would be exactly the quiet-failure pattern this plan exists to kill.
  • Twelve workflows. Six cover the real use cases; each addition is demand-driven.
  • An orchestrator/ directory. Naming a directory that is how one grows back.

Five judgment calls the plan left implicit, recorded here rather than buried in the code:

  • Fence and prose salvage succeeds; it does not fail. The contract reads "prose and code fences are rejected — the parser strips fences and takes the outermost {…} before rejecting", so salvage is attempted first and only a payload surviving neither path is rejected. The parse result records extraction: "exact" | "fence-stripped" | "outermost-object", so the phase engine can tell "the model emitted clean JSON" from "the host had to dig it out" at the moment it decides whether to spend a parse-retry. It is not carried onto StoredEnvelope: that interface is normative and this task does not widen it, and the verbatim output is retained at rawOutputPath regardless, so nothing about what the model actually said is lost. The outermost-object scan is first-{-to-last-} and deliberately not brace-balanced: anything cleverer starts guessing which of several objects the model meant, and a wrong guess is worse than a clean rejection the model can be re-prompted about.
  • The 256 KiB cap is measured in UTF-8 bytes, by a hand-written utf8ByteLength(). TextEncoder has no type declaration under lib: ES2023 without @types/node (outside the D2 allowlist), and a cap that silently measured UTF-16 code units would let a multibyte payload sail straight past it. A test checks the hand-rolled counter against the platform encoder across BMP, astral, and lone-surrogate samples.
  • The wire/stored split is asserted mechanically, not merely documented. HOST_OWNED_FIELD_NAMES enumerates every StoredEnvelope field in both camel and snake case — the one exception being the wire envelope's own schema literal, which the model must emit — and a test asserts that no phase envelope schema declares any of them, plus a second test asserting the deny list has not fallen behind the wrapper it guards. So a future envelope cannot quietly start asking a model to echo its own phase_id.
  • Artifact-path containment is a schema pattern, not only a gate. Absolute POSIX, drive-letter and UNC paths, backslash separators, .. segments, ./ prefixes and doubled separators are rejected structurally, so the rule travels with the emitted JSON Schema into the agent's own prompt instead of only firing after the fact. Containment against the real worktree root stays a gate concern; this is the structural floor beneath it. The rule is applied to every declared path field in every envelope — ArtifactClaim.path, both changedFiles, documentedAreas.documentPath, ScoutOutput.findings.file, ReviewFinding.file, and PlanOutput.implementationSteps.files. The first pass applied it to only four of the seven, leaving review findings and plan step files as bare strings, so the same traversal path was rejected by one envelope and accepted by another; a regression test now pins all of them together.
  • Tool-settlement and sequence invariants live here, as a pure checker. validateEventSequence() reports contiguous seq, exactly one terminal and it last, no settlement without a request, no double settlement, no reused id, and — the load-bearing one — no tool still open at any terminal, run.cancelled included, since cancellation settles open tools first. It returns every violation rather than throwing on the first, so a trace can show the whole picture of what a parser got wrong. T16's event sequencer implements against it.
