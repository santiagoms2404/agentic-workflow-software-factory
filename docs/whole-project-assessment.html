01

Executive assessment

Keep the foundation. Turn restored acceptance into useful delivery.

ELI · The short answer

AWSF helps agents build software while the owner keeps important decisions. The final recorded full test run passes, and follow-up checks confirm several repairs that were previously missing. Some weaker protection and recovery paths remain. Keep human control, finish the specific remaining checks, and demonstrate a useful tool that the owner can improve and keep with less effort.

AWSF has a coherent engineering purpose: turn an authorized request into checked, reviewable code while keeping lifecycle decisions in host software and landing authority with the owner. The whole-project review found genuine holes in that design’s implementation. The response closed many consequential ones, including ambient credential inheritance by quality commands, prompt-file overwrite hazards, stub evidence crossing into real landing, unvalidated publication output, and process failures that could crash or indefinitely stall the host.

The evidence now supports restored acceptance as well as meaningful mechanism repairs. The final archived npm test at 057370d records 5,521 passes and no failures. Source inspection and fresh checks confirm that plan-author routing, interrupted visual-frame delivery, owner correction authorization and production contract checking have materially changed. The earlier report’s 51 failing test occurrences describe 1a5ccea, not this revision. The closeout accurately distinguishes classification from repair. Remaining concerns include a reproducibly weak non-OS seed fingerprint, incomplete recovery guarantees, two unresolved original mechanisms and some unreconciled evidence. None establishes an observed production compromise.

D1 · Continue bounded use

Keep the single-owner, local, human-landed model. The command, permission, provenance and journal boundaries are valuable infrastructure.

D2 · Hold expansion to evidence

Preserve the restored acceptance baseline. Resolve the remaining seed-assurance, CI/gate-budget and evidence gaps before broader autonomy or supported-surface claims.

D3 · Prove useful delivery

Use the owner’s eventual Q5 task to demonstrate creation, feedback-driven improvement and retained reuse, including the human work each step requires.

03

The intended vision

A personal environment that keeps useful things.

ELI · The bigger idea

The goal is a personal AI system that helps you make useful tools, improve them and keep using them under your control. AWSF is the software-building part of that system. It does not yet prove the complete experience, including the everyday interface, running your tools or keeping them usable when services change. Smart Health is one possible application, rather than the whole product.

The owner’s intended product is a personal AI environment that a customer controls and can continue using. It should remember permitted context, accommodate supported models, help create and adapt useful tools, preserve the results, and connect to separately governed shared spaces or devices when authorized. Its value comes from what a person can accomplish and retain over time. More agents, more generated code or more stored interaction are not themselves evidence of improvement.

That direction is explicit in SRC9, SRC11, SRC12, SRC23–24 and SRC36. The earlier wellness framing was corrected by the owner. Smart Health is one application, not the definition of the platform. Q5/SRC16 accepts a create–improve–retain demonstration while leaving its concrete task to the owner. Choosing a convenient fixture, retail scenario or health example here would incorrectly turn an illustration into a product commitment.

From a need to a capability worth keeping

The intended journey is intelligible: express a need through Marimba or the workspace, establish context and authority, compare reuse with new creation, let an agent carry out permitted work through AWSF, inspect meaningful checks, obtain the required activation or release approval, use the result, improve it from feedback, and retain the useful version without inheriting somebody else’s private data or permissions. SRC15–16, SRC36, SRC44–46 support that chain. Its end-to-end implementation has not been demonstrated in this repository.

AWSF’s strongest contribution is in the middle: constrained execution, structured evidence, candidate-specific checks and human authorization. Durable customer ownership sits beyond a local Git repository. Cancellation of a service must still leave the supported local system and permitted data usable under Q2. That needs installation, dependency, licensing, model-availability, recovery and maintenance evidence. No count of landed code changes proves those outcomes.

The benefit is coherent, but the commercial and operational promise is not yet bounded. Personally generated software can remove an unwanted subscription while creating a maintenance obligation. A local model can reduce external dependence while lowering task success. Optional hardware can widen usefulness while multiplying support and safety obligations. The right proof is a named configuration and a meaningful retained result, not the assertion that future models will remove these costs.

Keep the full vision intact while testing a small part. The first demonstration should be representative enough to reveal approval, recovery and reuse costs, but should not silently redefine the platform around one app. Model training, a marketplace, a replacement source platform and custom hardware need separate value evidence. Q3’s license recommendation remains provisional, and the data strategy grants no collection, training or sale rights.

ELI · Does a feature help someone?

For each feature, ask who needs it, what they should be able to do and what would prove it worked. Safety checks and saved history help, but their value should reach a real person finishing and keeping useful work. More screens, models or agents are not enough by themselves. Running applications, shared access and device safety also need work beyond AWSF’s software-building role.

A capability is aligned when it enables an accepted outcome for an identifiable person and has a credible path to evidence. Necessary infrastructure need not be disguised as a customer feature. The permissions and journal work is justified by preventing unauthorized or untraceable changes. Its product value becomes visible when a person can safely finish, recover and keep useful work.

07

Whole-project critique

Good boundaries need usable recovery.

ELI · The main engineering trade-off

The design has useful rules for who may act, how programs run and how decisions are recorded. Many repairs strengthen those rules. But stopping safely when something goes wrong is only half the job. The owner also needs a clear way to continue without losing work. The key unanswered question is whether all these checks save more human effort than they create.

W1 · The architecture has a defensible center

The separation between pure state decisions, controlled process execution, append-only evidence and rebuildable SQLite projections is appropriate for a local factory that must explain what happened. Centralizing subprocess creation, pinning host-created candidates, separating landing from publication and forbidding model-emitted owner acts constrain failure propagation. The narrow dependency allowlist also keeps the runtime surface understandable. These are strengths worth preserving because they make authority and evidence inspectable.

Enforcement is less uniform than the architecture’s prose. Code fences are finite syntactic checks. Candidate-authored quality commands run outside phase filesystem isolation. The non-OS seed fallback is weaker than its recovery consumer assumes. These do not erase the architecture’s value, but they require explicit assurance levels rather than one general “sandboxed” or “safe” label.

W2 · The original review mostly found the right boundary failures

The review’s strongest work was concrete and consequential: credential propagation, mutable gate tooling, prompt-file redirection, missing review/stub distinctions, post-push validation, lost output, cancellation and journal edge cases. Its reproduction-oriented framing justified prioritizing these before stylistic cleanup. Merged H/M clusters correctly recognized that several B-series records shared one mechanism.

Its prioritization was less consistent at the integration layer. B3-22’s missing owner-spend operation affected availability, not merely tidiness. The B6 ledger mistakes show how a large numbered inventory can lose the original mechanism. The final closeout corrected two of those mistakes with real repairs and explicitly distinguishes classification from resolution. That is a substantive improvement over its earlier handoff. B6-05 and the wall-clock duration concern still require attention. Contract checking, previously an unused helper, now has a pinned host-authority path and production-gate tests.

Some review conclusions needed owner clarification rather than code changes. O2’s permission to release exact host-owned lock files and O5’s shipped-code scope for subprocess restrictions are legitimate refinements. O1’s exact historical attribution exemption preserves evidence instead of rewriting history. Declining an unneeded abstraction or a supported-scope change can also be correct. It would be unfair to treat every wontfix as an unresolved bug, or to retroactively demand the later multi-user physical-platform vision from the original factory.

W3 · The remediation improved containment faster than availability

Many new refusal paths are the right integrity choice. A system should stop rather than append after a torn journal or authorize a phase from uncertain evidence. But repeated owner-assisted repair can make a theoretically safe factory impractical. A recovery claim needs the interrupted operation, preserved evidence, legal next step and eventual useful result. The present evidence demonstrates more of the first three than the last.

The same distinction applies to publication and closure. Separating local landing, remote publication and plan bookkeeping is coherent. Allowing closure after PUBLISHED without reconciling the sealed-state language increases the number of policy exceptions an operator must understand. The smallest remedy is an explicit contract and a supported journey, not another lifecycle wrapper.

W4 · Tests are substantive, but passing fixtures are not sufficient

Negative cases now exercise real failure mechanisms: altered seeded tools, linked prompt files, EPIPE, malformed request targets, missing projection files and ambiguous remote URLs. The five layers have distinct value, and the root test command continues through all layers while retaining each exit code. These are stronger signals than test totals.

The route-vocabulary and interrupted-frame cases now have targeted regressions. The final repairs also bind gate measurements to the actual candidate rather than inventing successful evidence. Those are meaningful improvements in test effectiveness. The seed fingerprint’s stronger consumer assumption and CI’s missing trap layer remain gaps. The cleanup fence now tests narrow approved exceptions alongside negative controls. Preserve those controls as cleanup evolves rather than treating a green fence as an unlimited guarantee.

W5 · Coupling and ceremony have a measurable maintenance cost

The reviewed-to-current diff spans 687 files, 43,661 insertions and 5,100 deletions, from git diff --shortstat 335a184..057370d. This confirms substantial activity, not its quality. wc -l core/src/cli/commands/{production-run,rework,adopt}.ts reports 4,793, 1,750 and 1,354 lines respectively. Related launch, gate, duration and failure behavior crosses these command paths. The wall-clock and timeout inconsistencies show the practical risk of maintaining parallel orchestration logic.

The shared artifact reader, identity helper and environment filter reduce that risk. Further generalization should follow a demonstrated repeated bug, not precede one. Plans, canonical prompts, mirrored tickets, closure deltas and meta-tests provide traceability, but each additional representation also creates synchronization work. The light tier is therefore important. Do not add another evidence database to fix the remaining incorrect ledger citations.

W6 · The product bottleneck remains the owner’s work

Setup still depends on storage placement, provider access, catalog agreement, protected-path grants and a correct request. Recovery and publication remain consequential owner decisions. Those constraints are often appropriate. What is not yet established is that the complete workflow saves the owner more effort than it consumes. Earlier v3 measurements correctly motivated host-driven procedure and context reduction. No comparable new operating sample supports a post-remediation productivity claim.

A useful proof measures a finished request rather than an isolated phase. Count owner intervention time, number and reason of restarts, time to a usable result, provider consumption, successful recovery, and whether the result is actually used and retained. Keep the denominator visible, including abandoned and blocked work. The factory should not earn credit merely by generating more work for itself.

09

Final judgment

A credible contribution, with a bounded promise.

ELI · The final verdict

The repairs now have stronger evidence: the final recorded suite passes and several previously reproduced defects are gone. AWSF is a more credible software-building component for one owner. Remaining recovery and assurance gaps prevent an unrestricted reliability claim. The larger vision still needs a useful result you can recover, improve and keep with less effort.

J1 · Have the original findings been meaningfully addressed? Yes, in substantial and consequential areas. The strongest evidence is in repaired authority, execution and evidence boundaries. Acceptance is restored in the final recorded run, and the previously blocked owner decisions have scoped resolutions. A blanket claim that every finding is resolved remains unsupported because residual mechanisms, accepted limitations and 766 independently unverifiable findings remain.

J2 · Can the remaining AWSF plan produce a dependable factory? Plausibly, within its single-owner scope and with additional proof. Host-held procedure, legal next steps, better context, user-level checks and a staging feedback loop target real problems. The restored acceptance baseline makes this projection more credible. Finishing the plan is still insufficient if CI and operational gates diverge, recovery requires expert intervention or the owner’s total work does not improve. Future deep-plan approval and external dependencies remain conditions.

J3 · Is this becoming a credible foundation for the wider personal-AI vision? Yes, as its governed creation component. The broader product still needs an approachable interaction layer, permission-aware application operation, durable customer continuity, supported model choices and version-specific reuse evidence. Those are separate product and integration commitments, not promises that can be inferred from a software factory’s test suite.

The next meaningful milestone is a useful result that the owner can obtain, recover, improve and keep with less effort, under the same explicit authority boundaries. That is the evidence that should justify further expansion.
